# 事件驱动系统的边界设计

事件驱动不是“加一个消息队列”。它首先是一种边界表达：某个事实已经发生，其他模块可以按自己的节奏作出反应。

## 从预约成功开始

以校园场地预约为例，一次预约成功后通常需要：

- 锁定对应时段；
- 生成预约记录；
- 发送站内通知；
- 更新统计数据。

前两项决定预约是否成立，应该放在同一个本地事务中。通知和统计失败不应让预约回滚，更适合通过事件异步处理。

## 先画出一致性边界

可以把流程拆成两部分：

```text
[预约事务]
  校验名额 -> 创建预约 -> 写入待发布事件

[异步反应]
  发布事件 -> 通知模块
           -> 统计模块
```

这里最关键的不是箭头，而是“创建预约”和“记录待发布事件”必须一起成功或一起失败。

## 处理重复，而不是幻想恰好一次

网络重试和消费者重启都可能让同一事件被处理多次。消费者应通过业务键或事件 ID 保证幂等：

```sql
insert into handled_event(event_id, handled_at)
values (?, now())
on conflict (event_id) do nothing;
```

只有成功插入处理记录的消费者才继续执行业务逻辑。具体实现会因数据库而异，但原则是一致的。

## 失败必须可见

异步流程最危险的状态不是失败，而是静默失败。至少需要记录：

- 事件 ID 与业务关联 ID；
- 处理次数和最近错误；
- 下一次重试时间；
- 最终失败后的人工恢复入口。

## 什么时候不需要事件

如果两个步骤必须同时返回给用户、共享同一事务边界，而且没有独立演进的需要，直接调用通常更清晰。事件是解耦工具，也会引入延迟、重复和排障成本。

## 小结

判断是否引入事件时，我会依次确认事实边界、事务边界、幂等策略和失败恢复。只有四项都有明确答案，事件驱动才不是把复杂度藏进消息队列。
