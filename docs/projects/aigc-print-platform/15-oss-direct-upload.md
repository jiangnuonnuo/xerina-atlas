## 我为什么要把文件上传从应用服务器移开

图片、原始素材和压缩包都比普通业务字段大。如果文件先经过应用服务器，再由应用转发到对象存储，应用服务器会同时承担鉴权、网络中转和文件 IO，带宽和线程消耗都会随着文件大小增加。

我采用的思路是：应用服务器只负责签发一次性或短时有效的上传凭证，客户端直接把文件上传到 OSS；上传完成后，应用只接收文件标识、大小、类型和校验结果。

这条链路里我刻意区分了三种数据：文件字节、对象元数据和业务归属。文件字节由浏览器和 OSS 传输，元数据由服务端确认并保存，业务归属由服务端根据用户和任务校验。三者不能因为客户端上传成功就自动画等号。

## 一次上传的完整链路

### 1. 先创建待上传记录

客户端上传前先向后端提交业务对象、文件用途、大小和类型。服务端完成身份鉴权、用户权限、批次关系和配额检查后，创建一条待上传记录，并由服务端生成对象 Key。这个 Key 绑定用户、业务对象和随机部分，客户端只能拿到它，不能自行决定目录或覆盖其他对象。

待上传记录的作用是让后续的签名、上传确认、回调补偿和孤儿清理有共同依据。客户端如果在签名成功后关闭页面，记录仍然可以被定时任务识别为超时待上传，而不是永久占用业务状态。

### 2. 服务端签发受限凭证

客户端向后端申请上传凭证时，需要携带业务类型和文件信息。服务端完成用户权限、目录、文件类型、大小和数量校验后，生成限定 Bucket、对象前缀、有效期和回调信息的临时凭证。

凭证不能只返回一个长期 AccessKey。生产化控制至少包括：

- Bucket 保持私有。
- 对象 Key 使用服务端生成的目录和随机部分，不能允许客户端任意覆盖路径。
- 限制文件大小、MIME 类型和数量。
- 设置较短有效期，过期后重新申请。
- 回调中校验对象 Key、文件大小和业务归属。

签名接口还要防止“签名成功但业务记录没有落库”的情况：先创建待上传记录，再签发与该记录绑定的 Key；签名响应只返回必要的临时字段，不返回长期密钥。服务端日志记录的是任务 ID 和对象 Key，不记录完整凭证内容。

### 3. 客户端直接上传 OSS

拿到凭证后，浏览器把文件直接发送到 OSS。应用服务器不接收文件流，也不需要为每个文件建立长连接。

小文件可以直接上传，大文件则需要根据客户端能力使用分片或断点续传。无论使用哪种方式，上传过程中的分片状态都不直接代表业务成功，只有最终合并完成并能通过服务端确认，文件才进入可使用状态。

直传成功后，客户端把上传结果或文件标识提交给业务接口。服务端再次校验上传对象是否位于允许目录、是否属于当前用户、大小和类型是否符合预期，然后保存文件元数据。

### 4. 上传确认不是相信客户端参数

确认接口根据待上传记录查询对象存储的实际元数据，至少校验对象是否存在、大小、Content-Type、ETag 或业务侧校验和。对图片类文件，还可以在异步处理中读取文件头或做安全扫描，不能只相信前端传来的扩展名。

确认成功后才把文件状态推进为可用，并把对象 Key 与业务对象绑定。确认失败时保留失败原因；如果对象已经存在但元数据不匹配，不能直接覆盖或继续使用。

### 5. 生成结果使用预签名地址访问

生成图片或压缩包存储在私有 OSS 中，用户查询任务结果时，服务端根据权限生成短时预签名 URL。前端直接从 OSS 加载或下载，应用服务器只处理任务查询和访问授权。

预签名 URL 不是永久文件地址，过期后重新生成；用户没有权限时，不能仅凭对象 Key 自行构造可访问地址。

下载接口返回预签名地址前，先检查当前用户是否仍然拥有业务对象权限、文件状态是否可访问。URL 的有效期不宜过长，日志和页面也不把它当成永久资源地址保存；如果前端缓存了过期地址，重新请求授权即可。

## 上传和下载的异常处理

| 异常 | 处理方式 |
| --- | --- |
| 凭证过期 | 客户端重新申请，不能复用旧凭证 |
| OSS 上传失败 | 保留任务为待上传或失败，允许有限重试 |
| 回调丢失 | 通过客户端确认接口或定时校验对象元数据补偿 |
| 文件类型不符 | 服务端拒绝元数据确认，不仅依赖前端扩展名 |
| 预签名地址过期 | 重新鉴权并签发新地址 |
| 结果上传失败 | 记录失败原因，避免把临时第三方地址当成永久结果 |

还需要处理两个不明显的问题：

- **孤儿对象**：签名成功但业务确认没有完成的对象，定时任务根据待上传记录和对象创建时间清理；清理前要再次确认没有正在进行的分片上传。
- **重复确认**：客户端因为网络超时重复调用确认接口时，服务端重复返回已确认结果即可，不能重复创建文件记录或重复触发 AI 任务。

上传确认成功后，如果后续生成任务入队失败，也不能要求用户重新上传。文件已经是可用事实，只需要补偿任务入队；这样文件链路和 AI 任务链路的失败不会互相放大。

AI 结果有时来自第三方 URL。此时服务端仍可能需要把结果下载后转存到 OSS，但这属于“上游结果归档”，和“用户原始素材直传”是两条不同路径，文章中不能把它们混为同一种直传。

结果归档同样要限制来源、响应大小、下载超时和重试次数，防止把一个外部 URL 当成无限制的服务端下载入口。归档成功后保存对象 Key 和元数据，原始第三方地址只作为调试或追踪信息，不直接交给用户长期访问。

## 我如何验证直传真的减少了应用压力

改造前后我会分别记录上传请求耗时、应用服务器出网流量、OSS 成功率、确认接口延迟和失败重试量。只看到前端页面变快还不够，因为可能只是图片缓存生效；只有应用出网流量下降、文件字节不再经过应用实例，才能证明链路发生了变化。

验证时需要固定图片大小、网络环境和缓存条件，并区分上传耗时与下载加载耗时。小文件直传成功，也不能直接推导出大文件分片和断点续传没有问题，这些需要单独验证中断、重试和重复确认。

## 性能指标的计算口径

图片加载耗时应明确是首字节、首屏可见还是整张图片加载完成；带宽占用应明确统计的是应用服务器出网带宽，还是整个云账号的出网流量。本文沿用简历口径：图片加载约由 300ms 降至 120ms，服务器出网带宽占用由 80% 降至 20% 以下。

这个优化的价值不只是“上传更快”，更重要的是把应用服务器从文件中转链路中移除，让计算资源集中处理任务编排、状态更新和权限控制。

从故障恢复角度看，直传还让问题边界更清晰：凭证失败属于鉴权和签名问题，上传失败属于 OSS 或网络问题，确认失败属于对象校验问题，任务入队失败属于消息补偿问题。每一类故障都有自己的重试和告警入口，不需要通过重新上传或重新生成来碰运气。
