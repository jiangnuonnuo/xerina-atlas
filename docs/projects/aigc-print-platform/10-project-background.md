## 1. 一句话定义

**AIGC 打印平台**：面向电商运营/设计团队的一站式 AI 图片内容生产系统——用户提交"提示词/素材图"，系统调用 Midjourney、第三方 AIGC 绘图 API（印花提取、产品生场景、服装换装），批量生成可商用的高清图片（印花纹理、模特场景图、换装效果图），并打包下载交付。

通俗类比：电商运营平时要做 100 张商品图，传统方式请设计师一张张做，几天工期、成本高；本平台让运营"输入一句话/一张素材，批量得到图片"，把从"天"缩短到"分钟"。

## 2. 业务场景（三大核心场景）

| 场景 | 输入 | 输出 | 业务价值 |
|------|------|------|---------|
| **批量 AI 绘图** | 数十~数百条提示词（+风格/视角/灯光/画质参数） | 批量生成图 + ZIP 打包下载 | 运营批量出图，替代人工 P 图 |
| **印花提取（Print Extract）** | 带褶皱/透视变形的布料实物照片 | 平整、无缝、透明底、4K 以上的印花纹理（PNG，可印刷） | 印花设计从"描图"变"一键提取" |
| **产品生场景 / 换装（Try-on）** | 白底商品图 + 场景/模特要求 | 模特场景合成图 / 服装上身效果图 | 商品详情页素材自动生产 |

## 3. 业务痛点（为什么需要这个平台）

1. **人工产能瓶颈**：电商 SKU 动辄上千，逐张人工处理图片周期以"天"计，无法支撑上新节奏；
2. **AI 生成耗时长**：单次 AI 生图 30s~2min（Midjourney），印花提取 10s+，若同步调用，用户提交后页面一直转圈，体验不可接受；
3. **上游服务不稳定**：Midjourney/第三方绘图 API 存在限流、排队、偶发失败、回调丢失；直接调用会导致任务"半途而废"且无法自愈；
4. **请求突发性强**：运营常一次性批量提交（波峰），且集中在大促前，直连上游会导致上游过载、排队失控；
5. **存储与带宽瓶颈**：图片流量全部走应用服务器出网带宽（高峰期占用 80%），本地磁盘扩容小时级，图片加载慢（约 300ms）；
6. **失败不可追踪**：任务失败后用户只能"重新提交"，无法知道失败原因、无法续跑，运营成本高。

## 4. 项目目标（SMART 化）

| 维度 | 目标 |
|------|------|
| 吞吐 | 系统峰值处理能力 **50+ QPS**（消费端聚合消费速率） |
| 可靠性 | 任务最终成功率从 **75% 提升到 90% 以上**；消息零静默丢失 |
| 性能 | 提交接口毫秒级返回；图片加载 **300ms → 120ms** |
| 成本/容量 | 服务器出网带宽占用 **80% → 20% 以下**；存储扩容 **小时级 → 分钟级** |
| 可运维 | 全链路 traceId 可查、异常按层分类、告警分级、任务状态收敛到终态 |

## 5. 量化基线（优化前 vs 目标）

| 指标 | 优化前（基线） | 目标（优化后） | 测量口径 |
|------|--------------|--------------|---------|
| 提交接口耗时 | 分钟级（同步等待） | 毫秒级 | 生产观测 |
| 峰值处理能力 | 同步串行，受上游单次耗时限制 | 50+ QPS | 压测/生产高峰观测 |
| 任务最终成功率 | ~75% | ≥90% | 终态成功/(成功+失败) |
| 图片加载耗时 | ~300ms | ~120ms | 浏览器 Performance 全图加载 |
| 出网带宽占用 | 80% | <20% | 云监控出网流量/带宽上限 |
| 存储扩容 | 小时级 | 分钟级 | 运维变更时长 |

> 说明：以上量化指标为**简历口径**，其中压测数据、测量口径需在上线后补充监控/压测报告佐证（见 19-revision-and-metrics.md 待确认项）。

## 6. 系统边界（做什么 & 不做什么）

**做**：任务编排（提交/重试/超时/取消）、AIGC 上游对接（MJ Proxy + 第三方绘图 API）、结果存储与下载（OSS）、配额与计费（余额预校验、消费记录）。

**不做**（本期）：自研大模型/出图算法（调用第三方）；商品管理/订单等电商核心域（复用外部系统）；图片精修编辑能力（仅生成与下载）。

## 7. 关键角色与术语定义（小白速查）

| 术语 | 定义 |
|------|------|
| **批量任务** | 用户一次提交的整批请求（如 100 条提示词），主表 `sys_mj_batch_task` |
| **子任务** | 批量任务中的单条提示词/单张图，主表 `sys_mj_batch_prompt` |
| **上游 / 第三方 API** | Midjourney Proxy、grsai 等提供出图能力的服务，不可靠、按次计费 |
| **回调** | 上游出图完成后 POST 通知本系统（`/mj/run/{id}`），驱动任务状态流转 |
| **消息队列（MQ）** | 生产者→消费者之间的缓冲管道（本项目 RabbitMQ），实现异步与削峰 |
| **死信队列（DLQ）** | 处理失败且放弃重试的消息的"收容所"，用于归档/告警/人工重放 |
| **幂等** | 同一个操作执行多次，结果与执行一次相同（防止重复消费/重复扣费） |
| **Outbox 模式** | 先写本地消息表、事务提交后再发消息，保证"业务状态与消息不丢失"的一致性 |
