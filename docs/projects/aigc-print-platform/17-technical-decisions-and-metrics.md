## 我为什么选择这些方案

| 问题 | 我的选择 | 选择依据 |
| --- | --- | --- |
| AI 任务耗时长 | RabbitMQ 异步任务 | 需要低延迟入队、消费者并发和失败路由，业务量不需要复杂流式计算 |
| 上游不稳定 | 状态机 + 分类重试 + 死信 | 让自动恢复有边界，失败任务可追踪、可人工处理 |
| 回调可能异常 | 回调 + 受控查询 | 回调负责及时性，受控查询负责最终收敛 |
| 重复消息 | 任务 ID + 消息键 + 条件更新 + 上游 ID 防重 | 至少一次投递下保护本地状态和外部任务 |
| 文件体积较大 | OSS 直传 + 预签名访问 | 应用保留鉴权和元数据职责，文件流量走对象存储 |

这些选择不是一开始就确定的。最初更容易想到的是接口里直接调用上游、失败后立即重试、把文件先传到应用再保存。它们在功能演示阶段都能跑通，但在批量请求、上游变慢和文件变大后，问题会同时暴露：接口线程被占住、失败消息循环、结果地址失效、应用出网带宽升高。我的改造重点是把这些隐含的等待和副作用显式拆开。

| 改造前的表现 | 我做的拆分 | 改造后关注的结果 |
| --- | --- | --- |
| 请求一直等待上游返回 | 请求受理、消息执行、结果回调分段 | 入口响应和后台耗时分离 |
| 一个异常反复占用主队列 | 失败分类、延迟队列、最终死信 | 可恢复故障自动恢复，坏消息停止循环 |
| 回调和轮询各自改状态 | 统一状态迁移和条件更新 | 重复、乱序事件不覆盖新状态 |
| 文件经过应用中转 | 凭证签发、客户端直传、服务端确认 | 应用只处理鉴权和元数据 |

## 关于如何简述我完成的核心任务场景

### AI 任务异步化

AI 生图和视频生成耗时长、同步调用容易阻塞的问题，将任务提交和任务执行拆开：提交接口完成校验和任务落库后立即返回，RabbitMQ 负责缓冲任务，多个消费者按受控并发调用上游，回调或轮询再更新最终状态。通过消费者并发、prefetch、上游账号限制和超时控制，系统能够在请求波峰时削峰填谷。峰值处理能力需要明确是入队、消费受理还是端到端完成能力，并结合稳定窗口和资源指标验证。

这项工作真正难的地方不是创建一个队列，而是处理“任务已经落库、消息还没发出”“消息重复、上游可能已受理”“结果回调到了、文件还没归档”等中间状态。我把消息收敛到任务 ID 和稳定的上游请求 ID，消费者每次执行前重新读取任务事实，状态和结果写入完成后再确认消息；本地状态检查尽量跳过重复消费，即使消费者退出导致消息重投，再次提交也会复用原 ID，由上游完成防重。

### 任务可靠性

Midjourney 等上游服务的限流、超时、排队和回调异常，明确了提交、处理中、成功、失败和重试状态，并按异常类型决定是否重试。可恢复异常进入有界延迟重试，不可恢复异常直接失败，超过重试上限的消息进入死信，由人工确认后再重放；数据库唯一业务键和状态条件更新用于防止重复提交、重复回调和重复副作用。任务最终成功率需要以进入成功或失败终态的业务任务为统计对象，并说明统计窗口和任务类型。

我没有把重试次数简单调大。对于提交超时这类结果未知的异常，沿用原任务 ID 或请求 ID 重新提交或查询，让上游按原 ID 识别重复请求并保持防重；对于 429 和 5xx，延迟并降低对应账号并发；对于参数错误和审核拒绝，直接结束并保存可读原因。重试消息需要记录轮次、错误分类和下一次执行时间，死信则保留完整上下文，人工重放也必须沿用原 ID，再次经过状态检查和限流。

### OSS 直传

大文件经过应用服务器造成的加载慢和带宽占用问题，让服务端只负责生成受限的临时上传凭证，客户端直接把素材上传到 OSS；结果文件通过私有 Bucket 和短时预签名 URL 访问。服务端保存文件元数据和权限关系，不再承担所有文件流量转发。现有材料记录的观测结果是图片加载约由 300ms 降至 120ms，应用服务器出网带宽占用由 80% 降至 20% 以下，但仍需要明确图片大小、缓存命中和统计环境。

这里的关键是“直传完成不等于业务文件可用”。我先创建待上传记录，再签发绑定对象 Key 的临时凭证；上传完成后由服务端确认对象实际存在、大小和类型符合预期，之后才把文件与业务任务绑定。签名过期、上传中断、确认重复、回调丢失和孤儿对象都有独立的补偿路径，不通过让用户反复上传来解决。

## 指标复盘时必须说明什么

| 指标 | 必须补充的口径 |
| --- | --- |
| 50+ QPS | 提交、消费还是端到端吞吐；消费者数量；平均耗时；P95/P99 |
| 75% → 90%+ | 统计时间窗；任务类型；成功和失败终态定义；是否排除取消任务 |
| 300ms → 120ms | 首字节、首屏还是全图加载；图片大小；客户端和网络环境 |
| 80% → 20% 以下 | 应用服务器出网还是云账号总带宽；统计峰值还是平均值 |

除了结果指标，我还会保留过程指标来解释为什么结果发生变化：

| 链路 | 过程指标 | 能定位的问题 |
| --- | --- | --- |
| 异步任务 | 入队延迟、消费延迟、队列深度、未确认消息 | 入口变慢还是消费能力不足 |
| 上游调用 | 连接耗时、响应耗时、429、5xx、提交未知量 | 上游限流、网络问题还是结果不确定 |
| 重试可靠性 | 各轮重试量、死信量、重复消费量、最终终态耗时 | 重试是否恢复，是否出现重试风暴 |
| 文件链路 | 签名失败、直传成功率、确认延迟、应用出网流量 | 凭证、OSS、确认还是中转造成问题 |

指标采集也要注意去重。重试次数不能被误当成任务数，消息消费次数不能被误当成成功次数，图片加载耗时还要区分缓存命中和真实下载。只有业务任务、投递尝试和文件对象三个层次分开统计，数字才有解释力。

复盘时我会把“实际项目基础实现”和“生产化补充方案”分开说明：前者对应真实代码和业务链路，后者用于补齐一致性、幂等、重试边界和可运维性，避免把设计建议误写成已经上线的能力。

## 我如何判断改造没有引入新问题

我会用四类结果验证改造：

1. **功能闭环**：正常提交、上游成功、回调成功、结果可访问。
2. **重复安全**：重复点击、重复消息、重复回调、重复确认都只产生一次有效业务结果。
3. **异常恢复**：消费者退出、上游超时、429、回调丢失和 OSS 上传失败都能在边界内恢复或进入明确终态。
4. **容量和资源**：队列有积压时，消费者、HTTP 连接池、数据库连接池和应用带宽没有超过上限。

如果只验证“接口返回 200”，只能说明入口功能存在，不能说明异步任务最终会完成。对这类项目，我更看重任务是否最终收敛、失败是否可解释、恢复是否会产生重复副作用。
