## 我为什么没有只配置一个并发数

AI 任务的耗时主要由外部服务决定。同一个消费者线程可能遇到快速失败，也可能等待几十秒。如果只使用单线程，吞吐会被最慢的任务拖住；如果无限提高并发，上游账号、HTTP 连接池和数据库连接又会先达到上限。

所以我把“并发”看成一个受约束的容量参数，而不是越大越好。

我实际排查这类问题时，先问的不是“线程池要开多大”，而是“一个并发任务会同时占用哪些资源”。一个消费者任务可能同时占用一个消费槽位、一个 HTTP 连接、一个上游账号配额和一次数据库连接。如果只调大消费者线程数，最先被打满的可能是上游账号或数据库连接池，最终表现为队列更长、超时更多，吞吐反而下降。

因此并发配置需要跟任务类型绑定。生图、视频、印花提取的平均耗时、请求大小和上游限制不同，不能共用一个没有上限的线程池。短任务可以使用相对高一些的消费并发，长任务则需要更小的并发和更严格的超时。

## 我关注的四个资源边界

### 消费者并发

绘图、印花提取、场景合成等任务按业务类型使用独立队列和消费者。消费者并发设置为一个范围，允许实例在积压时扩展，但设置最大值，避免扩容后把压力一次性传给上游。

消费者使用手动确认消息。任务执行期间不提前 ack，只有本地状态和必要的外部任务标识保存成功后才确认；消费者异常退出时，未确认消息可以重新投递。为了避免一个实例预取大量长任务，我把 prefetch 控制在较小范围，让任务尽量均匀分配到空闲消费者。

### Prefetch 与未确认消息

prefetch 决定一个消费者在完成当前任务前最多预取多少消息。对于耗时差异较大的 AI 任务，prefetch 过大容易造成任务分配不均和内存占用；我更倾向于小批量预取，让空闲消费者能较快获取下一条任务。

prefetch 过小也不是绝对正确：如果任务非常短，消费者会频繁往返 RabbitMQ，吞吐会受到网络开销影响。所以我会先按最长常见任务的耗时和实例内存估算，再用队列深度、未确认消息数和消费延迟验证。配置调整后需要观察一段时间，不能只看瞬时 QPS。

### 上游账号与 HTTP 连接

消费者并发不是上游并发。对同一上游账号设置信号量或令牌限制，单次调用配置连接超时、读取超时和总执行超时。出现 429 或排队过长时，任务进入延迟重试，不继续扩大瞬时并发。

同一个上游账号可能被多个实例共同使用，本地线程池的并发限制不能覆盖集群总量。因此账号级限制要么使用 Redis 等共享协调，要么为每个实例预留保守额度，并通过监控观察总并发。共享限流组件短暂不可用时，默认采取保守策略，降低并发或拒绝新增任务，不能因为限流失效就全部放开。

我估算某类任务的可用并发时，会取多个资源上限中的最小值：

```text
可用并发 = min(消费者线程上限，HTTP 连接上限，数据库连接上限，上游账号并发上限)
```

这个式子不是精确容量模型，但能提醒我不能只看线程池。实际值还要扣除回调、轮询和结果归档占用的资源，并通过压测和线上监控逐步校准。

### 数据库连接与状态写入

消费者只有在关键状态变化时写库：开始处理、拿到外部任务 ID、回调成功、最终失败。重复回调和重复消息只做一次有效更新，避免把数据库写入量放大成消息量的数倍。

状态写入要尽量短事务，不能在事务里等待上游 HTTP 或下载文件。对于轮询任务，我按主键或更新时间分段扫描并限制单次数量，避免一次扫描锁住大量任务；更新失败时先区分死锁、连接耗尽和业务状态不匹配，再决定重试或告警。

## 积压时我如何判断是否需要扩容

我不会只看队列深度，而是同时观察：

| 信号 | 说明 | 处理判断 |
| --- | --- | --- |
| 队列深度 | 尚未被消费者取走的任务数量 | 持续增长才说明消费能力不足 |
| 消费速率 | 单位时间完成的消费数量 | 与目标吞吐和上游限流一起看 |
| 上游耗时/429 | 依赖侧是否成为瓶颈 | 依赖变慢时扩容消费者可能适得其反 |
| 数据库连接等待 | 状态更新是否阻塞 | 连接池紧张时先降低并发 |
| 失败和重试量 | 是否因为异常造成重复压力 | 区分流量增长和故障放大 |

队列的作用是把峰值流量摊平，而不是掩盖永久性容量不足。如果积压持续增长，就需要扩大消费者、优化上游调用或限制入口流量；如果只是短时波峰，队列本身就能完成削峰填谷。

我会把扩容判断拆成一个小闭环：

1. 先确认入口流量是否突然增加，排除重复投递或重试风暴。
2. 再确认消费者是否真的在工作，查看消费速率、未确认消息和线程池活动数。
3. 如果消费者活跃但上游耗时和 429 同时上升，先降低上游账号并发，不直接扩容。
4. 如果上游稳定而数据库连接等待上升，先减少状态写入和轮询批量，再评估数据库容量。
5. 只有资源指标都在安全范围内、队列仍持续增长时，才增加消费者实例。

这样可以避免把“队列有积压”误判成“消费者太少”。真实故障中，重试消息过多、上游响应变慢和数据库连接池耗尽都可能制造同样的表象。

## 50+ QPS 的指标口径

本文沿用简历中的“峰值处理能力 50+ QPS”表述，但在技术上需要先定义被测对象：

- **提交 QPS**：接口每秒创建并入队的任务数。
- **消费 QPS**：消费者每秒从队列取出并完成本地受理的任务数。
- **端到端吞吐**：任务从提交到最终成功或失败的每秒完成数。

由于 AI 任务本身耗时较长，三者不能直接等同。更可靠的记录方式是同时保存并发消费者数、平均上游耗时、P95/P99、失败率、重试量和队列峰值，再说明 50+ QPS 对应哪一项。

如果要复核这个指标，我会准备固定数量的消费者实例和固定的任务样本，先预热连接池，再分阶段增加入口流量，记录稳定窗口而不是只取单秒峰值。压测任务使用脱敏输入，避免把真实用户素材和真实上游账号带入测试；上游不可压测时，只能把结果表述为“本地入队或消费受理能力”，不能冒充完整的端到端生成吞吐。

## 我最终采用的控制关系

```text
入口限流
   ↓
RabbitMQ 缓冲
   ↓
消费者并发上限
   ↓
上游账号/连接池限流
   ↓
数据库状态写入与幂等更新
```

这条链路中任何一层达到上限，都应该通过排队、延迟重试或降级把压力挡在边界内，而不是让线程无限等待。

当消费者扩容时，新增实例会同时增加 RabbitMQ 消费者、上游请求和数据库写入，三个量几乎会一起增长。因此扩容动作必须有回退条件：队列不再增长但上游 429、数据库连接等待或接口错误率超过阈值时，立即停止扩容并降低并发。这个回退边界比“自动扩到最大实例数”更重要。

## 这项工作的价值

我解决的不是“把线程数从 1 改成 10”，而是让消费者并发、上游限制和数据库资源形成可解释的控制关系。这样在批量任务波峰到来时，系统能够保持可预测的处理速率，也能在依赖变慢时保护自身。

从开发结果看，异步化之后最直观的变化不是所有任务都立即完成，而是提交请求的响应时间和后台执行时间被分离：入口可以稳定受理，队列吸收短时波峰，消费者按资源上限推进，失败任务也不会因为一次重试把全部消费能力拖住。这才是 50+ QPS 能够成立的前提。
