## 我把控制点放在链路边界

三个简历要点虽然方向不同，但都涉及“外部依赖不可控”。我的处理原则是：入口限制流量，执行限制并发，状态记录事实，异常设置上限，结果通过权限受控的地址交付。

开发时我会给每个边界回答三个问题：调用方最多能提交多少、当前动作最多等待多久、失败后最多产生多少次副作用。只有把这三个上限写进配置、日志和状态里，故障时才有办法判断系统是在正常排队，还是已经进入失控状态。

## 入口和执行控制

| 边界 | 控制方式 | 避免的问题 |
| --- | --- | --- |
| 用户提交 | 用户、批次大小、文件大小和请求频率限制 | 单个请求占满系统资源 |
| 消费者 | 并发上限、prefetch 和队列隔离 | 一类任务拖垮所有消费者 |
| 上游账号 | 信号量、令牌桶和 429 退避 | 触发上游封禁或持续排队 |
| HTTP 调用 | 连接、读取和总耗时超时 | 线程和连接长期挂起 |
| 数据库 | 连接池、短事务和批量扫描上限 | 状态更新反向拖慢消费 |
| OSS | 临时凭证、目录、大小和类型限制 | 文件越权、覆盖和带宽中转 |

这些控制点需要互相配合。入口批次大小限制只能防止单次请求过大，不能防止多个用户同时提交；用户级限流只能限制调用方，不能替代上游账号级限流；RabbitMQ 能够承接突发流量，也不能替代任务最大执行时长。每一层只解决自己的边界问题，不能把所有保护都压到队列上。

## 超时要分层

不能用一个“8 小时超时”覆盖全部任务。至少要区分：

- 接口超时：只覆盖校验、落库和投递，不等待生成。
- 上游提交超时：连接和读取分别设置边界。
- 生成超时：从拿到外部任务 ID 开始计算最大处理时长。
- 回调等待超时：回调迟迟不到时由轮询接管。
- 压缩和文件交付超时：独立于上游生成超时。

超时任务必须先确认外部任务是否仍在运行，再决定取消、继续轮询还是标记失败，避免本地失败后上游仍然继续生成并产生无法归属的结果。

超时处理本身也可能失败。例如本地请求超时后，上游查询接口再次超时；这时不能在每次定时扫描时无间隔地继续查询。需要记录下一次查询时间、连续失败次数和最后一次确定状态，按退避策略重试，并在超过总时长后进入人工对账或明确失败。

## 可观测性至少要能回答五个问题

1. 这个任务是谁提交的、属于哪个批次？
2. 消息进过哪个队列、消费了几次、最近一次失败是什么？
3. 上游返回了什么分类，当前外部任务 ID 是什么？
4. 回调、轮询和状态更新谁先到，最终由哪一次事件生效？
5. 50+ QPS、90% 成功率和带宽变化是在什么时间窗口测出来的？

为此需要把 traceId 或 taskId 贯穿接口日志、消息属性、上游请求和回调处理；同时监控队列深度、消费速率、重试量、死信量、上游耗时、429 比例、数据库连接等待和 OSS 上传失败率。

我还会把日志分成“尝试”和“结果”两类。一次上游调用有开始时间、结束时间、超时阶段和外部任务 ID；一次状态迁移有旧状态、新状态、事件来源和是否生效。这样同一个任务出现两次调用时，可以判断是合法重试、消息重复，还是幂等控制失效，而不是只看到两条相似的错误日志。

## 降级和恢复

- 上游不可用时，停止继续放大并发，让任务进入有限重试或明确失败。
- 回调服务异常时，保留任务记录，由轮询补偿。
- Redis 限流不可用时，使用本地保守限流或直接降低入口流量，不能无条件放开。
- OSS 暂时不可用时，保留任务状态和文件元数据，避免重复生成 AI 结果。
- 死信量突增时，优先暂停自动重放，先确认故障原因和重试风暴风险。

这些措施的共同点是：故障发生时减少副作用，恢复后从本地事实继续，而不是依赖用户重新提交。

## 我如何做一次故障演练和上线验证

在修改消费者或重试逻辑后，我会用脱敏任务验证几类边界：消费者在 ack 前退出、上游返回 429、HTTP 读取超时、回调重复、回调乱序、结果归档失败、OSS 凭证过期以及数据库短暂不可用。每个场景都需要明确预期：消息是否重新投递、任务状态是否推进、是否产生新的外部任务、是否触发告警、最终是否能人工恢复。

上线时先小范围启用新消费者或新上传路径，观察队列深度、任务成功率、重复消息量和应用出网流量。发现异常时，优先关闭新增流量入口或暂停自动重试，保留已有任务记录和死信，不直接删除现场。确认原因后再恢复消费，避免边排查边继续制造更多失败任务。

## 发生故障时我的排查顺序

1. 用 taskId 或 traceId 找到任务当前状态和最近一次状态事件。
2. 判断任务是否已经产生外部副作用，先排除重复提交风险。
3. 查看消息投递、消费次数、重试次数和死信原因。
4. 再看上游响应、数据库写入和 OSS 对象状态，定位真正的阻塞边界。
5. 根据状态选择补偿、重试、人工重放或停止处理，不直接让用户重新提交。

这个顺序可以避免两个常见误判：把消息没有消费当成上游失败，把文件访问失败当成 AI 生成失败。只有先还原事实，再选择恢复动作，才能保证优化没有带来新的重复副作用。
