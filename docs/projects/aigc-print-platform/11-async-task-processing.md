## 我先拆开“提交”和“执行”

最初的同步思路是：接口接收请求后，直接调用上游并等待结果。这个方式在单次请求下比较直观，但不适合 AI 任务：上游耗时不可控，批量请求会占满接口线程，失败重试还会继续延长请求时间。

我把链路拆成两个阶段：

1. **提交阶段**：校验输入、创建主任务和子任务、保存必要参数、投递消息，然后立即返回任务 ID。
2. **执行阶段**：消费者从 RabbitMQ 取出子任务，调用上游，保存外部任务标识，再由回调或轮询更新最终结果。

这样，接口耗时不再等于 AI 生成耗时，队列也成为入口流量和上游处理能力之间的缓冲层。

我在实现时把“异步”具体化成三个约束：接口线程不能等待生成结果；消息不能依赖进程内对象；消费者不能把一次上游调用的失败直接当成整个批次失败。只有这三个约束同时成立，异步化才不是把同步代码换到线程池里，而是把任务生命周期真正交给后台处理。

## 一条任务是怎样走完的

下面以一个批量任务为例说明完整路径。批量任务在内部会拆成多个子任务，每个子任务独立调用上游、重试和回写，主任务只做进度和结果汇总。

### 1. 请求进入：先做准入和幂等

我在提交接口中保留四类快速动作：身份和权限校验、参数校验、配额预检查、任务记录创建。请求会生成或接收一个业务幂等键，服务端在创建主任务前先判断这个键是否已经受理；重复点击时返回已有任务 ID，不能因为前端重试就再次扣配额或创建一批外部任务。

主任务和子任务在一次短事务中建立，子任务保存输入引用、业务类型、初始状态和重试计数，不保存图片二进制。事务提交前不能把“任务已成功”返回给前端，提交后返回的是 `taskId` 和初始状态。

这里的关键不是“把代码放到异步线程里”，而是先把任务事实保存下来。只有任务记录存在，后续的消息重投、回调、轮询和用户查询才有依据。

### 2. 任务落库后：处理消息投递的不一致

任务落库和消息投递是两个系统动作，不能假设它们天然是一个事务。最容易出现的两个故障是：任务已经落库但消息没有发出去，或者消息已经发出但接口进程在记录状态前崩溃。

我把消息设计成可补偿的执行意图：任务记录保存“待投递”或“已投递”事实，投递失败由补偿扫描再次发送；消费者拿到重复消息时依靠任务状态和幂等键跳过已经完成的执行。对于要求更严格的场景，可以把待发送消息写入本地消息记录，由事务提交后的投递器负责发布，这个做法比在事务里直接等待 RabbitMQ 更容易控制数据库事务时长。

无论采用哪种投递方式，都要接受消息可能重复、延迟或乱序，不能把“只收到一次”作为正确性的前提。

### 3. 消息只承载执行意图

消息中只放任务 ID、子任务 ID、业务类型、幂等键和必要的版本信息，不把大图片内容和完整业务对象塞进消息。消费者拿到消息后，根据 ID 查询任务事实，避免消息体过大，也避免消息中的旧数据覆盖数据库中的新状态。

消息还需要带上投递次数、创建时间和追踪标识。消费者可以据此区分首次投递和延迟重试，日志也能把一次任务的接口请求、队列消费、上游调用和回调串起来。消息中不放临时签名 URL，因为 URL 可能过期；消费者需要时根据文件元数据重新获取短时地址。

### 4. 消费者先检查状态，再调用上游

消费者从业务队列取出一条子任务后，不会直接调用上游，而是按以下顺序处理：

1. 解析消息并校验任务 ID、业务类型和幂等键。
2. 查询本地状态，只有待处理或明确允许重试的状态才能继续。
3. 获取对应上游账号的并发许可，超过上限就延迟处理，不在当前线程里长时间等待。
4. 调用上游提交接口，分别设置连接超时、读取超时和总耗时。
5. 保存外部任务 ID、提交时间和响应分类，再确认消息。

如果任务已经成功、失败或被取消，说明这是一条迟到消息或重复消息，消费者只记录一次跳过原因；如果任务已经被其他消费者抢先推进，当前消息也不能再次提交上游。

处理成功的含义是“上游已经接受并且本地记录已经保存”，不是“图片已经生成完成”。生成完成由上游回调或定时查询驱动。

### 5. 上游受理和最终完成是两个状态

我把上游调用拆成“提交动作”和“生成结果”两个阶段。提交响应只证明上游受理成功，不能把它直接写成最终成功；本地至少要保存外部任务 ID、上游状态、最近查询时间和最后一次错误。

这里有一个实际困难：提交接口超时后，客户端可能已经创建了外部任务。此时不能盲目重试提交，而要先用业务幂等键、请求指纹或上游任务查询确认是否已经受理；如果上游没有提供查询能力，就把任务放入“提交结果未知”的补偿状态，由人工或定时任务确认，而不是静默创建第二个任务。

### 6. 结果通过回调和轮询完成闭环

回调接口只做快速校验、幂等判断和状态更新，不在回调请求中进行压缩、批量下载等重操作。对于没有回调的任务，定时任务根据外部任务 ID 主动查询，直到成功、失败或超时。

回调链路至少要校验签名或来源、外部任务 ID、业务归属和状态版本。回调可能重复到达，也可能先到成功、后到处理中；状态更新必须使用允许迁移条件，迟到事件不能把成功状态改回处理中。

轮询任务按时间窗口分批扫描，只处理仍处于处理中且未超过最大执行时长的任务。扫描本身也要限速，避免回调丢失后所有任务同时查询上游。连续查询失败时走和消费者一致的失败分类与退避规则。

### 7. 结果归档：把外部地址变成本地事实

上游返回图片地址后，我不会直接把这个地址当成永久结果。结果处理器先校验响应，再把文件转存到对象存储，保存对象 Key、文件大小、类型和校验信息，最后才把子任务推进到成功。

下载、转存、压缩都属于独立的重操作，不能放在回调 HTTP 请求里同步完成。转存失败时保留“生成完成、结果待归档”的中间事实，允许只重试归档，不重新调用上游，从而避免重复生成和重复计费。

### 8. 批次汇总：处理部分成功和重复完成

当一个批次的子任务全部进入终态后，再触发图片聚合、压缩和文件交付。用户查询的是本地任务状态，避免把上游接口直接暴露给前端。

主任务不能只用一个成功计数判断完成，因为子任务可能重复回调。每次子任务从非终态首次进入成功、失败或取消时，才更新主任务计数；计数更新和状态迁移在同一事务中完成。主任务的结果需要区分全量成功、部分成功和全量失败，部分成功不能被异常处理器误判为系统故障。

## 我在落地时遇到的几个难点

### 任务落库成功但消息丢失

如果接口先写库后发消息，进程可能在两步之间退出。我通过待投递状态和补偿扫描保证任务最终能再次进入队列；补偿任务本身也带幂等条件，不能因为重复扫描产生多条有效执行。

### 消费者宕机导致消息重复

消费者可能已经调用上游，但还没有来得及保存外部任务 ID 就宕机。重新投递时，本地看起来仍是待处理。此时需要优先使用业务幂等键或上游查询确认，无法确认时进入提交未知状态；“手动 ack”只能保证消息重新投递，不能单独保证外部调用不重复。

### 回调成功但结果下载失败

我把上游生成成功和结果归档拆开，保留可恢复的中间状态。这样文件网络异常只会重试下载或 OSS 写入，不会重新走生图流程。

### 批量任务中只有部分子任务失败

主任务汇总必须等待所有子任务进入终态，不能第一个失败就直接结束整个批次。前端查询返回已完成数量、失败数量和可重试数量，后续可以只重试失败子任务，不重复执行已经成功的子任务。

## 我用一张表固定每个阶段的责任

| 阶段 | 本地必须留下的事实 | 下一步触发者 | 失败后的动作 |
| --- | --- | --- | --- |
| 请求受理 | 主任务、子任务、业务幂等键 | 投递器或补偿任务 | 保持待投递，告警或补偿 |
| 消息消费 | 投递 ID、消费次数、开始时间 | 消费者 | ack 前退出则重新投递 |
| 上游提交 | 外部任务 ID、受理时间、响应分类 | 回调或轮询 | 分类重试或进入结果未知 |
| 生成处理中 | 外部状态、最近查询时间 | 回调或定时扫描 | 退避查询，超过总时长终止 |
| 结果归档 | 对象 Key、大小、类型、校验信息 | 归档任务 | 只重试归档，不重新生成 |
| 批次完成 | 子任务终态计数、交付状态 | 用户查询或通知 | 部分成功可单独重试 |

这张表对应到代码职责时，接口层只负责受理，消息生产者只负责发布，消费者只负责执行一次尝试，状态服务只负责合法迁移，回调和轮询只负责产生事件，归档任务只负责文件处理。职责拆开后，出现问题时能定位应该重试哪个动作，也避免一个异常处理器把整条链路重新执行。

代码层可以用下面的伪代码表达边界：

```text
submit(request)
  ├─ validate(request)
  ├─ transaction { createTaskIfAbsent(); createItems(); markPendingPublish() }
  ├─ publish(taskId, itemId, idempotencyKey)
  └─ return taskId

consume(message)
  ├─ item = load(itemId)
  ├─ if item is terminal → ack and return
  ├─ if claim(item) fails → ack and return
  ├─ result = submitUpstream(item)
  ├─ transaction { saveExternalId(); moveToProcessing() }
  └─ ack only after local facts are durable
```

这里的 `claim` 和 `moveToProcessing` 不是普通的无条件更新，而是带当前状态和版本条件的更新；`publish` 失败也不能把已经创建的任务删除，而是等待补偿。伪代码中的每一个分支，都对应后文的重试、状态机和幂等控制。

## 并发控制是异步化的一部分

RabbitMQ 只负责缓冲，不代表消费者可以无限增加。我把并发控制拆成三层：

| 控制层 | 控制内容 | 目的 |
| --- | --- | --- |
| 消费者层 | 固定并发范围和合理 prefetch | 避免单实例一次拉取过多未完成任务 |
| 业务层 | 用户、业务类型和上游账号维度的限流 | 避免某个用户或账号占满资源 |
| 依赖层 | HTTP 超时、连接池和上游并发上限 | 防止慢请求拖垮线程和连接 |

如果队列积压，优先观察消费速率、上游响应时间和数据库连接使用率，再决定是否扩容消费者。不能只看到队列变长就盲目增加并发，因为上游限流或数据库瓶颈可能会让积压更严重。

## 这项工作的价值

- 提交接口不再同步等待几十秒甚至几分钟的生成结果。
- 波峰请求先进入队列，由消费者按照可控速率处理。
- 上游任务有本地记录，回调、轮询、重试和用户查询可以围绕同一个任务 ID 协作。
- 任务失败时可以定位到投递、消费、上游受理、回调还是结果归档阶段，恢复动作也不会扩大原有副作用。
- 按简历口径，系统峰值处理能力达到 50+ QPS；这个数字应明确为消费侧或端到端的实际统计口径，不能把提交 QPS 和完成 QPS 混写。
