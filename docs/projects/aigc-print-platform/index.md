## 项目的定位与背景

这是公司面向 C 端用户建设、同时配套 B 端运营能力的 AIGC 应用平台。公司作为科技技术有限公司，负责把 Midjourney 代理和第三方 AIGC API 等外部能力产品化：C 端用户可以提交提示词或图片素材，发起 AI 生图、印花提取、场景合成、换装等任务，并在任务完成后查看和获取结果；B 端运营人员则负责批量提交、任务监控、异常处理和结果管理。

它的完整形态是：C 端负责承接用户创作需求，B 端负责运营和管理，后端平台负责把长耗时、强外部依赖的 AI 任务稳定地处理完并交付结果。真正需要解决的核心问题，不是模型本身如何生成内容，而是任务如何被可靠受理、排队、执行、重试、回调、归档和查询。


| 层次 | 项目定位                                                    | 关注的问题 |
| --- |-------------------------------------------------------------| --- |
| 产品层 | C 端内容创作入口 + B 端运营管理能力                         | 用户如何提交任务、查看进度并拿到结果，运营如何批量管理和处理异常 |
| 平台层 | 面向多类调用方的长耗时 AI 任务异步编排与可靠交付平台        | 如何削峰、限流、重试、回调、补偿和状态收敛 |
| 文件层 | 面向用户和运营结果的对象存储与安全访问链路                 | 如何直传、确认、授权访问和避免应用中转 |

从 C 端用户或 B 端运营人员点击提交到最终拿到结果，中间并不是一次 HTTP 请求，而是几段生命周期：请求进入、身份与参数校验、任务落库、消息投递、消费者执行、上游受理、回调或轮询、结果归档、文件访问。任何一段发生故障，前端或运营后台看到的都不能只是一个模糊的“系统异常”，后端必须知道任务停在哪一段、是否可以继续、是否已经产生外部副作用。

不把 RabbitMQ、状态机和 OSS 当成孤立技术点，而是沿着“用户或运营提交任务 → 平台异步处理 → 结果安全交付”的完整链路，说明每一步保存了什么事实、下一步由谁触发、失败时如何恢复，以及什么时候必须停止自动处理。这样既能解释 C 端用户体验，也能说明 B 端运营效率背后的后端工程机制。

## 三项工作与业务价值

| 我负责的方向 | 我解决的问题                                                        | 技术结果                                                                                 |
| --- |---------------------------------------------------------------------|------------------------------------------------------------------------------------------|
| AI 任务异步化 | C 端生图和 B 端批量任务都可能耗时较长，单纯同步请求会占用连接和线程 | RabbitMQ 任务队列 + 多消费者并发，峰值处理能力达到口径的 50+ QPS                         |
| 任务可靠性 | C 端不能因一次异常反复提交，B 端也需要知道批量任务停在哪里          | 任务状态机 + 有界重试 + 死信处置 + 幂等控制，最终成功率由约 75% 提升至 90% 以上          |
| OSS 直传 | C 端素材和结果文件较大，B 端批处理也会放大文件流量压力              | 临时上传凭证 + OSS 直传 + 预签名访问，图片耗时约 300ms 降至 120ms，带宽占用降至 20% 以下 |
