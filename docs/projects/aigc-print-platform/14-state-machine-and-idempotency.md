## 状态机解决的是“现在到底是什么状态”

上游返回“已接受”不等于图片生成成功，本地任务至少要区分提交、处理中、成功、失败和重试中。主任务只负责汇总子任务，不能用主任务状态代替子任务的执行事实。

我把状态设计成“能指导下一步动作”的状态，而不是为了展示更多枚举：待处理表示可以进入业务队列，处理中表示外部任务已经受理或正在查询，重试中表示暂时不能执行但还没有结束，提交未知表示可能已经产生外部任务副作用，成功、失败和取消则是终态。状态名做了脱敏，实际字段和表结构不在文章中展开。

```text
待处理
  └─提交成功→ 已提交/处理中 ──生成成功→ 成功
                 │                  └─失败→ 失败
                 └─可恢复异常→ 重试中 ──重试耗尽→ 失败
```

批次主任务还有一层汇总状态。它不直接接收上游回调，而是根据子任务的终态计数计算进行中、部分成功、全部成功或全部失败。这样一个子任务的迟到回调不会把整个批次重新打开，也不会因为某个子任务失败就丢掉其他已经成功的结果。

## 我如何定义合法状态迁移

| 当前状态 | 触发事件 | 目标状态 | 允许的副作用 |
| --- | --- | --- | --- |
| 待处理 | 消费者开始处理 | 处理中 | 记录开始时间 |
| 待处理 | 参数或审核拒绝 | 失败 | 保存错误分类和原因 |
| 处理中 | 上游接受 | 处理中 | 保存外部任务 ID |
| 处理中 | 回调/轮询成功 | 成功 | 保存结果地址和完成时间 |
| 处理中 | 可恢复故障 | 重试中 | 增加重试次数 |
| 重试中 | 到达重试时间 | 处理中 | 重新尝试执行 |
| 处理中/重试中 | 超过最大时长 | 失败 | 记录超时原因并告警 |

状态更新不应该使用“收到事件就直接覆盖”的方式。回调可能重复，轮询可能晚于回调，旧事件也可能在新事件之后到达。更新时需要带上当前状态条件：只有仍处于允许的状态，事件才有资格推进任务。

示意语义如下：

```sql
UPDATE task_item
SET status = 'SUCCESS', result_url = :url, finished_at = :now
WHERE id = :id
  AND status IN ('SUBMITTED', 'PROCESSING');
```

影响行数为 0 时，不把它当作系统异常，而是先查询当前状态：如果已经成功，说明是重复事件；如果已经失败或取消，说明是迟到事件；只有状态不符合预期且无法解释时才需要告警。

状态条件更新解决的是“谁有资格推进状态”，但不负责所有业务副作用。比如更新成功后还要触发压缩或通知，不能把这些重操作放在数据库事务中等待。更稳妥的方式是先在状态事务中记录一个待处理事件，再由后续消费者执行一次性副作用；副作用自身也要使用业务键去重。

## 回调和轮询为什么要同时存在

回调延迟或丢失时，单靠回调无法保证任务结束；只靠轮询又会增加上游查询压力，并且无法及时处理部分完成事件。所以我把两者定位成同一状态机的两个事件来源：

- 回调负责更快地推进状态。
- 轮询负责补齐没有回调的任务。
- 两者都必须经过同一个状态迁移函数。
- 状态迁移成功后才更新主任务的成功、失败和完成计数。

轮询只扫描处于提交中或处理中的任务，并设置查询间隔、最大执行时间和单次扫描上限。已经进入成功、失败或取消的任务不再重复查询。

回调和轮询同时到达是常见竞态。例如轮询先查到处理中，回调随后报告成功；或者回调已经成功，轮询拿着旧结果晚到。两条路径都不应该各自实现一套更新逻辑，而是把事件转换成统一的状态迁移请求，带上事件时间、来源和版本。最终由状态条件决定哪一个事件生效，另一条只记录为重复或迟到事件。

## 我如何控制重复消费

幂等不是一张表或一个判断，而是三层防线：

1. **业务幂等键**：用本地子任务 ID 或客户端请求号标识“同一个业务动作”，避免用户重复提交产生两笔业务任务。
2. **消息幂等键**：每条消息带唯一消息 ID，消费记录用唯一约束防止同一消息重复执行。
3. **状态条件更新**：即使消息记录检查和业务执行发生竞态，最终状态更新仍然必须满足当前状态条件。

外部任务 ID 也要建立唯一约束或唯一查询语义。收到同一个外部任务回调两次时，第一次负责保存结果，第二次只读取已完成状态，不能重复扣费、重复发放结果或重复触发压缩。

## 四个容易出问题的并发场景

### 消息重复而状态还未更新

两个消费者可能几乎同时取到同一条消息。如果只做“先查后改”，两个消费者都可能看到待处理并同时调用上游。因此开始处理也需要条件更新或短时业务锁，只有抢到处理资格的消费者才能继续；没有抢到的消费者确认消息并记录跳过原因。

### 上游已受理但本地事务回滚

消费者拿到外部任务 ID 后写库失败，消息重新投递时本地仍可能显示待处理。此时先按请求幂等键或外部查询对账，确认已有任务后补写外部任务 ID；不能因为本地回滚就认定上游也回滚。

### 回调重复或乱序

相同外部任务 ID 的回调只能第一次推进状态，重复回调不重复保存结果。已经成功的任务收到处理中事件时，状态条件更新影响行数为 0，并记录迟到事件，不能覆盖成功事实。

### 批次汇总重复计数

子任务只有首次从非终态进入终态时才能增加主任务计数。重试消息、回调和轮询都可能触发同一个终态事件，因此计数变化必须和子任务状态变化放在同一事务中，不能由多个入口分别 `+1`。

## 计费和结果交付的边界

如果任务成功才计费，计费记录应与“首次成功状态迁移”绑定，并用业务键保证只记一次；如果提交上游就计费，则需要区分提交费用和最终结果费用。无论采用哪种规则，都不能把“重复回调”当成新的计费事件。

结果地址也属于任务状态的一部分。先保存对象元数据，再生成短时访问地址；不要把长期公开的第三方 URL 直接当作业务事实。

如果状态更新成功但通知、压缩或计费服务暂时不可用，我会保留成功事实，把后续动作变成可重试事件；如果后续动作失败，不能把已经成功的生成任务回滚成失败。生成状态和交付状态需要能够被分别查询，用户看到的是明确的“生成成功、文件处理中”或“文件已就绪”，而不是一个笼统的失败。

## 这项工作的价值

状态机让我能够解释每一次状态变化，幂等控制让我能够承受消息重复、回调重复和回调乱序。这里追求的是“至少一次事件 + 业务副作用有效一次”，而不是宣称消息系统能够提供绝对的 Exactly Once。

对开发排障来说，状态机还提供了一条固定路径：先看当前状态，再看最近一次合法迁移，最后看没有生效的迟到事件。这样可以把“任务卡住”拆成待投递、消费未成功、上游结果未知、回调缺失、结果归档失败等具体问题，分别安排补偿，而不是让用户反复点击提交。
