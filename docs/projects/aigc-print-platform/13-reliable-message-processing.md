## 我先回答一个问题：失败之后怎么办

AI 任务的失败不是一种情况。网络短暂抖动、上游 5xx、账号限流、参数错误和内容审核拒绝，恢复方式完全不同。如果所有异常都重试，会把不可恢复的错误重复提交；如果所有异常都直接失败，又会把短暂故障放大成业务失败。

因此我把失败处理拆成三步：**分类、有限重试、最终处置**。

我不会把“重试”理解成把消息重新放回原队列。真正需要处理的是：这次失败有没有产生外部副作用、多久后再试、最多再试几次、重试期间是否会挡住其他任务，以及最后谁来接手无法自动判断的任务。

## 一条消息的完整生命周期

### 0. 我先把消息路径分开

业务队列只承载第一次执行和重新执行的任务，延迟重试队列只负责等待，最终死信队列只负责收容和告警。不同重试轮次使用不同的延迟级别，例如短延迟、较长延迟和最终人工处理，避免一条长延迟消息挡住同一个队列里本来可以立即执行的消息。

每次投递都带上任务 ID、投递 ID、重试次数、首次创建时间、最近错误分类和追踪标识。重试不是创建一条新的业务任务，而是创建一次新的投递尝试；业务幂等键始终保持不变。

消息拓扑可以抽象为：

```text
业务交换机 → 主队列 → 消费者
                  ├─ 可恢复失败 → 重试交换机 → 延迟队列 → 主队列
                  └─ 超过上限   → 最终死信队列
```

延迟队列可以通过 TTL + 死信转发或延迟消息能力实现，重点不是具体插件，而是让等待发生在队列层，不占用消费者线程。不同延迟级别最好拆成不同队列，避免长延迟消息挡住短延迟消息。

### 1. 业务任务先有本地事实

生产者投递的不是“立即调用上游”的指令，而是一个带有任务 ID、子任务 ID、业务类型和幂等键的执行意图。消费者始终以数据库中的任务状态为准。

项目中的基础实现是创建任务后投递到业务队列；如果业务要求“任务记录和消息投递”严格一致，可以在同一个业务事务中写入本地消息记录，再由事务提交后的投递器发送，这属于生产化补充。

我在排查“任务创建成功但没有消费”的问题时，会先查本地任务状态和投递记录，再查 RabbitMQ 的发布确认与队列堆积，而不是直接让用户重新提交。补偿扫描只发送仍处于待投递状态的任务，并使用投递幂等键，避免补偿本身造成重复执行。

### 2. 消费成功后再确认消息

消费者取到消息后先做幂等检查，再执行上游调用。只有本地状态和必要的外部任务标识已经保存，才确认消息。

```text
读取消息
  ↓
幂等检查 + 状态检查
  ↓
调用上游
  ↓
保存外部任务 ID / 本地状态
  ↓
确认消息
```

如果消费者在确认前宕机，消息可以再次投递；因此“至少一次投递”必须和“重复消费无副作用”一起设计，单独依赖 ack 并不能解决重复问题。

消费者对异常的处理也不能只有一个 `requeue` 开关：

- 参数错误、无法反序列化和明确的业务拒绝，记录失败原因后拒绝重新入队，避免坏消息无限循环。
- 网络超时、上游 5xx 和明确的 429，写入重试信息后投递到延迟队列，原消息确认掉，避免主队列被同一条消息反复占住。
- 数据库暂时不可用时，不能在本地状态未保存的情况下确认消息；让消息重新投递，同时通过退避保护数据库。
- 上游已经受理但本地保存失败时，优先进入“提交结果未知”处理，而不是简单地再提交一次。

消费者的核心逻辑可以抽象成下面这样，具体类名和实现细节不在文章中展开：

```text
consume(message)
  ├─ 校验消息 + 查询任务
  ├─ 任务已是终态？        → 记录重复并 ack
  ├─ 抢占执行资格失败？    → 记录并 ack
  ├─ 调用上游
  │    ├─ 明确成功/已受理  → 保存外部任务 ID，ack
  │    ├─ 可恢复失败        → 写入重试信息，投递延迟队列，ack
  │    ├─ 不可恢复失败      → 写入失败状态，ack
  │    └─ 结果未知          → 进入对账状态，不直接重复提交
  └─ 本地保存失败           → 不 ack，让消息重新投递
```

这里的 `ack` 位置很关键：业务已经把失败归类并保存后，原消息才可以确认；如果只是因为异常被捕获就 ack，消息会消失；如果所有异常都 `requeue`，坏消息会在主队列里高速循环。

### 3. 只对可恢复异常重试

| 失败类型 | 例子 | 处理方式 |
| --- | --- | --- |
| 瞬时故障 | 网络抖动、连接超时、上游 5xx | 延迟后重试 |
| 上游限流 | 429、账号队列繁忙 | 延迟更长，并降低对应账号并发 |
| 参数问题 | 参数缺失、格式不合法、反序列化失败 | 直接失败，不重试 |
| 业务拒绝 | 审核拒绝、余额不足 | 直接失败，保留可读原因 |
| 明确不存在 | 上游返回任务不存在等确定性错误 | 直接失败或进入人工处理 |

失败分类应在消费者边界完成，而不是把所有异常都交给一个通用重试器。这样可以避免参数错误占满重试队列，也能让告警区分“上游故障”和“业务输入错误”。

我尤其关注“结果未知”这一类异常。比如 HTTP 读取超时发生在上游已经创建任务之后，本地没有拿到外部任务 ID。这时应先用请求幂等键、上游查询接口或请求指纹确认；只有确认上游没有受理，才允许重新提交。如果无法确认，就让任务进入人工或定时对账路径，宁可暂时等待，也不在不确定时制造第二个外部任务。

### 4. 延迟重试不能占住消费者线程

对于可以恢复的错误，消息进入独立的延迟重试队列，等待 30 秒或更长退避时间后再回到业务队列。等待期间不占用消费者线程，业务主队列也不会被失败消息卡住。

延迟时间不是固定 sleep，而是根据失败类型和重试次数计算。例如限流错误需要比普通网络抖动更长的退避，连续失败时还要叠加随机抖动，避免多个消费者在同一秒重新冲击上游。总重试时长也必须受任务最大执行时长约束，不能因为不断重试让任务永远处于处理中。

推荐的重试边界是：

- 第一次失败：短延迟重试，处理偶发网络抖动。
- 第二次失败：延长退避，给上游恢复时间。
- 超过最大轮次：进入最终死信，不再自动调用上游。

重试次数、重试间隔和总超时必须是配置项，并且要能在消息属性或本地任务记录中查询。不能依赖无限 `requeue=true`，否则一条坏消息可能持续占用队列。

每次重试前都会重新检查任务状态。如果用户已经取消、其他消费者已经成功，或者任务超过了最大执行时间，即使延迟消息再次到达，也只做状态记录和 ack，不再调用上游。

### 5. 死信是收容和人工入口

进入最终死信的消息只做四件事：记录失败原因、更新任务终态、触发告警、等待人工重放或忽略。死信消费者不应该再次无条件调用上游，否则失败消息会在死信和上游之间循环。

人工重放前需要确认：参数是否修复、上游是否恢复、是否允许重新扣费，以及原任务当前状态是否仍允许执行。重放要生成新的投递记录，但沿用原业务任务的幂等键。

死信处理还需要防止“人工重放变成第二个重试器”。我会要求重放带操作人、操作原因和新的投递 ID，并重新经过状态检查和限流；一次重放失败后不能自动绕过最大重试次数继续循环。对批量任务，人工重放优先选择单个失败子任务，而不是整批重新执行。

## 我如何定位一次失败

遇到任务失败时，我会按时间顺序串起四类记录：

1. 任务记录：当前状态、重试次数、外部任务 ID和最后一次错误分类。
2. 消息记录：发布是否确认、进入哪个队列、被消费几次、最后一次投递 ID。
3. 上游记录：请求开始和结束时间、HTTP 状态、超时阶段、是否拿到外部任务 ID。
4. 结果记录：回调是否到达、结果是否转存、文件是否可以访问。

如果只记录一条异常堆栈，很难判断应该重试提交、重试查询、重试下载还是直接人工处理；把失败阶段记录下来，恢复动作才不会误伤已经成功的部分。

## 这项工作的价值

我把“调用失败”变成了有规则的处理路径：短暂故障自动恢复，不可恢复故障快速失败，无法自动判断的故障进入可追踪的人工入口。按简历口径，任务最终成功率由约 75% 提升到 90% 以上；这里的“最终成功率”应定义为统计窗口内进入成功终态的任务数除以成功和失败终态任务数之和。

这个结果不是单纯增加重试次数得到的。无限重试只能延迟失败，还会放大上游压力；有效的提升来自三件事：把可以恢复的异常送到正确的延迟路径，把结果未知的调用和已明确失败的调用分开，把超过边界的消息送入死信后停止自动副作用。这样成功率提升的同时，失败任务也更容易解释和恢复。
