## 1. 从 0 到 1：链路从哪开始，了解背景业务

[40 · 数据库并发与 XLSX 字典交付](./40-field-dictionary-data-delivery) 的产物是一份字段字典：页面上的菜单、页签、表单、表格列，经过采集、清洗、审核，映射到数仓物理字段，再异步导出。

这份字典回答了一个问题：

> 业务术语 A，对应数仓里的哪个物理字段？

它没有回答下一个问题：

> 业务人员拿着这份字典，怎么直接查出结果？

所以从 0 到 1 不是「再做一次采集」，而是在字典下游补一层**可执行语义**：

| 环节 | 谁做 | 输入 | 输出 | 发生频率 |
| --- | --- | --- | --- | --- |
| A. 字段治理 | 采集、目录、导出（前面章节） | 业务页面 | 字段字典 | 页面变更时持续维护 |
| B. 语义建模 | 数据工程师按主题录入 | 字段字典 + 口径 + 关联 | 一份生效的语义模型 | 主题上线或口径变更时 |
| C. 日常问数 | 业务人员提问，系统调度 | 自然语言 | 表格 / 图表 | 每天反复发生 |

本篇把 **A → B** 讲透。B 之后如何编译见 [52](./52-metricsql-compile-engine)，如何调度见 [60](./60-text2sql-report-flow)。这里只标明接口。

三个环节都具有唯一的必要性：

- 没有 A，B 没有业务词来源，只能对着数仓盲建，口径会和页面各说各话；
- 没有 B，C 只能让人写 SQL，或让模型现场发明口径；
- 没有 C，B 只是另一份文档，业务人员仍然查不到数。

## 2. 业务现场：字典对上了，查询还是断的

电商服务场景里，数据环境天然碎：

- **多系统并行**：订单、仓储、物流、客服、财务，再加上多个电商平台的数据仓，不是一张宽表能讲完；
- **物理表极多**：中大型数仓可以到上千张表、数万字段，人没法靠记忆写 SQL；
- **多品牌多口径**：同一个「GMV」「订单数」，不同品牌的统计口径可以不同，必须分开维护；
- **查数需求爆炸**：运营、商品、财务、管理层每天都在要日报、周报、对比和归因，数据团队人手不够。

字段字典解决的是「页面上这个词，数仓哪一列」。它解决不了「这个词今天怎么算、跟哪张表连、状态值怎么翻译」。

我在实习里看到的断层很具体。运营会说「上周华东区的 GMV 按天看一下」——他知道要什么数字，不知道该写哪张表、用什么聚合、怎么把「已完成」翻成库里的枚举。数据同学能写对 SQL，但每天都在排队解释同一套口径。字典本身往往是对的，只是还停在「给人看」的形态。

![运营能说出 GMV，却没法对着字段表把查询跑起来](./assets/illustrations/semantic-query-gap.png)

### 2.1 业务人员知道什么，不知道什么

| 他们知道 | 他们不知道 |
| --- | --- |
| 「我想看上周华东区的 GMV」 | 哪个物理表存订单 |
| 「GMV 是多少」 | 支付金额列叫什么、要不要过滤成功单 |
| 「按天展示」 | 日期字段是下单时间还是支付时间，怎么分桶 |
| 「各渠道订单数对比」 | 表之间怎么关联，会不会把金额加重复 |
| 「最近 6 个月利润趋势」 | 数据库连接、权限、方言 |

由此可见的到，业务人员每日都需要和数据人员去进行具体交流才可以实现对应的数据，这样他们之间的沟通成本很高

诉求只有一句：**用业务语言提问，直接拿到结果。** 他们全程不该知道 SQL、表结构、物理列名和连接信息。

### 2.2 三种日常用法，字典都接不住

**场景 1：运营查上周 GMV**

- 输入：「上周华东区的 GMV 是多少？按天展示」
- 期望：表格（日期 | GMV）+ 折线图
- 字典只能告诉人：GMV 大概对应支付金额列。人还得自己写时间窗、区域过滤、按天分组。

**场景 2：产品做渠道对比**

- 输入：「各渠道的订单数和客单价对比」
- 期望：柱状图 + 表格（渠道 | 订单数 | 客单价）
- 字典里可能有订单号、支付金额、渠道，但「客单价 = 支付总额 / 订单数」通常写在口径文档里，不在 Excel 单元格里。

**场景 3：管理层看趋势**

- 输入：「最近 6 个月的 GMV 和利润趋势」
- 期望：双轴折线图 + 指标卡
- 「利润」如果是营收减退款，字典里是两列，不是一个可执行公式。

## 3. 三种旧做法为什么接不住

有了字段字典，传统上还是三条路。它们不是完全没用，而是**无法同时保证会用、用对、用得起**。

| 做法 | 实际过程 | 卡住的地方 |
| --- | --- | --- |
| 业务人员自己写 SQL | 把字典和表结构文档发给需求方 | 不会写；写错时间字段或 JOIN；口径漂移；还有误写风险 |
| 找数据团队写 SQL | 提需求 → 排期 → 对口径 → 出数 | 排队久；同一指标被解释很多遍；沟通成本高于计算本身 |
| BI 工具拖拽 | 预先配主题、拖字段出图 | 字段一多难维护；复杂口径拖不出来；学习成本高 |

三条路共同缺一块：

> 字典是静态知识，不是系统能执行的知识。

人看懂了「GMV 对应支付金额」，程序仍然不知道：

- 默认怎么聚合（求和、计数、去重计数）；
- 要不要 JOIN 用户维表；
- 「已完成」在库里到底是中文还是 `completed`；
- 「销售额」「成交额」「GMV」是不是同一个指标。

## 4. 核心转换：静态知识 → 可执行知识

### 4.1 静态知识（字段字典）

字段字典本质上是一份**给人看的映射表**：

- 记录「业务术语 A 对应数仓字段 B」；
- 存在 Excel / 文档 / 知识库里，程序不能直接当规则执行；
- 通常没有聚合方式、指标公式、JOIN 规则、枚举翻译；
- 业务人员拿到手，仍然要自己拼查询逻辑。

可以把它想成一张对照纸条：

```
"GMV"  →  订单事实表.支付金额
"大区"  →  用户维表.省份
```

纸条是对的，但还不是一台能运转的机器。

### 4.2 可执行知识（语义模型）

语义模型保留同一套映射，但改成**程序可读、可版本化、可执行**的结构：

- 同样记录「业务术语 A 对应数仓字段 B」，映射关系不变；
- 存进系统，查询时可以整份加载；
- 补上完整业务规则：默认聚合、指标公式、表关联、枚举翻译、同义词；
- 问数入口可以只选业务名，编译侧按既定口径生成 SQL。

对照变成对象：

| 字典纸条 | 语义模型里的对象 |
| --- | --- |
| 「大区」对应省份列 | 维度：名称是「大区」，表达式指向省份列，可用于分组和筛选 |
| 「GMV」对应支付金额求和 | 先有度量「支付金额」，再有指标「GMV / 营收」，公式在建模期写死 |

### 4.3 为什么必须做这一步，而不是继续维护 Excel

| 静态字典 | 语义模型 |
| --- | --- |
| 人可读，程序不可执行 | 人可读，程序可执行 |
| 只有映射关系 | 映射关系 + 聚合、公式、JOIN、枚举 |
| 业务人员拿到手仍不会查 | 系统可以按名称组装查询 |
| 无法保证口径一致 | 指标表达式一次性定义，运行时不变 |
| 无法自动翻译业务语言 | 「上周华东区 GMV」可以被翻译成结构化取数请求 |

一句话：

> 语义模型是把字段字典从「人看的文档」升级成「系统能执行的结构化元数据」。字典是素材，模型是可运行的口径。

## 5. 语义模型是什么，不是什么

### 5.1 一句话定义

**语义模型是一份预先定义、按业务主题存放的业务术语映射。** 数据工程师录入一次，查询时由系统读取。它不靠大模型现场发明口径。

它在整条问数链里只做一件事：**把业务词变成编译器认识的对象。** SQL 怎么生成、人话怎么分类，都不是它的职责。

### 5.2 它不是什么

| 容易混成的东西 | 实际边界 |
| --- | --- |
| 字段字典的替代品 | 字典仍是业务侧素材。模型是字典的可执行版本，不是把采集推倒重来 |
| SQL 生成器 | 模型只存规则。生成 SQL 是 [执行引擎](./52-metricsql-compile-engine) 的职责 |
| 模型自动学出来的指标 | 口径由人在建模期钉死。运行时只许按名称查找，不许改公式 |
| 数仓本身 | 数仓存事实数据。模型是数仓之上的业务语义层，不落明细、不改数 |
| 问数机器人 | 人话理解是问数调度那一章。模型不聊天，只提供对象 |


后面所有编译规则，都建立在这几条上：

- **建模侧录入的表达式视为可信。** 公式、JOIN、物理列由数据工程师确认。
- **用户输入只有名称和过滤值。** 业务人员说「GMV」「华东」，不提交 SQL 片段。
- **未登记的名称不能装成半截 SQL。** 覆盖失败要整段回退，细节在编译章展开

## 6. 字典表长什么样

实习里维护的字典，通常是一行一行的映射。如下表的例子：

| 页面显示 | 业务模块 | 数仓表（脱敏） | 数仓字段（脱敏） | 类型 | 说明 |
| --- | --- | --- | --- | --- | --- |
| GMV / 营收 | 订单报表 | 订单事实表 | 支付金额 | 度量 | 已支付金额 |
| 订单数 | 订单报表 | 订单事实表 | 订单主键 | 度量 | 订单笔数 |
| 退款额 | 订单报表 | 订单事实表 | 退款金额 | 度量 | 退款金额 |
| 大区 | 用户分析 | 用户维表 | 区域 / 省份 | 维度 | 用户所在区域 |
| 订单状态 | 订单报表 | 订单事实表 | 状态 | 维度 | 业务枚举 |
| 下单时间 | 订单报表 | 订单事实表 | 创建时间 | 维度 | 订单创建时间 |
| 渠道 | 订单报表 | 订单事实表 | 渠道 | 维度 | 下单渠道 |

这份表回答「词 → 列」。它通常**没有**下面这些格子，而这些格子恰恰是系统执行时必须有的：

| 字典经常没有 | 执行时为什么必须有 |
| --- | --- |
| 默认聚合 | 「支付金额」不写 SUM，系统不知道该加总还是取平均 |
| 指标公式 | 「客单价」「净营收」不是单列 |
| 同义词 | 「销售额」「成交额」「GMV」可能是同一个指标 |
| 枚举翻译 | 页面写「已完成」，库里可能是 `completed` |
| 表关联 | 「按城市看 GMV」需要订单连用户，乱连会把金额放大 |
| 数据源 | 同一套词可能对应不同品牌库，打错库就是错数 |

语义建模要做的，就是把这些缺格补成对象。

## 7. 六类对象总览：字典如何被「装下」

语义模型不另造一套业务语言，而是把每一行包装成不同类型的对象。

  title="一行字典如何拆成语义对象"

  poster="../../media/projects/baozun-lexicon/diagrams/dictionary-to-objects/index.html?embed=1"

| 字典里的一行 | 语义对象 | 补上的规则 |
| --- | --- | --- |
| 页面叫「订单」 | **逻辑表** | 业务表名 → 物理表，并绑定数据源 |
| GMV → 订单事实表.支付金额 | **度量** | 原子列 + 默认聚合 |
| 同一条再升一层 | **指标** | 业务口径，可引用度量或其他指标 |
| 大区 → 用户维表.省份 | **维度** | 用于分组和筛选 |
| 订单状态 → 状态列 | **维度 + 值映射** | 「已完成」翻成库里的物理值 |
| 订单.用户 = 用户.ID | **关系** | 只允许预先声明的关联 |

可以记成三组：

- **结构**：逻辑表、关系。找哪张表、表怎么连。
- **计算**：度量、指标。数字怎么来、口径叫什么。
- **筛选**：维度、值映射。按什么切开、标签对应哪个物理值。

下一篇会把每个对象的字段级语义和流转拆开。本篇先把「一行字典怎么变」走完。

## 8. 逐行映射：从 0 把 GMV 装进模型

### 8.1 先登记逻辑表

字典里出现「订单事实表」「用户维表」，在模型里先变成逻辑表：

| 业务名 | 物理表（脱敏） | 还要补什么 | 为什么 |
| --- | --- | --- | --- |
| 订单 | 订单事实表 | 数据源、主键 | 决定 SQL 打到哪个库；主键用于判断会不会一对多放大 |
| 用户 | 用户维表 | 数据源、主键 | 「按城市 / 大区」往往在维表上 |

没有逻辑表，后面的度量、维度无处归属。编译时也无法知道 FROM 从哪张表起。

### 8.2 再登记度量：支付金额

字典行：

```
页面显示：GMV
数仓表：订单事实表
数仓字段：支付金额
类型：度量
说明：已支付金额
```

这里其实混了两件事：页面上的业务指标名叫 GMV，物理上的原子列叫支付金额。语义模型把它们拆开：

**度量「支付金额」**

- 名称：支付金额（原子，给公式引用）
- 归属：订单这张逻辑表
- 表达式：指向支付金额列（完整保留字典里的数仓字段）
- 默认聚合：求和
- 说明：实付金额

业务人员以后很少直接说「支付金额」这个度量名，他们说的是指标。度量是原材料。

**特殊度量要单独登记，不能一律外套一层 SUM。** 例如「客户数」如果已经是「去重客户标识再计数」，默认聚合就应是「不再外套」，否则会被加成 `SUM(COUNT(DISTINCT ...))` 这种错口径。

### 8.3 再升一层指标：GMV / 营收

**指标「营收」**（对外同义词可以包含 GMV、销售额、成交额）

- 名称：营收
- 公式：对支付金额求和
- 口径说明（给人看的话）：已支付金额之和
- 展示格式：金额
- 同义词：GMV、销售额、成交额、revenue

关键点：

- 字典里的数仓字段被**完整保留**在度量表达式里；
- 业务人员永远只说「GMV / 营收」，看不到物理列；
- 同义词在建模期写死，查询时按名称命中，不靠模型自由发挥。

![字典卡片拆成逻辑表、度量和指标](./assets/illustrations/gmv-semantic-blocks.png)

### 8.4 派生指标：净营收、客单价、退款率

字典往往只有原子列。业务真正问的常常是公式。

| 指标 | 公式怎么钉 | 语义 |
| --- | --- | --- |
| 净营收 | `{营收} - {退款额}` | 引用已有指标 / 度量，运行时再展开 |
| 客单价 | 支付总额 / 订单数，分母为 0 时要能兜住 | 不能让问数时再发明除法 |
| 退款率 | 退款额 / 营收 | 展示为百分比 |

`{营收}` 这种引用表示：先找到名叫「营收」的对象，把它的表达式嵌进去。展开、环检测是编译章的算法；**本篇要记住的是：引用关系必须在模型里事先存在，不能查询时现场点名一张不存在的指标。**

### 8.5 维度：大区、下单日期

**维度「大区」**

- 名称：大区
- 归属：视建模而定，可能在订单上，也可能在用户维表上
- 表达式：区域 / 省份列
- 类型：文本
- 同义词：区域、地区
- 用途：GROUP BY 或 WHERE

**维度「下单日期」**

- 名称：下单日期
- 表达式：订单创建时间
- 类型：时间
- 同义词：日期、下单时间
- 用途：按天 / 按周 / 按月分桶时，编译章会认这是时间维

维度**不负责算**。把「大区」写进指标公式是建模错误。

### 8.6 值映射：订单状态、VIP 等级

**维度「订单状态」** 必须带值映射，否则页面语言和库内枚举对不上。

| 业务人员说 | 库里可能是 |
| --- | --- |
| 已完成 / 完成 | completed |
| 已取消 / 取消 | cancelled |
| 已支付 / 支付 | paid |

**没有值映射时会发生什么：** 业务人员说「已完成」，条件被原样写成「状态 = 已完成」，库里存的是 `completed`，结果是 **0 行**。这不是编译算错，是模型没把字典里的枚举翻译补上。

VIP 这类整数枚举也一样：「金卡」对应 `2`，不能把中文标签直接拿去和数字列比较。

值映射还有一条安全边界：给问数对话看的时候，只暴露业务标签（已完成、金卡），**不暴露物理值**（completed、2）。完整映射只给编译侧。

### 8.7 关系：订单到用户

「华东区的 GMV，按城市分组」往往跨表：金额在订单，城市在用户。

关系对象登记的是：

- 左表：订单（事实表）
- 右表：用户（维表）
- 连接类型：左连接
- 连接条件：订单.用户标识 = 用户.主键
- 语义约束：**to-one**。一个订单对应一个用户，聚合不会因为这条 JOIN 被放大

如果查询时临时把订单再连到一对多的明细上再对 GMV 求和，金额会被放大。所以关联必须预先声明，编译时只许走声明过的边。怎么选基表、怎么补桥接表，是编译章的 JOIN 规划；本篇只把「关系是模型的一部分」钉死。

## 9. 映射总表：字典维护的东西，模型里落到哪

| 你在字段治理里维护的内容 | 语义模型中的落点 | 核心作用 |
| --- | --- | --- |
| 页面模块 / 业务表名 → 数仓表 | 逻辑表的物理表名 | 业务表名映射到物理表 |
| 页面字段 → 数仓列（数字） | 度量的表达式 + 默认聚合 | 原子度量 |
| 页面字段 → 数仓列（分组 / 筛选） | 维度的表达式 | 分组和筛选 |
| 页面枚举 / 状态文案 | 维度的值映射 | 业务标签 → 物理枚举 |
| 表怎么连（字典里常缺失） | 关系的连接条件 | 合法 JOIN |
| 口径文档里的公式 | 指标的表达式 + 口径说明 | 业务指标 |
| 别名、英文名、口语 | 同义词 | 多名称指向同一对象 |
| 哪个品牌库 / 哪套数仓 | 逻辑表绑定的数据源 | 避免打错库 |

### 9.1 映射时不能省的四条

1. **物理字段要留下，但不能直接暴露给提问的人。** 支付金额仍然对应原来的数仓列，只是被指标名包住。
2. **聚合和公式必须在建模期写死。** GMV 用求和还是去重计数，不能留给每次提问去猜。
3. **同义词是字典质量的一部分。** 「销售额」「成交额」如果都指向营收，要在建模时登记。
4. **值映射和 JOIN 也是字典的延伸。** Excel 里往往没地方写，模型必须写。

### 9.2 字典质量决定后面能自动覆盖多少查询

名字对不上、口径没写全、关联缺失、枚举没翻译，编译侧就只能判定「未覆盖」。未覆盖不是偷偷用相近列凑一个 SQL，而是整段失败，再交给回退路径。回退细节在问数调度章；**根因在本篇：模型里没有对应对象。**

所以字段采集不是「给文档用的」，它直接决定问数能不能走治理主路径。
