## 我最初面对的不是一个技术问题

项目表面上是在做“HTTP 转 MCP”，但落地时至少同时面对六种不同的成功标准：

| 问题 | 表面要求 | 真正要回答的事情 |
| --- | --- | --- |
| 协议接入 | 把 HTTP 暴露为 MCP | 模型得到的参数契约是否稳定、可解释 |
| 数据源接入 | 让 AI 访问 MySQL/Redis | 哪些查询可以执行，哪些副作用必须阻断 |
| 能力管理 | 让管理员选择工具 | 草稿修改何时才影响客户端 |
| 认证隔离 | 增加 Token | Token 究竟授权网关、能力包还是单个工具 |
| 会话协议 | 支持 SSE/Streamable HTTP | 断线后哪些事件可以恢复，哪些状态必须丢失 |
| LLM 联调 | 让模型调用工具 | 如何区分模型选择失败、网关拒绝和下游失败 |

如果把这些问题都归为“转发”，系统虽然可以很快演示，但一旦进入企业环境，就会出现能力越权、旧配置泄露、数据库误写、缓存切换异常和无法解释的 LLM 失败。

## 困难一：原始 HTTP 文档不是模型契约

### 我遇到的具体问题

OpenAPI/Swagger 文档经常存在 operationId 缺失、路径写法不一致、参数分布在 path/query/header/cookie/body、响应结构不完整等情况。直接遍历文档生成工具会导致工具名不稳定、schema 层级混乱、管理者无法知道哪些 operation 被选中。

### 我的处理

我把流程拆为 parser port、统一文档模型、normalizer、候选查询、选择器和 preview builder。解析库只负责把不同规范翻译为统一对象；归一化负责 method/path 和 synthetic id；选择器负责表达管理员意图；预览负责生成真正要保存的 request/response mapping。

这样做的取舍是管理端多了一次预览和确认，但换来了三个确定性：

1. 文档解析和工具发布不再是同一个动作。
2. operation 变更可以通过 warning 暴露，而不是静默删除。
3. MCP schema 和 HTTP 请求组装使用同一棵 mapping tree，减少发现与执行不一致。

### 仍然留下的边界

文档能被解析不代表所有业务语义都能自动推导。输入范围、字段脱敏、是否允许写入和两个相邻工具的自然语言边界，仍然要由管理者通过语义卡补齐。模型契约不是解析库可以完全替代的。

## 困难二：MySQL/Redis 的“方便”与企业安全相冲突

![数据源安全责任链](./assets/datasource-safety.gif)

图要回答的问题：工具调用参数先经过来源和操作白名单、写权限与显式确认、结构化参数以及 SQL 专项规则，只有全部通过才进入 JDBC 或 Redisson。安全规则不是下游数据库的默认行为，也不能等执行失败后再补救。

### 为什么没有提供万能 SQL 和 Redis command

模型提交任意 SQL 时，网关无法从调用参数本身稳定判断数据范围、写入副作用和真实业务意图；模型提交 Redis 原生命令时，`KEYS`、脚本、扫描和管理命令都会进入能力范围。前端隐藏按钮也没有意义，因为攻击者或错误客户端可以直接构造 MCP JSON-RPC。

### 我把安全拆成两种操作模型

MySQL 允许表发现、表结构、参数化查询和受控写操作。SQL 进入执行端口前会检查：操作 token、单语句、注释/DDL/事务/文件关键字、INSERT 形式、UPDATE/DELETE 的有效 WHERE、明显恒真条件以及 placeholder 和 params 数量。运行端还限制 max rows 和 query timeout，写入影响行数超过上限会回滚。

Redis 不接收任意 command，而是按 String、Hash、List、Set、ZSet 形成固定操作；key、field、value、side、range、score 和 TTL 分别校验，控制字符、非法范围和超限参数在触达 Redisson 前拒绝。

### 取舍和后果

受控模型会牺牲一部分数据库工具的自由度，例如不能让模型临时写一个复杂 JOIN，也不能直接使用某个尚未建模的 Redis 命令；但它把风险变成了可审查、可测试、可限流的业务规则。如果企业确实要开放更复杂查询，我会新增经过审批的领域工具或只读报表接口，而不是放宽通用 SQL 入口。

## 困难三：保存、测试和发布之间存在时间差

### 最危险的错误是把保存当成上线

管理员修改 HTTP mapping、数据源状态或工具描述时，数据库保存成功并不意味着当前 MCP 客户端应该立刻看到新内容。如果保存动作直接改写运行时缓存，管理员在还没测试新参数前，线上模型就可能开始调用半成品。

### 我把三种事实分开

`contentVersion` 表示能力包内容发生了变化；`publishedVersion` 表示客户端使用的冻结版本；工具测试状态通过配置指纹绑定到某一次具体配置。只要工具协议、映射、语义或成员关系发生变化，旧测试不能继续证明新配置。

发布门禁按生命周期、成员、语义、测试和 Token 顺序执行。这个顺序的意义不是为了返回更多错误码，而是让管理员能知道当前能力停在哪里：没有包、包不能发布、工具没语义、工具没通过当前测试，和没有访问 Token 是不同的问题。

### 我如何处理并发编辑

管理更新使用顶层或成员 `version` 做乐观锁。请求版本过期返回 `2001`，前端刷新后让用户确认最新内容；不会用“最后一次写入覆盖”隐藏并发冲突。能力包成员变更和发布相关写入还通过包级行锁串行化，防止两个发布请求同时基于不同成员快照产生发布指纹。

## 困难四：缓存不是事实，缓存切换也不是删除一个 key

能力包运行时读取量高，如果每次 `tools/list` 都回 MySQL，数据库连接和序列化开销会变成运行瓶颈；但如果只把固定缓存 key 删除，删除失败、并发回填和旧值晚到都可能让实例继续使用旧授权。

我的选择是用网关版本键作为缓存代际，发布或配置变更通过 dirty marker 标记当前代际不可直接信任，回源时按包版本加载新的运行时投影，并用锁减少并发回源。正常投影有 TTL 和 jitter，空结果使用短负缓存，dirty TTL 必须大于最大缓存 TTL，避免脏状态过早消失。

这套设计解决的是“实例不要继续相信旧投影”，没有承诺 MySQL 和 Redis 的跨存储原子提交。若 MySQL 已提交而 Redis 版本切换失败，运行时宁可回源或失败，也不把旧投影当成最新授权；这需要监控和恢复动作配合。

## 困难五：Streamable HTTP 的连接资源不能完全放入 Redis

### 我需要同时处理三类状态

MCP 会话有授权 scope 和 idle timeout，SSE/Streamable GET 有正在工作的 Sink，事件恢复还有按 Last-Event-ID 查询 replay buffer。它们的生命周期不同：session 元数据可以序列化，Reactor Sink 和网络连接不能简单序列化，历史事件也不一定值得永久保存。

因此当前实现把 Redis Map 用于活跃 session 元数据，把 Redis Topic 用于实例间同步，把 Sink 和 replay 保留在本机。首次 GET 发送 priming event；有 Last-Event-ID 时先尝试回放，随后接实时流；心跳刷新租约，过期清理释放本地资源。

### 这个选择解决了什么，没解决什么

它让单实例 Streamable HTTP 语义清晰，也让多实例可以同步创建、删除和刷新元数据；但固定容量 200 的 replay buffer 仍然是 JVM 本地资源。跨实例切换时，session 可能存在而事件不存在，这是当前实现必须公开给部署方的边界。

生产有三种处理方向：负载均衡启用粘性会话，共享 replay 存储，或者把恢复协议收敛为客户端重新初始化。不能只把 session Map 搬到 Redis，就宣称流恢复已经分布式可靠。

## 困难六：新 Token 与旧 API Key 不能混成一条兼容逻辑

历史网关使用网关级 API Key，能力包主链路使用绑定 package 的 Bearer Token。两者都叫“认证”，但授权范围、存储形式、限流实现和旧客户端兼容规则不同。

我保留了旧 SSE 的兼容路径，但明确拒绝把 `mcp_` 包级 Token 当成旧 SSE 凭证；Streamable HTTP 才在 initialize 时建立 package scope。包级 Token 格式固定、secret 只返回一次、数据库只保存 HMAC；认证查询还要检查 Token 状态、过期、hash key version 和当前发布包。

旧 API Key 继续使用兼容的网关级限流，包级 Token 使用按 tokenId 的分布式限流。这个重复看起来不够“统一”，但强行统一会让旧客户端获得超出原有语义的权限，或者让新 Token 失去包级隔离。

## 困难七：LLM 的“没有调用工具”不是网关执行成功

Spring AI 的真实联调有几个容易被忽略的未知点：模型可能不选择工具，模型可能选择错误的工具，callback 可能没有触达下游，工具执行可能返回 MCP JSON-RPC error，或者下游调用成功但结果解包不符合模型预期。

我在 Domain 层把 LLM 命令、期望工具名和 MCP 配置独立建模；Infrastructure 通过 per-gateway slot 创建 ChatModel 和 MCP callback，并用调用锁保护 reload 与调用并发。`TrackingToolCallback` 记录成功、失败和 UNKNOWN 轨迹，LLM Service 再根据 expected tool names 判断是否满足本次验收。

这样模型选择问题和网关权限问题可以分开排查。代价是测试结果不能只返回最终文本，需要同时保存工具调用轨迹、失败状态和是否覆盖预期工具；这也是为什么真实 LLM 验收要放在确定性 MCP 调用之后。

## 我最终保留的技术取舍

| 取舍 | 保留的方案 | 放弃的直觉方案 | 原因 |
| --- | --- | --- | --- |
| 应用形态 | DDD 分层单体 | 早期拆成微服务 | 当前共享发布、会话和调用事实，拆分会先引入分布式一致性 |
| HTTP 接入 | 候选、预览、保存、执行分离 | 文档遍历后直接暴露 | 管理者需要明确选择和审阅契约 |
| 数据源 | 操作白名单与责任链 | SQL/Redis command 透传 | 模型不能拥有连接级权限和任意命令解释权 |
| 发布 | 能力包 + 指纹 + 运行时投影 | 保存即生效 | 防止半成品和旧测试结果进入线上 |
| 认证 | 包级 Token + 旧凭证兼容 | 一个 token 适配所有入口 | 保留历史客户端语义，收窄新运行范围 |
| 会话 | Redis 元数据 + JVM 流资源 | 所有连接对象放 Redis | 网络 Sink 和本地 replay 不能伪装成可序列化事实 |
| LLM | callback 轨迹 + expected tools | 只看模型最终文本 | 需要区分模型、网关、下游三类失败 |

## 当前实现最需要企业补齐的部分

这些不是当前代码已经完成的功能，我会在企业落地评审中明确列为后续工作，而不是在文章中假装已经解决：

- 管理端当前没有独立的 SSO、RBAC、操作审计和受限 CORS，必须由统一门户、反向代理或内网访问控制接管。
- 数据源权限目前以数据源、工具和操作规则为主，生产还需要租户、行列权限、敏感字段脱敏和完整审计。
- Streamable HTTP replay 当前受实例内存限制，集群需要粘性会话、共享回放或重新初始化策略。
- `application-dev.yml` 的固定地址和密码只适合本地样例，生产必须切换密钥管理、最小权限账号、TLS、备份和监控。
- Java 25 环境下部分 Mockito/Byte Buddy 测试代理不兼容，流水线要固定支持的 JDK 17 或升级测试依赖后重新回归。

## 本篇结论

这个项目真正难的地方不在于把 MCP JSON-RPC 接上，而在于把“谁可以看、谁可以叫、谁可以执行、执行到哪一版、失败是否可恢复”拆成彼此关联又不互相替代的事实。我的最终方案没有消除所有复杂性，而是把复杂性放到能力包、指纹、责任链、session scope、缓存代际和调用轨迹这些可以被测试、审计和排障的边界里。
