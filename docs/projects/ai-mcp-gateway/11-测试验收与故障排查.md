## 我为什么不只看服务是否启动

MCP 网关的“成功”至少有四种层次：服务可以启动，配置可以保存，工具可以被发现，工具可以在正确权限和安全条件下完成真实调用。只验证 HTTP 200 或 Spring Boot 启动，会漏掉最关键的越权、草稿泄露、SQL 风险、session scope 和缓存切换问题。

我把测试目标定义为：**证明每一条能力链在正常路径能闭环，在边界路径会停在正确的位置，并且故障不会被错误地转换成成功**。因此测试不是单一的全量命令，而是从纯 Domain 规则到 Docker 真实依赖，再到 MCP 客户端和 LLM 的分层证据。

## 测试分层

| 层次 | 关注点 | 典型测试 | 不能替代什么 |
| --- | --- | --- | --- |
| 领域单元 | 状态、规则、指纹、参数和错误码 | DataSourceSafety、CapabilityPackage、LLMService | 真实 JDBC/Redis/HTTP |
| 端口/适配 | Repository、HTTP、Redis、MCP client 适配 | SessionPort、Mapper、Cipher、Cache Repository | 业务全链路 |
| 集成 | 多组件和真实协议互操作 | H2、Redis、本地 HTTP、上游 MCP | 生产流量容量 |
| Docker E2E | MySQL、Redis 和数据源真实读写 | DataSourceDockerEndToEndTest | 企业生产权限和网络拓扑 |
| MVP 验收 | 发布、MCP、真实下游和 LLM 联调 | `docs/MVP端到端验收报告.md` | 长期稳定性和安全审计 |

我会先用领域测试锁定业务规则，再用适配测试确认端口实现，最后用 E2E 验证多个边界协同。这样某个真实环境测试失败时，可以判断是规则回归、连接问题、外部协议问题还是测试工具链问题。

## 按功能建立测试矩阵

### 网关、协议和 HTTP

| 目标 | 要验证的事实 | 代表证据 |
| --- | --- | --- |
| OpenAPI 解析 | OpenAPI3/Swagger2 能进入统一文档模型 | Protocol analysis tests、真实导入验收 |
| 归一化 | method/path 稳定，缺 operationId 有 warning | `ProtocolDocumentNormalizer` 相关测试 |
| operation 选择 | 只保存被选择的 operation，未命中有 warning | `UpstreamMcpImportServiceTest`、管理接口测试 |
| 请求组装 | path/query/header/cookie/body 位置正确 | `SessionPortHttpExecutionTest`、协议执行测试 |
| 响应解包 | object/array/scalar/text/header-only 分支不误判 | Protocol execute tests、工作台测试 |
| 兼容兜底 | 无 mapping 的旧 HTTP 工具仍能按历史方式执行 | ToolInvocationService/HTTP tests |

必须特别验证一条负向用例：响应映射期待 JSON 结构，但下游返回纯文本或标量时，结果应保留真实原文，不能构造一个空对象让调用看起来成功。

### MySQL、Redis 和数据源安全

`DataSourceInvocationSafetyChainTest` 是这条链的第一组单元证据，至少要覆盖：

- 正常参数化 SELECT 能通过，并保留规范化后的单条 SQL。
- 未开启写权限的 insert/update/delete 被拒绝。
- 开启写权限但没有 `confirmWrite=true` 被拒绝。
- 通过后 confirmWrite 从执行参数中移除。
- 多语句、注释、DDL/事务/文件关键字、operation 类型不匹配被拒绝。
- update/delete 缺少有效 WHERE 或包含明显恒真条件被拒绝。
- SQL 占位符数量与 params 数量不一致被拒绝。
- Redis `command`、非法 side、控制字符、超范围 TTL 和非数字范围被拒绝。

`DataSourceServiceTest` 验证数据源默认只读、超时和最大返回量边界；`AesGcmDataSourceCredentialCipherTest` 验证密文、IV、key version 和错误密钥；`DataSourceDockerEndToEndTest` 再验证真实 MySQL 与五类 Redis 结构的读写和限制。

### 能力包和发布

能力包测试不能只验证“publish 方法返回成功”，需要验证整个门禁：

| 场景 | 期望结果 |
| --- | --- |
| 包不存在、跨网关、package code 重复 | 管理操作被拒绝 |
| 没有启用成员 | 不能发布 |
| 成员数量超过配置上限 | 不能发布 |
| 语义卡不是 READY | 不能发布 |
| 工具没有当前指纹成功测试 | 不能发布 |
| 没有有效 ACTIVE token | 不能发布 |
| 任意成员/协议/语义变化 | 旧测试或旧发布指纹失效 |
| 停用或归档包 | 运行时不可见，归档不能恢复发布 |
| 管理 version 过期 | 乐观锁冲突，不能覆盖新修改 |

`CapabilityPackageServicePublishingTest`、`CapabilityPackageServiceLifecycleTest`、`CapabilityPackageFingerprintServiceTest` 和 `ToolConfigurationFingerprintServiceTest` 分别覆盖这些规则。`CapabilityPackageQueryIntegrationTest` 验证详情查询能补齐成员、语义和测试状态，而不是只返回成员表的原始行。

### MCP 会话、scope 和恢复

测试需要把 transport 和 session 生命周期拆开：

- initialize 没有 sessionId 时能够认证并创建 Streamable session。
- 后续请求缺少 sessionId、session 不存在或 gateway 不匹配时不执行工具。
- session transport 不匹配时不能跨 SSE/Streamable HTTP 复用。
- 包级 session 的 `tools/list` 只返回发布投影工具。
- 包级 session 的 `tools/call` 直接构造未授权工具名也会被拒绝。
- 首次 GET 会生成 priming event，并将它写进 replay buffer。
- Last-Event-ID 命中且有后续事件时先 replay，再接实时流。
- Last-Event-ID 命中但无积压时直接 resume，不生成新的 priming event。
- replay 未命中时遵循当前回退策略，并记录 warning。
- 心跳刷新租约，旧 SSE 取消回收 session，Streamable GET 取消保留 session。
- 过期会话被清理，本地 Sink 和 Redis 元数据最终都被释放。

代表测试是 `SessionManagementServiceTest`、`StreamableSessionServiceTest`、`SessionDistributedServiceTest`、`SessionMessageServicePackageScopeTest`、`ToolsListHandlerPackageScopeTest` 和 `McpStreamableHttpAuthenticationTest`。

### 认证、令牌和限流

`PackageAccessTokenServiceTest` 要证明 token secret 只返回一次、数据库只保存 HMAC hash、tokenId 和 secret 格式严格校验，错误 secret、过期、撤销和未发布包都不能授权。`PackageAccessTokenMapperTest` 验证 token 绑定的 package 属于指定网关，不能因 packageId 相同跨网关复用。

`McpGatewayControllerBearerTest` 验证 Authorization Bearer 被正确透传为命令，旧 SSE 拒绝包级 token；`AuthLicenseServiceTest` 验证未开启强认证的旧网关兼容分支和错误 token 不回退；`AuthRepositoryPackageTokenCacheTest` 验证缓存不会扩展 token 有效期或作用域。

限流测试要区分两条实现：包级 token 使用分布式端口按 tokenId 和窗口限制；旧 API Key 使用实例内 RateLimiter 兼容旧行为。两者的故障放行/拒绝策略不同，不能用一个“限流成功”断言覆盖所有场景。

### LLM 工具调用

`LLMServiceTest` 验证 Domain 层在以下情况下返回可区分的错误：需要工具但模型没有调用、调用全部失败、没有覆盖预期工具、命令参数或 MCP timeout 不合法。`TrackingToolCallbackTest` 验证成功、明确 MCP JSON-RPC 拒绝和无法判断是否触达下游的 UNKNOWN 轨迹。

真实 LLM 联调的验收口径不是“模型返回了一段文字”，而是：模型收到已发布工具定义、实际产生 tool call、工具回到本地 MCP Gateway、下游结果返回模型、轨迹记录成功，最终回答引用了工具结果。若要求某个工具必须被调用，还要检查 expected tool names。

## MVP 真实验收证据

现有 `docs/MVP端到端验收报告.md` 记录了一个真实闭环：

| 项目 | 结果 |
| --- | --- |
| MySQL | 已导入网关、两个协议和两个工具配置 |
| Redis | 存在 Streamable HTTP/SSE 会话元数据和网关运行时版本 |
| OpenAPI | 成功解析企业详情 GET 和员工搜索 POST 两个 operation |
| HTTP 下游 | 两个工具返回 HTTP 200，POST 返回两名员工 |
| MCP | initialize、tools/list、tools/call 均成功，`isError=false` |
| LLM | 模型真实调用 `search_company_employees` 一次并返回员工结果 |
| 构建 | Maven 跳过测试打包通过 |

这份记录证明核心功能可以在真实依赖上闭环，但不能推导出所有场景都已完成：数据源安全边界、多实例 replay、企业 RBAC、长期性能和故障注入仍需要单独验收。

## 建议的验证顺序

### 第一阶段：快速检查

先确认依赖、配置和代码构建：

- 检查 Java 版本、MySQL/Redis 地址、AES/HMAC 环境变量和 LLM 地址是否符合当前 profile。
- 执行 Maven 编译/打包，确认模块依赖和资源文件没有问题。
- 使用领域单元测试验证发布、数据源、token、session 和 LLM 规则。

### 第二阶段：真实下游

数据源集成测试可以启动独立 Docker 栈：

```bash
docker compose -p mcp-gateway-datasource-test \
  -f docs/dev-ops/docker-compose-datasource-test.yml up -d --wait

export MCP_DATASOURCE_AES_KEY="$(openssl rand -base64 32)"
MCP_DATASOURCE_IT=true ./mvnw -B \
  -pl ai-mcp-gateway-app -am \
  -Dtest=DataSourceDockerEndToEndTest \
  -Dsurefire.failIfNoSpecifiedTests=false test
```

测试完成后关闭测试依赖栈，避免残留端口和测试数据影响下一次运行。测试用数据库和 Redis 密码只用于这个栈，不能复制到生产。

### 第三阶段：MCP 和 LLM

按实际运行地址完成一次 initialize，记录 `Mcp-Session-Id`，执行 tools/list 确认工具范围，再执行 tools/call 确认下游结果。随后通过工作台或测试接口发起 LLM 调用，确认 callback 轨迹和 expected tool names。

验收记录应该保留 gatewayId、packageId、发布版本、工具名、测试指纹版本、session transport、下游状态码、调用耗时和失败分类，但不能保存 token secret、数据源密码或完整敏感结果。

## 已知测试工具链边界

当前开发环境为 Java 25，完整单元测试中记录到 20 个 Mockito/Byte Buddy 兼容性错误，原因是现有 Byte Buddy 正式支持范围未覆盖 Java 25。这类错误发生在测试代理初始化或 mock 创建阶段，不能直接解释为业务规则失败；真实 MySQL/Redis/HTTP/MCP/LLM 验收链路已经有独立通过记录。

企业流水线应固定项目支持的 JDK 版本，或者升级 Mockito/Byte Buddy 后重新跑完整回归。汇报测试结果时必须分开写：构建结果、业务测试结果、环境兼容错误，不能用“测试通过”或“测试失败”一个词覆盖三种事实。

## 故障排查：先定位能力停在哪一层

### 工具完全没有出现在 tools/list

按这个顺序检查：

1. gatewayId 是否正确，网关和工具是否存在。
2. session 是否是 Streamable HTTP，packageId/tokenId 是否在服务端 session 中。
3. token 是否 ACTIVE、未过期，绑定包是否当前发布。
4. 能力包是否至少有启用成员，publishedVersion 和 contentVersion 是否一致。
5. Redis 是否处于 dirty，version 是否能读取，投影是否可回源 MySQL。
6. 发布投影中的 toolId 是否能按当前 gateway 查询到完整工具配置。
7. 工具是否因语义、测试指纹或数据源状态被管理面标为不可发布。

不要直接查询网关工具表就下结论；包级 session 的工具列表必须以发布投影为准。

### tools/list 有工具，但 tools/call 被拒绝

重点查看 toolName 是否与发布投影匹配、调用是否复用了已过期 session、工具协议配置是否存在、arguments 是否为正确 JSON object。若是数据源工具，再查 operation 白名单、confirmWrite、SQL/Redis 参数规则。这个现象通常说明发现和执行的边界正在发挥作用，不应先关闭 `requirePublishedTool` 或安全责任链。

### HTTP 工具返回错误

先看工作台保存的 request mapping 和工具配置指纹，再看实际 HTTP method、URL、query、header key 和 body shape。下游 4xx/5xx 说明请求已经触达外部服务，应区分参数错误、鉴权错误和服务端错误；响应解包失败不应触发重复 HTTP 调用，先查看 raw body、content type 和 response mapping。

### MySQL/Redis 工具失败

先确认数据源状态为 ENABLED、secret 存在且 key version 与当前环境一致；再确认连接地址、端口和超时。若请求在安全链失败，检查 operation、参数白名单、写开关、confirmWrite、SQL 首 token、WHERE 和 placeholder。若已经进入运行端口，再看数据库/Redis 服务状态、账号权限、maxRows、query timeout 和连接释放。

### 断线后无法恢复

确认客户端保留了 `Mcp-Session-Id` 和上一次有效的 `Last-Event-ID`；检查 session 是否超过 idle timeout、Redis 元数据是否存在、请求是否落到正确 gateway。若跨实例，检查负载是否切到了没有 replay buffer 的实例；当前实现下这会导致 Last-Event-ID 未命中，生产需要粘性或共享 replay。

### LLM 没有调用工具或调用错工具

先确认 MCP client initialize 和 tools/list 成功，再检查工具描述、input schema、Prompt 和模型配置。若测试命令要求 tool call，查看 `LLMToolCallGatewayTrace` 是没有轨迹、FAILED、UNKNOWN 还是调用名称不匹配。不要把模型没有选择工具的问题直接归因于网关执行失败，也不要为了让测试通过而删除 expected tool names 检查。

## 最终验收口径

我会用下面六个问题作为发布前的最后检查：

1. 客户端看到的工具是否严格等于当前能力包的启用发布成员？
2. 客户端直接构造未授权 tool name 时是否在下游之前被拒绝？
3. SQL、Redis 写操作和超量返回是否都在正确边界被阻断？
4. HTTP、MySQL、Redis、上游 MCP 和 LLM 的真实结果是否能回到 MCP，并区分错误类型？
5. 配置变更、token 撤销、包停用、缓存异常和 session 断线是否不会泄露旧能力？
6. 多实例和重启时，哪些状态可以恢复、哪些状态会丢失，验收记录是否明确写出？

如果这些问题都能用测试或验收记录回答，项目才算完成了从“能调用”到“可治理”的闭环。

## 本篇结论

测试的价值不是堆积通过数量，而是把每个边界变成证据：Domain 测试证明规则，适配测试证明端口，Docker E2E 证明真实数据源，MCP/LLM 验收证明外部调用闭环，故障排查表证明失败仍然可解释。到这里，整套知识库已经从项目定位、架构、领域模型、接入、执行、发布、隔离、一致性走到验证终点。
