# 测试、验收与故障排查：用真实调用证明能力边界

## 我如何组织验证

我把验证拆成规则、适配和链路三层：领域服务测试验证状态与安全规则，Repository/Port 测试验证 MySQL、Redis、HTTP 和上游 MCP 边界，端到端验收验证 MCP 客户端是否真的可以完成发现和调用。

## 已覆盖的测试方向

| 方向 | 代表性验证 |
| --- | --- |
| 会话 | 生命周期、消息处理、会话作用域、Redis 恢复、本地端口 |
| MCP | Streamable HTTP、SSE、initialize、tools/list、tools/call |
| HTTP | 请求映射、响应解包、协议导入、HTTP 下游执行 |
| 数据源 | MySQL/Redis 安全链、数据源状态、Docker 下游调用 |
| 发布 | 能力包指纹、成员生命周期、发布、缓存投影 |
| 安全 | Bearer、包令牌、HMAC、AES-GCM、限流 |
| AI | LLM 调用、工具选择、工具调用轨迹 |

## 真实端到端证据

MVP 验收资料记录了 MySQL、Redis、OpenAPI 导入、本地 HTTP 下游、MCP Streamable HTTP 和真实 LLM 联调均通过。示例网关发布了企业详情 GET 和员工搜索 POST 两个工具，MCP `initialize`、`tools/list`、`tools/call` 均获得成功结果。

## 已知工具链问题

打包验证通过。当前 Java 25 环境中有 20 个 Mockito/Byte Buddy 兼容性错误，原因是现有 Byte Buddy 正式支持范围未覆盖 Java 25；这属于测试运行时兼容问题，不能被解释为业务链路失败。企业流水线应固定受支持 JDK，或升级 Mockito/Byte Buddy 后重新执行全量测试。

## 故障排查顺序

### MCP 没有工具

先检查网关是否存在，再检查能力包是否已发布和启用，随后检查 Redis 运行时版本、脏标记和会话授权作用域。不要直接从数据库工具配置表推断客户端一定可见。

### 工具调用被拒绝

按授权、限流、会话 scope、工具协议、数据源状态和安全责任链依次定位。若是写操作，确认数据源写开关与二次确认字段同时满足。

### HTTP 工具结果异常

检查 operation 选择、request mapping、HTTP 方法和 URL，再检查响应类型是否与 response mapping 匹配；无映射或无命中时应确认系统是否按预期返回了原始响应。

### 断线无法恢复

检查 `Mcp-Session-Id`、`Last-Event-ID`、租约是否过期以及 replay 是否仍在当前实例。多实例环境还要确认负载均衡策略和共享回放能力。

## 最终验收口径

验收不是只看 HTTP 200，而是要证明：工具列表范围正确、未授权工具不可调用、危险数据操作被拒绝、下游结果能回到 MCP、断线语义符合预期、缓存异常不会把已发布能力误判为空。
