# 项目背景与定位：AI 需要的不是更多接口，而是可治理的能力

## 我为什么开始做这个网关

企业系统已经有 API，但 API 的存在不等于 AI 可以安全使用。一个 OpenAPI operation 可能要求复杂的嵌套参数，一个 SQL 接口可能包含超过业务需要的数据范围，一个 Redis 客户端可能拥有删除或修改全部 key 的权限，一个上游 MCP 服务也可能暴露了不应进入当前业务场景的工具。

如果把这些能力直接拼进 Prompt，模型得到的是不可验证的文本；如果把数据库连接或 HTTP 客户端交给模型，系统就失去了最重要的边界。

所以我把问题定义为：如何把企业已有能力重新建模成 MCP 工具，并让“可见什么、能调什么、调到哪里”都成为服务端可验证的事实。

## 项目定位

AI MCP Gateway 位于 AI 客户端与企业内部能力之间，包含两个面：

- 管理面负责配置、测试、能力包组织和发布。
- 运行面负责认证、会话、工具发现、工具调用和结果返回。

它不是数据库代理，不是通用 HTTP 代理，也不是只做协议转发的 MCP 适配器。它把协议适配、能力治理和运行时会话放在同一个可验证的边界内。

## 我保留的三个核心事实

第一，配置事实保存在 MySQL；第二，运行时能力是发布后的投影；第三，会话是带租约的连接资源。把这三者混成一个对象，会导致草稿泄露、缓存误判或断线恢复失效。

## 企业边界如何落到项目中

企业处理这类系统时，通常需要把“数据访问”与“AI 推理”分离，把“管理权限”与“运行权限”分离，把“版本发布”与“实时调用”分离。当前项目通过能力包、包级令牌、会话绑定和数据源安全责任链实现了这几个边界。

后续文章分别解释这些边界如何在架构和代码中落地。
