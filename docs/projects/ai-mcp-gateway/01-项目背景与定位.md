## 我先回答一个容易被问错的问题

这个项目是不是一个 MCP 版的 API Gateway？如果只看对外接口，它确实接收 MCP JSON-RPC 消息，随后调用 HTTP、MySQL、Redis 或上游 MCP；但这只是最外层表现。真正决定项目价值的不是“能不能转发”，而是“什么能力可以被转发、谁可以看到、谁可以调用、调用产生什么副作用，以及配置变化何时进入线上”。

所以我没有把它定位成一个通用代理，而是把它定位为：**企业内部能力接入、治理、发布和运行的 AI 工具网关**。

这个定位会直接影响架构：协议适配必须与授权分开，配置态必须与运行态分开，LLM 必须与执行权限分开，数据源连接必须与模型参数分开。后面的文章都是从这几个判断继续展开的。

## 企业背景：原有能力已经存在，但它们并不适合直接交给 AI

### HTTP API 有接口，不一定有模型契约

企业 HTTP API 通常为前端、服务间调用或固定 SDK 设计。它可能使用复杂的嵌套请求体、多个位置的参数、内部字段名和不稳定的响应结构。模型如果只知道 URL 和方法，往往无法稳定地生成参数；如果把整份 OpenAPI 文档不加筛选地暴露，工具数量和描述长度又会让模型选择变差。

项目用 OpenAPI/Swagger 分析形成候选 operation，再由管理面选择和配置参数映射。这样“发现接口”与“决定上线什么能力”分开，模型最终拿到的是经过治理的 MCP `tools/list` 契约，而不是原始文档的全部内容。

### 数据库能查数据，不代表模型应该拥有数据库权限

把 MySQL 账号交给 AI，实际上把表、字段、条件、写操作和连接级权限的判断交给了一个概率模型；这种授权粒度太粗，审计也很难回答一次调用到底想做什么。

项目把 MySQL 变成有限的工具操作，例如表发现、表结构描述和受控的 `select`、`insert`、`update`、`delete`，并在工具调用前校验操作白名单、SQL 首 token、禁止关键字、单语句、占位符数量和 `WHERE` 条件。数据库凭证仍由网关保存和使用，模型只提交结构化工具参数。

### Redis 方便，但任意命令是不可接受的边界

Redis 原生命令的能力面非常宽。允许模型提交 `command` 和参数数组，等价于允许它自己组合删除、扫描、脚本或管理命令。项目没有选择做一个“Redis 命令透传器”，而是把 String、Hash、List、Set、ZSet 的有限操作分别建模为工具，并限制 key、field、value、范围、score 和 TTL。

### 上游 MCP 已经有工具，也不代表本系统可以原样继承

上游 MCP 解决了协议互通，但没有替本系统完成租户、业务场景和发布范围治理。项目在导入上游 MCP 时先通过 `initialize` 和 `tools/list` 形成预览，管理员选择需要的工具，保存为本地协议配置，再由本地能力包发布。上游工具进入本系统以后，仍然要受本系统的 token、session、package 和下游连接策略约束。

## 我把系统职责拆成管理面和运行面

![AI MCP Gateway 运行时边界](./assets/architecture.gif)

图要回答的问题：管理者如何配置和发布能力，MCP 客户端如何获得稳定的运行能力，以及 MySQL、Redis、上游服务和 LLM 分别处于哪条边界。

### 管理面：把外部能力变成可发布资产

管理面由 `AdminController` 和 Case 层管理用例承载，实际覆盖以下对象：

| 管理对象 | 做什么 | 为什么不能直接进入运行面 |
| --- | --- | --- |
| Gateway | 形成一个独立对外入口和配置归属 | 一个入口可能包含多个场景，不能默认全部公开 |
| Tool | 定义 AI 看到的名称、描述和参数契约 | 保存工具只表示草稿存在 |
| Protocol | 保存 HTTP、MySQL、Redis 或上游 MCP 的执行事实 | 执行协议不等于客户端授权 |
| Data Source | 保存数据源类型、连接属性和加密凭证 | 数据源连接不能被模型直接持有 |
| Capability Package | 组织对外可见的工具集合 | 需要成员、语义、测试和发布门禁 |
| Semantic Card | 补足工具用途、输入约束和风险描述 | 描述不完整时模型容易误用 |
| Test State | 记录当前配置指纹下的测试结果 | 一次旧成功不能证明新配置安全 |
| Access Token | 绑定某个能力包的运行凭证 | 管理权限和运行权限不是一回事 |

管理面保存的是 MySQL 中的长期事实。管理员可以修改草稿、重新测试或停用发布；这些动作不会直接改写某个已经存在的 MCP 会话，也不会让运行时在没有发布的情况下读取编辑中的工具。

### 运行面：只消费已发布且已授权的能力

运行面由 `McpGatewayController` 接收旧 SSE 和 Streamable HTTP，Domain 会话服务负责 JSON-RPC 分派，工具处理器负责 `tools/list` 和 `tools/call`，最后由工具策略选择下游执行端口。

运行面只关心几类已经收敛的事实：

- 请求属于哪个 `gatewayId`。
- 凭证是否有效，是否绑定某个能力包。
- 当前 session 是否仍存活，是否属于这个网关和 transport。
- 能力包是否处于有效发布状态。
- 工具名称是否属于当前发布投影。
- 下游执行是否通过对应的协议或数据源安全门禁。

这让管理态和运行态之间形成了“发布”这个明确的闸门，而不是依赖前端约定“保存后应该很快生效”。

## 项目不负责什么

我认为把边界说清楚，比再列几个功能更重要。当前工程不应被理解为以下系统：

| 容易产生的误解 | 实际边界 |
| --- | --- |
| 通用反向代理 | 工具必须先注册、映射、测试并发布，HTTP 不是任意 URL 转发 |
| 数据库 IDE | SQL 仅通过已配置数据源工具和责任链执行，不提供任意账号和脚本环境 |
| LLM 自治执行器 | LLM 只产生工具选择和参数，授权、风险和范围由网关判断 |
| 完整 IAM/RBAC 平台 | 当前重点是运行 token、能力包 scope 和数据源门禁，管理身份要接企业体系 |
| 跨实例消息系统 | 运行时缓存有 Redis 协调，Streamable HTTP replay 当前仍依赖实例内存 |
| 已拆分微服务 | 项目是分层单体，模块化是为了边界和演进，不代表已完成服务拆分 |

这些限制不会削弱定位，反而决定了企业接入时要把哪些能力放在网关，哪些能力交给已有平台。

## 我最终保留的四个核心事实

### 工具契约事实

客户端看到的工具名称、描述和 JSON Schema 必须能反映真实调用参数。HTTP 映射工具由协议映射生成 schema，数据源工具使用操作专属 schema，上游 MCP 工具保留上游 input schema。契约不完整时，问题应在管理预览或发布阶段暴露，而不是等模型调用后才发现。

### 发布事实

工具属于某个能力包并不代表它已经可以被客户端使用。能力包发布会记录内容版本、发布版本、发布指纹和发布时间；发布前还要通过生命周期、成员数量、语义卡片、当前测试指纹和有效 token 门禁。

### 执行事实

一次 `tools/call` 最终必须形成可解释的统一结果：成功时有下游响应和解包文本，失败时能区分参数、权限、协议、数据源安全、网络或下游业务错误。执行结果不能只返回一个“调用失败”字符串，否则工作台和故障排查无法定位边界。

### 连接事实

Streamable HTTP 会话同时包含网关归属、transport、授权 scope、活跃时间、事件序列和本地事件流。它是运行资源，有过期、心跳、删除和恢复；不能把它当成能力包配置的一部分，也不能只凭一个 session id 就允许跨网关使用。

## 我用什么方式判断项目是否真的完成

我不会把“服务启动”和“接口返回 200”当作完成标准，而是看一条能力是否形成闭环：

1. 管理面能从真实来源发现能力，并生成可以审阅的参数契约。
2. 工具保存后能在工作台中准备测试参数，并记录当前配置指纹。
3. 能力包必须通过语义、测试、成员和 token 门禁才能发布。
4. 包级客户端建立 MCP 会话后，只能发现当前发布投影中的工具。
5. 客户端即使绕过 `tools/list` 直接构造工具名，也不能越过 `tools/call` 范围校验。
6. 工具进入 HTTP、MySQL、Redis 或上游 MCP 前，能执行对应的参数和安全检查。
7. Redis 缓存异常、配置切换、会话断开和下游超时都有可解释的结果。

MVP 验收资料已经记录 MySQL、Redis、OpenAPI 导入、本地 HTTP 下游、MCP Streamable HTTP 和真实 LLM 联调均通过；测试和故障边界在文章 11 中展开。
