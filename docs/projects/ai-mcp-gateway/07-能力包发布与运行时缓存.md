## 我为什么必须引入能力包

如果运行时工具列表直接来自网关的全部工具，那么管理台保存一个新工具或修改一个 HTTP mapping，就可能立刻改变线上客户端看到的能力；如果只在前端过滤工具，客户端仍可以直接构造 `tools/call`。企业需要的是一个明确的发布单元，能把“正在编辑的配置”和“客户端当前使用的能力”分开。

我把这个发布单元定义为 Capability Package。它包含有序成员、语义卡片状态、当前配置测试状态、发布版本、发布指纹和访问 token 事实。只有能力包通过发布门禁后，运行面才建立对应的 Redis 投影；只有 session 绑定到这个能力包，`tools/list` 和 `tools/call` 才能使用这个范围。

![能力包生命周期](./assets/capability-lifecycle.gif)

图要回答的问题：能力包如何从可编辑草稿进入测试和发布，为什么禁用、重新启用和归档不是同一种动作，以及运行时投影何时失效。

## 管理态、测试态、发布态和运行态

我把几个容易混淆的状态拆成四组：

| 状态组 | 代表字段/枚举 | 由谁修改 | 用来回答什么 |
| --- | --- | --- | --- |
| 管理生命周期 | `DRAFT`、`PUBLISHED`、`DISABLED`、`ARCHIVED` | CapabilityPackageService | 这个能力包还能否编辑、发布或归档 |
| 工作台状态 | `DRAFT`、`DISABLED`、`NEEDS_TEST`、`READY_TO_PUBLISH`、`PUBLISHED` | WorkbenchService | 当前网关配置下一步该测试还是发布 |
| 语义卡片 | `DRAFT`、`READY`、`DISABLED` | ToolSemanticCardService | 工具说明是否达到发布门槛 |
| 工具测试 | SUCCESS/FAILED + configFingerprint | WorkbenchService | 某次成功是否仍对应当前配置 |
| 运行时投影 | `PublishedCapabilityPackageVO` | RuntimeCacheRepository | 本次 MCP 请求可以看到哪些已发布工具 |

这些状态不能互相推导替代。例如工作台 `READY_TO_PUBLISH` 只说明当前配置已经通过工具测试，不说明某个具体能力包已经发布；能力包 `PUBLISHED` 也不代表 token 仍未过期，包级认证还要复核有效 token。

## 能力包写入和并发控制

`CapabilityPackageService` 在创建、更新、成员变更、发布、启用、停用和归档时都以能力包为聚合边界。

### 创建和元数据更新

创建时校验网关存在、package code 在同一网关内唯一，初始化 contentVersion 为 1、状态为 DRAFT、管理 version 为 0。更新元数据时先锁住能力包行，再用 command 中的 version 做乐观锁检查；版本不匹配时拒绝，避免管理台过期页面覆盖另一个管理员的修改。

### 成员增加、更新和移除

新增成员先锁包，再确认 toolId 属于当前 gateway，检查成员数量上限，保存 includeReason、memberStatus、sortOrder 和成员 version。更新或移除使用成员 version 做并发保护。

成员变化会同时做两件事：让当前网关的运行时缓存失效，并使已发布内容失效。这样即使能力包表仍然保持 `PUBLISHED`，只要成员或工具配置已经变化，当前发布快照也不会继续被错误当作有效版本；管理员需要重新测试并发布。

### 为什么要以包行锁串行化

发布校验需要看到一组一致的成员、工具、语义和测试状态。如果两个管理员同时移除工具和发布，只靠前端 version 可能出现发布读取到半套变化的问题。包行锁把“读取当前包、补齐成员、执行门禁、写发布快照”放到同一事务内，保证一个发布判断对应一个稳定内容版本。

## 发布责任链：四道门禁按固定顺序执行

能力包发布由 `CapabilityPackageService.publish` 负责编排，在锁定的能力包上查询成员、补齐工具配置和测试状态，然后把 `CapabilityPackagePublishContext` 交给 Spring Order 排序的发布规则。

| 顺序 | 规则 | 门禁 |
| --- | --- | --- |
| 10 | Lifecycle | 停用或归档能力包不能发布 |
| 20 | Member | 至少一个启用成员，成员总数不超过 `mcp.capability-package.max-tools`，默认上限 20 |
| 30 | Tool Test | 每个启用工具的语义卡必须 READY，且当前配置指纹测试通过 |
| 40 | Access Token | 发布时至少存在一个未过期的 ACTIVE 访问 token |

责任链的价值是让每个规则只解释一种业务原因。新增审批规则、敏感工具规则或组织权限规则时，可以增加新的规则节点，而不把所有判断写进发布 Service 的长条件中。

发布通过后，服务把当前 contentVersion 写入 publishedVersion，基于当前启用成员生成发布 fingerprint 和 fingerprint version，写入 publishedAt 与 `PUBLISHED` 状态，再让运行时缓存失效。发布结果查询返回管理详情，但运行面会懒加载新的投影。

## 指纹如何防止旧测试被复用

### 工具配置指纹

`ToolConfigurationFingerprintService` 使用 SHA-256 和稳定序列记录 gatewayId、toolId、toolName、toolDescription、toolVersion、protocolId/type、语义版本、HTTP URL/method/headers/timeout、上游 MCP 连接与 input schema，再按 mapping type、sortOrder、MCP path、HTTP location/path 等字段稳定排序。JSON 对象键也会被规范化，避免数据库返回顺序或 JSON 键顺序造成无意义的指纹变化。

工具测试开始前保存 expectedFingerprint；调用完成后重新读取当前工具配置并再次计算。配置变化时，测试结果不能落库，返回“配置已变化，请重新测试”。这样一个较慢的测试不会把旧响应写到刚刚被修改的新配置上。

### 能力包发布指纹

`CapabilityPackageFingerprintService` 记录 fingerprint version、gatewayId、packageId、packageCode、contentVersion 和启用成员的 toolId、sortOrder、member version、当前工具指纹，并按稳定顺序生成 SHA-256。它不把禁用成员放进运行时发布快照，客户端看到的工具集合和指纹保持一致。

运行时回源时，会再次验证：

- 包状态仍是 PUBLISHED。
- contentVersion 等于 publishedVersion。
- 指纹算法版本一致。
- 至少存在一个启用成员。
- 每个启用成员当前测试仍通过。
- 当前重新计算的 package fingerprint 等于数据库保存的 publishedFingerprint。

任一条件不满足，回源也只能得到“发布已失效”，不能因为缓存未命中就把当前草稿当作线上能力。

## MySQL 事实和 Redis 运行时投影

MySQL 保存网关、工具、协议、映射、数据源、能力包、成员、语义卡片、测试状态和访问 token，是长期业务事实。Redis 保存已发布能力包的最小运行投影：gatewayId、packageId、packageCode、publishedVersion、publishedFingerprint、fingerprint version、enabledToolIds 和 enabledToolNames。

运行面读投影时不需要把所有管理字段放进 Redis；`tools/list` 再根据有序 enabledToolIds 加载完整工具定义，形成第二层工具定义缓存。这样“能力包 scope 是否有效”和“完整工具 schema 如何组装”可以分别缓存和校验。

能力包投影的 key 使用网关运行时 version 隔离，而不是覆盖一个固定的 package key。概念上可以理解为：网关版本变化以后，旧版本 key 自然变成不可读，旧数据等待 TTL 回收。负结果也按版本短暂缓存，避免未发布包被高频请求反复打 MySQL。

## Cache-Aside 的真实保护逻辑

`CapabilityPackageRuntimeCacheRepository` 的读取不是简单的“先查 Redis，空了查 MySQL”：

1. 先检查网关 dirty 标记，再捕获运行时 version。
2. 使用 gateway、package、version 读取已发布投影；读取前后都复核 dirty 和 version 是否稳定。
3. 版本化空结果标记命中时，直接返回未发布/失效，空结果 TTL 默认 10 秒。
4. 未命中时尝试获取单包回源锁，拿到锁的实例二次检查缓存，再从 MySQL 查询并构建投影。
5. 只有投影生成成功，且 version 仍稳定，才写入带 TTL 和随机抖动的缓存。
6. 无论是否拿到锁，当前请求都可以回源；锁的职责是减少并发回源，不把 Redis 锁当作业务正确性的唯一保障。

正常投影 TTL 默认 5 分钟并增加最多 30 秒抖动，降低同一时刻大量失效造成的回源峰值。Redis 异常时读取接口返回 cache miss，由上层回源 MySQL；它不会把 Redis 连接异常误判成“能力包没有工具”。

## 事务脏标记为什么先于版本切换

配置写入或发布开始时，运行时仓储先写入独立 dirty mutation，并设置覆盖最大缓存 TTL 的过期时间，默认 dirty TTL 10 分钟且要求大于缓存最大 TTL。事务提交后切换 gateway version，再清理当前 mutation；事务回滚则只清理当前 mutation，不切换版本。

这个顺序解决两个竞态：

- 事务尚未提交时，运行面不继续信任旧投影，也不把尚未完成的读取结果回填为稳定版本。
- 一个事务的回滚不能清除另一个并发事务仍在使用的 dirty mutation。

如果 Redis 在版本切换时不可用，仓储保留 dirty 标记直到 TTL 到期，而不是清掉 dirty 让旧缓存重新被信任。它牺牲短时间可用性，换取配置变化期间不错误授权旧能力。

## 生命周期动作的含义

| 动作 | MySQL 事实 | Redis/运行面 | 是否可继续发布 |
| --- | --- | --- | --- |
| 更新元数据 | 更新名称、描述、编码和 version | 网关运行时失效 | 可以，需按当前版本重新测试/发布 |
| 添加/移除成员 | 修改成员和内容版本 | 失效已发布内容 | 可以，需重新发布 |
| 发布 | 写 publishedVersion、指纹和时间 | 版本失效，后续懒加载 | 已发布 |
| 停用 | PUBLISHED 变为 DISABLED | 立即失效投影 | 启用后作为待重新发布草稿 |
| 启用 | DISABLED 重新进入可编辑状态 | 失效旧投影 | 可以重新发布 |
| 归档 | 进入 ARCHIVED，只读查询 | 失效运行时 | 不可恢复和重新发布 |

启用不等于自动上线，归档也不是“软删除后可恢复”。这些语义在管理台动作和运行时可见性上都要保持一致。

## 测试证据

`CapabilityPackageServicePublishingTest` 覆盖发布责任链、成员数量、语义 READY、测试指纹、active token 和发布快照；`CapabilityPackageServiceLifecycleTest` 覆盖发布、停用、启用、归档和版本冲突。

`CapabilityPackageFingerprintServiceTest` 与 `ToolConfigurationFingerprintServiceTest` 验证顺序稳定、配置变化能产生新指纹；`CapabilityPackageRuntimeCacheRepositoryTest` 验证 dirty 期间跳过缓存、事务回滚不切版本、切版失败保留 dirty、负缓存 TTL 和旧版本加载结果不污染新版本。

`CapabilityPackageQueryIntegrationTest`、`SessionRepositoryPublishedToolCacheTest` 和 `ToolsListHandlerPackageScopeTest` 验证发布投影到工具发现的实际查询路径。

## 本篇结论

能力包把“管理配置”与“运行授权”隔开；测试指纹把“曾经成功”与“当前仍可用”隔开；Redis 版本、dirty 标记和回源锁把“数据库事实”与“可重建投影”隔开。只有这几条边界同时成立，客户端才不会看到草稿、失效成员或过期发布。下一篇进入执行层和 AI：模型怎样选择工具，网关又怎样把统一 MCP 调用分派到不同策略。
