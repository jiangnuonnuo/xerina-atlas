## 我为什么先画知识地图

AI MCP Gateway 同时包含管理面、MCP 运行面、协议适配、数据源执行、能力包发布、缓存一致性、认证隔离和 LLM 联调。如果把这些内容全部写进总览，读者只能看到名词列表；如果只写某一条调用链，又会丢掉“为什么需要能力包”和“为什么数据源不能直接暴露”这类更重要的判断。

我把文档拆分的依据不是代码包数量，而是每个问题的变化原因和验证方式：

- “能力从哪里来”是协议接入问题，关注解析、映射和上游发现。
- “能力谁能看到”是发布与授权问题，关注能力包、token 和 session scope。
- “能力怎样执行”是策略与数据源安全问题，关注请求组装、SQL/Redis 责任链和结果映射。
- “连接如何持续”是会话问题，关注 Streamable HTTP、SSE、事件回放和租约。
- “多实例能否一致”是运行时问题，关注 MySQL 事实、Redis 投影和 JVM 本地资源。

每篇专题只保留一个相对完整的核心问题，跨文档只引用结论，不重复讲完整链路。

## 跨文档主线

读者可以把所有专题放回同一组事实中理解：

| 事实类别 | 由谁产生 | 谁消费 | 失效方式 |
| --- | --- | --- | --- |
| 配置事实 | 管理用例和 Domain Service | Repository、工作台、发布服务 | 版本、状态和归档 |
| 发布事实 | 能力包发布服务 | Streamable Session、`tools/list`、`tools/call` | 禁用、重新发布、缓存版本切换 |
| 会话事实 | 认证后的 MCP 建连 | 消息分派、GET 监听、删除和恢复 | idle timeout、显式删除、网关不匹配 |
| 执行事实 | 策略和下游端口 | MCP 响应、工作台测试、调用轨迹 | 非 2xx、超时、领域拒绝 |
| 运行时投影 | Redis 缓存仓储 | 工具发现和能力包 scope 校验 | TTL、脏标记、版本变化 |
| 本地连接资源 | JVM Session 管理 | Reactor sink、SSE/Streamable HTTP | 取消、清理、实例重启 |

这里的“事实”不是所有记录都具有同等权威性：MySQL 的配置和发布字段是长期业务事实，Redis 是可重建投影，JVM 内存只承载当前实例连接资源。文章 10 会专门展开这个区分。

## 如何使用这套文档进行项目复盘

如果目标是理解业务定位，阅读总览、文章 1 和文章 3；如果目标是新增一种协议，阅读文章 2、4、5、8；如果目标是接入企业生产环境，阅读文章 7、9、10、11；如果目标是排查一次调用失败，按文章 11 的故障定位表回到文章 6、7、8 或 9。

如果目标是评估安全边界，不要只读文章 9 的权限章节，还要一起看文章 5 的数据源责任链、文章 7 的发布门禁和文章 8 的策略入口。企业真实事故往往不是单个授权判断写错，而是“可见范围、可调用范围和可执行副作用”由不同层分别放大后叠加产生。

如果目标是接手开发或准备上线，按文章 12、13、11 的顺序执行：先建立最小垂直样例，再用接口复现管理和 MCP 调用，最后用测试矩阵和故障表确认每个边界都有证据。遇到“为什么要这样设计”的问题，再回到文章 14，而不是只看接口参数。
