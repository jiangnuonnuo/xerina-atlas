## 我先把“能力”拆成几个不同的对象

项目早期最容易出现的建模误区，是把“一个 MCP 工具”理解成数据库里的一行工具记录。实际上，客户端看到的工具名称，执行时使用的协议配置，管理员组织工具的能力包，调用时绑定的会话，以及工具背后的数据源，都有不同生命周期。

如果把它们塞进一个对象，保存工具配置就会顺带改变客户端可见范围；修改数据源描述就可能绕过发布；会话删除也可能误删配置；更新一个 HTTP 映射还可能把旧测试结果错误地保留为有效。我的做法是把长期事实、运行时投影和一次调用上下文分别建模。

## 核心对象关系

| 对象 | 领域含义 | 主要状态或版本 | 依赖它回答的问题 |
| --- | --- | --- | --- |
| Gateway | 一个独立的 MCP 对外入口和配置归属 | gatewayId、配置版本 | 这套能力属于哪个边界 |
| Gateway Tool | 对外可命名的工具资产 | toolId、工具配置和版本 | AI 看到的能力叫什么、描述什么 |
| Protocol | 工具如何执行 | `http`、`mysql`、`redis`、`mcp` | 参数如何组装、由哪个端口执行 |
| Protocol Mapping | MCP 字段和下游位置之间的映射 | 请求/响应、父子路径、排序 | 一个嵌套参数落到哪里 |
| Data Source | MySQL 或 Redis 外部资源 | 类型、启停、写开关、凭证版本 | 工具执行访问哪一个资源 |
| Capability Package | 对外发布的工具集合 | `DRAFT`、`PUBLISHED`、`DISABLED`、`ARCHIVED` | 一个客户端最多能看到哪些工具 |
| Package Member | 工具进入能力包的有序成员关系 | 成员状态、版本、排序 | 某个工具是否属于这个发布单元 |
| Semantic Card | 工具的用途、输入和风险说明 | `DRAFT`、`READY`、`DISABLED` | 模型能否正确理解并使用它 |
| Tool Test State | 某个工具配置指纹下的测试结果 | 成功、失败、指纹版本 | 当前配置是否经过可执行性验证 |
| Access Token | 运行面访问某个能力包的凭证 | ACTIVE、过期、撤销、限流 | 谁可以建立这个运行范围 |
| MCP Session | 一段带 transport 和 scope 的连接上下文 | active、idle、event cursor | 请求是否属于同一次合法连接 |
| Tool Invocation | 一次工具执行的临时事实 | request、response、耗时、失败原因 | 这一次调用发生了什么 |

这里的 Gateway 和 Capability Package 都不是“权限字符串”：Gateway 是顶层归属，Package 是发布和运行授权范围；Tool 和 Protocol 也不是一回事，Tool 是 AI 可见的名称和契约，Protocol 是执行事实。

## Gateway：所有配置关系的第一层归属

`gatewayId` 出现在网关配置、工具、协议、能力包、会话和运行时缓存的 key 中。它的作用不是单纯做 URL 路径，而是防止相同工具名在不同业务边界之间串用。

例如，两个网关都可以有 `query_customer`，但它们背后的数据源、请求头、能力包和访问令牌可能完全不同。`IToolInvocationRepository` 查询协议配置时必须带 gateway，Session 处理消息时也必须比较路径中的 gateway 与 session 中的 gateway。任何一个层只按 toolName 或 sessionId 查询，都可能形成跨网关越权。

## Tool 和 Protocol：对外命名与内部执行分离

### Tool 是模型契约

工具名称、描述和 input schema 会进入 MCP `tools/list`，直接影响 LLM 的选择和参数生成。工具名称需要稳定、可读且在网关范围内唯一；描述要说清用途和限制；schema 要把必填字段、类型和可选字段写明。

### Protocol 是执行策略

同一个工具资产只应该绑定一个明确的执行协议：

| Protocol | 运行时行为 | 结果形态 |
| --- | --- | --- |
| HTTP | 从 MCP arguments 组装 Path、Query、Header、Cookie、Body，调用外部 HTTP | 根据 response mapping 解包或返回原始文本 |
| MySQL | 按数据源操作白名单校验 `sql` 或表名，交给数据源运行时端口 | 表格/行结果的文本化结果 |
| Redis | 按有限操作模型校验 key、field、value、范围和 TTL | 受限制的字符串或集合结果 |
| MCP | 将本地工具参数映射成上游 `tools/call`，由上游 MCP client 执行 | 上游 MCP 结果文本和业务错误 |

`ToolsListHandler` 根据协议类型生成不同的 input schema：HTTP 从映射树构建，数据源从 `DataSourceOperationEnum` 提供，上游 MCP 保留发现时的 schema。`ToolInvocationService` 再依据 protocolType 选择策略。这样工具对外保持统一，而内部执行可以演进。

## Data Source：连接资源不进入模型边界

数据源对象保存来源类型、连接属性、启停状态、最大返回量、超时、写开关和加密凭证。凭证通过 AES-GCM 加密保存，运行时解密后只存在于执行端口所需的短生命周期上下文中，不能在 `tools/list`、MCP 响应或普通日志中出现。

数据源的启用状态是执行条件，不是管理台展示字段。工具可以继续存在于草稿或能力包成员中，但执行时如果数据源已停用，必须在触达 MySQL/Redis 客户端前拒绝。重新启用也不等于自动扩大范围，仍然要由工具协议和能力包发布事实决定。

## Capability Package：把“可见能力”从工具配置中抽出来

能力包是本项目的核心边界对象。一个网关可以拥有很多工具，但每个对外客户端只应获得一个经过选择、测试和发布的能力集合。

### 生命周期不是展示字段

领域枚举目前包含四种能力包状态：

| 状态 | 可以做什么 | 运行面含义 |
| --- | --- | --- |
| `DRAFT` | 编辑元数据、添加/移除成员、测试和发布 | 不进入有效发布投影 |
| `PUBLISHED` | 对外提供当前版本，允许停用或重新编辑 | 包级 token 可以建立作用域 |
| `DISABLED` | 查看、启用为待重新发布草稿 | 旧运行投影必须失效 |
| `ARCHIVED` | 只读查询历史内容 | 不能重新发布或恢复为运行能力 |

能力包的 `contentVersion` 表示内容变化，`publishedVersion` 表示对外冻结的版本，`version` 用于管理更新的乐观锁。三者分开，是为了让“编辑一次”和“客户端切换一次版本”拥有不同语义。

### 成员关系也有独立事实

成员表只表示工具是否被纳入能力包、启用状态、排序和版本，不重复保存 HTTP URL、SQL 或 Redis 连接细节。发布前需要把成员补齐成当前工具配置，再检查语义状态和测试指纹。一个已经进入能力包的工具，修改了协议配置后不能继续借用旧成功状态。

## Semantic Card 和 Test State：发布前的两道不同门槛

语义卡片解决“模型是否能理解工具”，测试状态解决“当前配置是否真的可以执行”。它们不能相互替代：描述写得好不代表 URL 可达，HTTP 测试成功也不代表模型知道参数限制。

工作台保存测试时，先生成工具配置指纹；工具调用完成后再次读取当前配置并比对指纹。只有指纹没变，测试结果才允许写入 `mcp_tool_test_state`。如果网关配置发生变化，工作台状态会派生为 `NEEDS_TEST`，即使上一次测试是成功，也要重新测试；成功测试后还要显式发布。

## Session：把连接上下文与业务配置分开

SessionConfigVO 至少包含：

- sessionId、gatewayId 和 transport 类型。
- 旧认证会话的 legacy auth 信息，或新认证会话的 packageId、tokenId 和限流参数。
- Sink、本地 active 状态、创建时间和最后访问时间。
- Streamable HTTP 会话的事件序列和 replay buffer 关联。

Session 并不保存完整工具配置。后续消息通过 session 恢复 gateway 和 package scope，再实时查询当前发布投影；这样能力包重新发布可以影响新查询，但不会把凭证或协议明细复制到每一个会话对象里。Session 的存在只说明“这条连接上下文暂时有效”，不表示客户端永远拥有该能力。

## Tool Invocation：一次执行的边界

ToolInvocationCommandEntity 包含 gatewayId、toolName 和 arguments；它不携带数据库密码、不携带客户端自定义的 packageId，也不允许调用方自己指定执行策略。服务端先根据 gateway 和 toolName 查询协议配置，再由策略工厂决定执行方向。

统一结果对象包含 request、response、durationMs、unpackedResponseText 和 failureReason。HTTP 非 2xx、数据源运行异常、上游 MCP 业务错误或解包失败都可以进入这个统一结果，但“工具不在能力包”“参数不合法”这类执行前拒绝仍应以领域异常返回，不能伪装成下游 HTTP 失败。

## 领域不变量

我把下面这些不变量作为跨文章的判断基准：

1. 同一网关内能力包编码唯一，工具配置归属于当前网关。
2. 未发布、停用或归档能力包不能作为有效运行 scope。
3. `tools/list` 和 `tools/call` 都必须使用服务端确定的能力包范围，不能信任客户端提交的 packageId。
4. `tools/call` 必须在策略执行前检查工具协议配置存在且与策略匹配。
5. 数据源操作必须属于来源类型对应的枚举白名单，未知操作不能向下游透传。
6. SQL 写操作既要有数据源写权限，又要有调用参数的显式二次确认。
7. session 不能跨 gateway、transport 或失效的授权上下文使用。
8. 测试结果必须对应当前工具配置指纹，发布指纹必须由当前启用成员的确定性内容生成。
9. Redis 缓存命中不代表业务事实变更；缓存损坏或不可用时不能返回“无工具”作为成功结果。

## 我为什么不用一个“万能能力对象”

万能对象看起来减少了类数量，却会把几类变更绑在一起：协议变更影响授权，授权变更影响连接，连接删除影响配置，缓存字段又反过来定义领域状态。拆开之后，每个对象都有明确的写入者和消费者：管理服务写配置，发布服务写发布事实，会话服务写连接资源，执行服务生成调用结果，缓存仓储只投影已发布必要字段。

这也是后续新增执行来源时的保护：新增一种策略，只需要扩展 Protocol 配置、策略和运行时端口；不会因为增加一个下游适配器而修改 Session、Token 或能力包生命周期。

## 本篇结论

领域建模的核心不是把所有名词都变成类，而是把生命周期和权威来源分开：Tool 描述可见能力，Protocol 描述执行方式，Package 描述发布范围，Session 描述连接上下文，Data Source 描述受控资源，Invocation 描述一次尝试。下一篇进入其中最容易被误解的一条链：HTTP/OpenAPI 如何在不暴露任意接口的情况下成为 MCP 工具。
