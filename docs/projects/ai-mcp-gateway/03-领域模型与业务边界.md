# 领域模型与业务边界：工具不是配置表的一行记录

## 我先把几个容易混淆的对象拆开

| 对象 | 表示什么 | 不负责什么 |
| --- | --- | --- |
| Gateway | 一个独立的 MCP 对外入口 | 不等于某个客户端会话 |
| Protocol | 工具如何执行 | 不直接决定工具是否对外可见 |
| Gateway Tool | 被网关管理的工具定义 | 不代表一定已经发布 |
| Data Source | MySQL、Redis 等外部资源 | 不直接暴露原始客户端 |
| Capability Package | 一组对外发布的工具范围 | 不替代网关配置 |
| Package Member | 工具在能力包中的成员关系 | 不保存下游执行细节 |
| Tool Test State | 工具测试和准备状态 | 不等于发布事实 |
| Access Token | 访问某个能力包的凭证 | 不承担管理端身份体系 |
| MCP Session | 一段有租约的连接上下文 | 不作为永久业务数据 |
| Tool Invocation | 一次具体执行 | 不改变工具配置事实 |

## 能力包是运行时的业务边界

网关可以拥有很多工具，但客户端不应看到所有工具。能力包把工具集合、语义描述、测试状态、发布版本和访问令牌收敛为一个可对外管理的范围。`tools/list` 返回的是当前会话授权作用域下已发布的能力，不是数据库里所有工具的查询结果。

## 协议和工具的关系

HTTP/OpenAPI、上游 MCP、MySQL、Redis 都是工具的执行来源。工具对客户端呈现统一的 MCP 契约，内部通过协议配置记录参数映射、响应映射、数据源操作或上游连接信息。

这使得客户端不用知道工具后面是一个 REST endpoint 还是 Redis Hash；同时也让网关可以在执行前统一做授权、限流和参数治理。

## Session 为什么单独建模

MCP 会话包含 transport、gateway、凭证作用域、会话标识、心跳时间和事件序列。它是运行中的资源，必须支持恢复和清理；它又不是能力包配置，不能进入发布事务。当前实现用本地资源承载 Sink，用 Redis 保存可恢复的会话元数据。

## 领域不变量

- 未发布工具不能进入运行时工具列表。
- 能力包成员必须属于当前网关。
- 会话不能跨网关或跨 transport 使用。
- 数据源写操作必须显式授权。
- 工具协议必须与配置的执行策略匹配。
- Redis 缓存异常不能直接解释为能力为空。
