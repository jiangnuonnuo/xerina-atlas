# MySQL、SQL 与 Redis 转 MCP：把原始数据能力收敛成有限工具

![数据源安全责任链](./assets/datasource-safety.gif)

图要回答的问题：AI 的参数怎样进入 MySQL 或 Redis，哪些校验失败后不会触达下游。所有数据源调用都经过同一类安全责任链，再由具体运行时端口执行。

## 数据源不是连接字符串

注册数据源时，项目同时保存来源类型、连接地址、超时、最大行数、写开关和加密凭证。运行时读取的是经过解密和规则校验的连接上下文，AI 永远看不到数据库密码、Redis 客户端或原始连接对象。

## MySQL 工具

当前支持表发现、表结构描述以及 select、insert、update、delete 等受控操作。SQL 不是无限制的脚本入口：操作类型必须与 SQL 首 token 匹配，禁止 DDL、事务控制、权限管理和文件导出等危险关键字，参数通过结构化字段传入，并受查询超时和最大行数约束。

数据库默认只读。写操作必须同时满足数据源开启写权限和调用参数显式带 `confirmWrite=true`；确认字段只用于门禁，真正执行前会从参数副本中移除。

## Redis 工具

Redis 能力以有限的操作模型暴露，包括 String、Hash、List、Set、ZSet 的读取和受控修改。系统不接受原生命令参数，不允许把 `command` 作为工具参数传入；key、value、field、side、score、start、stop 和 TTL 分别进行类型、长度、字符和范围校验。

这种设计的重点不是“支持多少 Redis 命令”，而是让每个可用操作都有明确的参数契约和风险等级。

## 统一责任链

责任链依次检查协议白名单、写授权与二次确认、结构化参数和 SQL/Redis 专项规则。任何一步抛出领域异常，执行端口都不会被调用。安全规则放在 Domain，Infrastructure 只负责连接和读写。

## 数据源停用

数据源停用不是前端按钮状态，而是运行时执行条件。停用后，工具仍可能保留在配置或草稿中，但执行前必须被领域服务拒绝；重新启用后也要重新通过运行时配置读取和授权检查。
