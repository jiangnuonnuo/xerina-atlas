V-Team 反对两种同样危险的完成方式：一种是“代码写完了，理论上能用”；另一种是为一个局部修改启动全量测试、重复审查和多轮报告，直到功能本身开始怀疑人生。

它采用最小充分证据：验证必须直接支持验收结论，验证范围必须与真实风险匹配。

## 验证不是测试数量竞赛

高质量验收关心三个问题：

1. 功能是否产生了正确结果；
2. 实现是否遵守通过评判的架构；
3. 代码是否具备足够的可维护性和安全性。

三者需要证据，但不一定需要三套独立流程。一次有针对性的集成测试可以同时证明接口行为与契约兼容；一次页面主流程验收可以同时覆盖交互、状态和接口消费。

## 按风险选择验证深度

### 快速改动：直接结果

只验证被修改的行为。例如调整一个空状态文案，检查对应页面状态或组件测试即可；不必顺便验证支付、搜索和用户中心，除非它们共享了被修改的公共组件。

### 标准功能：关键主流程

验证用户主路径、最重要的错误分支和直接受影响的自动化测试。若新增契约，提供者和消费者分别留下直接证据。

### 重大变更：真实影响范围

扩展到兼容、迁移、安全、性能或回滚路径，但仍以影响分析为边界。重大任务需要更深的证据，不等于无差别运行仓库里每一个历史测试。

## 修复任务使用同一路径复验

Bug 修复遵循四步：

1. 用稳定步骤复现失败；
2. 定位根因，而不是只处理表面症状；
3. 做最小完整修复；
4. 使用同一复现路径证明前后变化。

只有在成本低且确实能防止回归时，才增加一个相关自动化测试。测试应锁住根因，不应把当前实现细节全部铸成混凝土。

## 功能验收

功能验收直接对应需求阶段的可观察条件：

- 主流程是否成功；
- 输入边界是否清楚；
- 空、加载、失败和重试状态是否合理；
- 权限与数据范围是否正确；
- 并发、重复提交或幂等是否符合方案；
- 兼容行为是否保持；
- 用户是否获得明确反馈。

验收失败时，应记录输入、预期、实际和稳定复现步骤。只写“有问题”会让问题获得很大的发挥空间。

## 架构评估

架构评估检查实现与方案的一致性：

| 检查点 | 通过条件 |
| --- | --- |
| 模块责任 | 行为位于约定边界，没有职责漂移 |
| 依赖方向 | 高层规则不反向依赖具体适配器 |
| 契约来源 | 公共接口和类型有唯一可定位来源 |
| 数据边界 | 读写、事务、迁移与错误语义清楚 |
| 兼容策略 | 破坏性变化经过明确设计 |
| 安全边界 | 权限、敏感数据和输入校验符合约束 |
| 方案偏差 | 所有实质变化均有理由并重新评判 |

普通功能不要求新建架构总结或 ADR。只有稳定架构事实确实变化时，才维护项目已有文档。

## 代码质量评估

代码质量评估关注：

- 命名是否表达业务意图；
- 分支、错误和边界条件是否完整；
- 类型与 Schema 是否一致；
- 是否复制已有能力；
- 抽象是否有真实复用或隔离价值；
- 日志是否泄露敏感信息；
- 测试是否验证行为而非偶然实现；
- 临时代码、mock 和调试输出是否清理。

“代码行数少”不自动等于高质量，“抽象层数多”也不自动获得建筑奖。判断标准始终是正确、清楚、可维护。

## V-Team 自身怎样验证

仓库的自动化测试集中在 `tests/test_vteam.py`，覆盖 33 个行为场景，包括：

- 无状态时的 context 行为；
- 角色与 ID 校验；
- 本地和外部契约引用；
- draft、ready、verified、blocked、deprecated 生命周期；
- 单契约自动选择与多契约显式选择；
- 提供者和消费者验证权限；
- 恢复记录覆盖与清除；
- 模块完成、契约稳定性和 active 清理；
- 里程碑按需记录与渐进读取；
- Skill 路由和参考规则的一致性。

运行测试：

```text
python3 -m unittest discover -s tests -p 'test_*.py'
```

检查 CLI 帮助：

```text
python3 scripts/vteam.py --help
python3 scripts/vteam.py contract --help
```

测试使用 Python 标准库，不要求额外测试框架。这样技能可以在常见开发环境中直接验证，不必先解决依赖安装问题。

## 接入 Codex 或其他 coding agent

V-Team 是目录型 Skill。使用时需要让 coding agent 能够发现根目录中的 `SKILL.md`，并保留以下结构：

```text
v-team/
├── SKILL.md
├── agents/openai.yaml
├── references/
├── scripts/vteam.py
└── tests/test_vteam.py
```

在 Codex 的个人技能目录中，通常可将仓库放置或链接为：

```text
~/.codex/skills/v-team/
```

不同 coding agent 的 Skill 目录和注册方式可能不同，但核心要求一致：`SKILL.md`、references 和脚本之间的相对路径必须保持不变。

## 显式调用

V-Team 只在任务中明确调用时启用：

```text
$v-team 为客户列表增加批量归档功能。
```

显式调用有三项价值：

- 开发者清楚本次任务会进行需求与架构判断；
- 普通问答不会意外进入交付流程；
- 状态、契约和额外验证不会在不知情时出现。

若只需要评估或设计，应在同一请求中说明边界：

```text
$v-team 评估批量归档是否值得做，只给结论和方案，不修改代码。
```

## 项目状态目录何时出现

`.vteam/state.json` 不会因为调用 Skill 自动创建。只有以下行为会写入：

- 发布或修改契约索引；
- 设置恢复记录；
- 记录模块完成事实；
- 显式记录重大里程碑。

只读取 context、发现契约、列出里程碑或清除不存在的恢复记录，不会凭空创建状态文件。

项目可以根据协作方式决定是否提交 `.vteam/state.json`：

- 若契约索引和恢复状态需要跨成员共享，可以纳入版本控制；
- 若只用于本地临时恢复，可以加入忽略规则；
- 决策应由项目规则确定，V-Team 不擅自修改 `.gitignore`。

## Git、CI 与发布边界

V-Team 本身不要求创建分支、提交、push、merge 或 PR，也不自动部署。只有用户明确授权或仓库规则要求时，才进入这些操作。

在正式项目中，可以把 V-Team 测试接入现有 CI：

```text
python3 -m unittest discover -s tests -p 'test_*.py'
```

若项目只消费 V-Team 而不修改技能代码，则没有必要把技能自身测试混入每次业务构建。功能验证仍应使用业务项目自己的测试、构建和验收命令。

## 安全与可靠性边界

- CLI 只写项目根目录下的 `.vteam/state.json`；
- 本地契约引用必须位于项目内；
- 保存采用原子替换，减少部分写入；
- 不读取契约正文到状态；
- 不自动访问网络；
- 不自动执行 Git 或部署操作；
- 不用“应该通过”替代实际验证结果。

V-Team 的验证哲学可以浓缩为一句话：该证明的必须证明，与结论无关的不要顺手证明。这样既守住交付质量，也让一次小功能仍然能够在合理时间内结束。
