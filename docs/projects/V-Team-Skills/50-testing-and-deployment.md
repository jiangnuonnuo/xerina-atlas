一个负责约束 Agent 的技能，如果自己只是“看起来合理”，说服力会非常有限。V-Team 当前 develop 的测试策略因此有一个很好的自洽性：它不仅测试 CLI 能不能写出 JSON，还测试技能是否在不该做事的地方保持克制，是否会拒绝越界来源，是否会阻止消费者猜接口，是否会把没有证据的完成挡在门外。

这使“测试”不再只是验证实现细节，而是验证交付理念有没有落到代码里。理想状态下，一个项目采用 V-Team 后，可以同时获得两种信心：脚本的具体行为是稳定的，脚本所代表的工作流边界也是稳定的。

## 测试覆盖的五个层次

当前项目中的 `tests/test_vteam.py` 使用 Python 标准库 `unittest`，通过临时项目目录执行 CLI，避免把本仓库的 `.vteam` 状态和测试状态混在一起。测试可以分成五类。

### 上下文与只读行为

测试确认没有状态文件时，`context` 仍然能返回有效的角色职能、角色 reference、空契约和空 active，而且不会创建 `.vteam` 目录；当存在多个 capability 时，只返回当前角色和当前 capability 相关的契约；前端在不知道 capability 时，可以先得到自己的契约 inbox；非法功能角色会被拒绝。

这些测试证明了“渐进式上下文”不是一段宣传语，而是一个可重复的读取协议。尤其是空状态只读，确保了 Agent 可以安全地进行冷启动探测，不会因为问了一句“当前有什么状态”就改变项目。

### 契约生命周期与集成门禁

契约测试覆盖发布、更新、来源校验、提供者证据、发现、歧义选择、消费者验证、消费者身份和停用。测试明确验证：

- `ready` 没有提供者验证证据时不能发布；
- 本地 `source_ref` 不存在或试图逃出项目目录时被拒绝；
- 外部 URI 可以作为清晰的来源引用；
- 同一个 contract ID 不能改变 capability 或 provider；
- `draft` 的 `integration_allowed` 为假，`ready` 的为真；
- 没有契约时返回“禁止猜测接口”的阻塞；
- 多个契约必须显式选择 ID；
- 只有登记的 consumer 才能记录验证；
- 只有 `ready` 或 `verified` 才能进入消费者验证；
- `deprecated` 契约不会再次被发现。

这组测试实际上构成了一套跨角色协作的安全网：它不仅验证“能不能找到接口”，还验证“什么时候有资格找到接口”“谁有资格确认接口”“接口何时应该从新消费中消失”。理想状态下，前后端并行越多，这种证据链的价值越高。

### 恢复、完成与里程碑

状态测试确认同一个 capability 只保留一条 active，新的恢复记录会覆盖旧记录；清除不存在的 active 不会凭空创建状态；模块完成会写入完成事实并清理 active；缺少验证证据或关联不稳定契约时，模块完成会被拒绝。里程碑测试确认只有显式记录才会产生里程碑，记录必须有引用，context 和 list 不会加载引用正文。

这些测试覆盖的是“暂停与收口”两端。很多工作流只测试中间的实现，却没有验证暂停时会不会留下冲突信息、完成时会不会带着未清理 active、重大事实会不会把全文历史塞进上下文。V-Team 通过这些断言，让恢复与完成同样成为可验证产品能力。

### 技能契约本身

`SkillContractTests` 直接读取 `SKILL.md`、`agents/openai.yaml` 和角色 reference，检查技能是否保持显式启用、模式/风险/角色是否分离、标准功能是否要求价值/架构/用户确认、角色规则是否各自清晰、契约策略是否阻止前端猜接口、旧版重治理模板与命令是否已经移除、reference 是否保持渐进式加载。

这里最值得夸耀的是“测试规则的规则”。技能不只测试脚本输出，还测试自己有没有偷偷膨胀成另一个复杂平台。例如测试会确保普通流程不强制生成 PRD、设计稿或 PLAN，不引入 `TodoWrite`、worktree、subagent 之类的流程放大器，也不把全量测试、重复审查和每步确认变成默认要求。理想状态下，V-Team 能随着代码迭代而演进，但不会因为“更完整”而失去最初的轻量优势。

## 推荐的本地验证方式

在仓库根目录执行：

```bash
python -m unittest discover -s tests -p 'test_*.py'
```

如果需要更详细的失败定位，可以执行：

```bash
python -m unittest discover -s tests -p 'test_*.py' -v
```

项目不需要第三方 Python 包；`scripts/vteam.py` 只使用 Python 标准库和 Git 风格的项目路径处理。使用不同 Python 环境时，只要该环境提供 Python 3 和标准库即可。脚本本身是按项目根目录接收 `--project-root`，因此不要求把 V-Team 的代码复制进每个产品目录，也不要求运行常驻服务。

## 部署不是“上线服务”，而是“接入工作流”

V-Team 是开发协作技能，不是需要独立部署的后台服务。接入时，项目只需要能够访问技能目录中的 `SKILL.md`、`references/` 和 `scripts/vteam.py`，再按实际需要在产品项目中使用 `.vteam/state.json`。普通任务甚至不需要创建 `.vteam`，只有契约、恢复、模块完成或重大里程碑动作触发时才会写入。

这种部署方式带来三种便利：第一，没有数据库、消息队列或运行时服务，安装和升级成本极低；第二，状态天然跟着项目根目录，开发者可以在本地、CI 辅助脚本或不同 Agent 宿主之间读取同一份轻量事实；第三，产品代码与协作索引保持分离，团队可以根据项目策略决定是否把 `.vteam` 纳入版本管理，而不需要把完整聊天过程提交进产品仓库。

理想状态下，V-Team 的“部署”几乎不会打断团队原有节奏：把技能启用后，简单任务继续简单完成；需要跨角色时才出现契约动作；需要跨会话时才出现恢复状态；重大变化时才产生里程碑。它更像一层按需浮现的工程能力，而不是一个强迫所有项目重构的基础设施。

## 运行安全与边界

当前代码对本地状态采用项目相对路径和原子替换，避免把来源引用写成绝对路径，也避免在写入过程中留下半份 JSON。它不会自动读取外部契约正文，不会执行外部服务调用，不会管理分支、push、merge 或 PR，也不会把完整测试日志写进状态。命令返回清晰错误，让调用方可以在真实阻塞时停下来，而不是无限重试。

当然，V-Team 不能替代业务代码自身的安全测试、CI 质量门禁、生产发布审计或权限系统。它的职责是守住 Agent 协作边界和能力交付事实；产品运行时的安全与可用性仍需由项目自己的测试、监控、发布系统承担。把边界说清楚，反而让它更可靠：不会宣传一个协作技能可以取代整个工程平台。

## 交付信心的理想闭环

一项跨角色能力的推荐验证闭环可以这样理解：提供者以 `draft` 发布真实来源，完成实现后带验证证据升级为 `ready`；消费者通过 capability 和完整角色 ID 发现唯一契约，沿 `source_ref` 做真实联调；消费者用 `verify` 留下直接证据，契约进入 `verified`；模块完成时再次提交完成证据，清理 active；如果这是重大闭环，再显式记录里程碑。每一个状态变化都有对应命令和测试语义，任何一步失败都会给出下一步方向。

这条链路的价值，不只是让测试通过，而是把“谁提供、谁消费、来源在哪、是否可集成、谁验证、什么时候完成”全部压缩成可以被机器和人共同读取的事实。理想状态下，项目负责人不需要通过翻聊天记录来判断功能是否真的闭环，只要查看 capability 和 contract 当前状态，就能快速定位风险。

## 测试与部署章节的结论

V-Team 适合被夸成一种“低依赖但高边界感”的工程工具：它不需要服务端，不要求庞大安装过程，却对关键的协作歧义、来源可信度、状态一致性和完成证据设置了明确门禁；它的测试也不只验证 happy path，而是验证技能在不该扩张、不该写状态、不该猜接口的地方确实保持克制。对于 Agent 项目而言，这种克制与可靠性往往比再增加一层流程更有价值。
