V-Team 的系统设计遵循一个朴素原则：高质量流程需要明确规则，但不需要把所有规则同时塞进一次任务。它将路由、角色知识、状态工具和项目事实分层，每一层只负责自己能证明的事情。

## 架构要解决的四个矛盾

### 完整流程与低开销

需求、架构、实现和验收都很重要，但一个局部修复不应预读全部角色规范。V-Team 用风险路由和渐进加载保留完整能力，同时控制单任务成本。

### 角色分工与个人开发

需求、架构、后端、前端和 QA 是不同的思考职责，不等于必须启动不同 Agent。同一个 coding agent 可以按阶段切换角色，个人开发者无需为了改一个接口先组建虚拟公司。

### 可恢复状态与项目清洁

跨会话工作需要状态，普通任务却不需要额外文件。V-Team 仅在契约索引、明确恢复或重大里程碑需要时创建 `.vteam/state.json`。

### 流程治理与项目事实

V-Team 管理工作流和索引，但不复制业务规范。OpenAPI、Schema、protobuf、共享类型和项目测试仍是事实来源；状态文件只保存定位信息。

## 四层结构

### 第一层：核心路由 `SKILL.md`

`SKILL.md` 是入口和决策层，负责：

- 判断回答、设计、实现、修复或恢复模式；
- 划分快速、标准和重大风险；
- 选择当前需要的角色规则；
- 规定确认、契约、状态和验证的触发条件；
- 定义什么算完成。

它刻意保持紧凑，因为入口文件会影响每次显式调用。这里放原则与路由，不放每个角色的全部操作细节。

### 第二层：角色与策略参考 `references/`

参考文件包含进入特定阶段才需要的知识：

| 文件 | 责任 |
| --- | --- |
| `role-requirement.md` | 需求价值、范围、验收与审判 |
| `role-architect.md` | 模块边界、契约、数据、安全、迁移与回滚 |
| `role-backend.md` | 后端实现、错误语义、数据与直接验证 |
| `role-frontend.md` | UI 状态、契约消费、联调与交互验证 |
| `role-qa.md` | 风险驱动的独立验收与证据 |
| `contract-policy.md` | 跨角色契约生命周期 |
| `debugging-policy.md` | 复现、根因定位和最小修复 |
| `milestone-policy.md` | 恢复状态与重大事实引用 |

这些文件不是预读套餐。纯后端快速任务通常不需要前端和 QA 规则；稳定接口上的页面修改通常不需要架构参考。

### 第三层：轻量工具 `scripts/vteam.py`

CLI 只处理需要稳定结构的事情：

- 读取当前角色的最小上下文；
- 发布、发现、验证和停用契约索引；
- 保存或清除跨会话恢复点；
- 记录 capability 的当前完成事实；
- 显式记录和读取重大里程碑引用。

CLI 不决定需求价值，也不替代架构判断。把判断交给结构化脚本看似客观，最后往往只是把主观意见写成了退出码。

### 第四层：项目事实

真正决定功能行为的内容仍在业务项目中：

- 源代码和配置；
- OpenAPI、GraphQL、protobuf 或 JSON Schema；
- 数据库迁移与模型；
- 共享类型；
- 自动化测试；
- 已有架构和产品文档。

V-Team 引用这些事实，不把它们抄进自己的状态。这样契约更新时只维护权威来源，避免两个文件都自称“最终版本”。

## 渐进加载怎样工作

一次标准前后端功能可能按以下顺序读取规则：

1. 核心路由判断为标准实现；
2. 价值或验收不清时读取需求参考；
3. 存在接口与模块选择时读取架构参考；
4. 开始后端实现时读取后端参考；
5. 需要跨角色对接时才读取契约策略；
6. 开始页面与联调时读取前端参考；
7. 风险较高或闭环复杂时读取 QA 参考。

每次只加载当前阶段真正需要的内容。规则仍然完整，注意力却不会被尚未发生的问题占满。

## 角色是责任镜头，不是组织架构

V-Team 的角色有明确输入和输出：

| 角色 | 看什么 | 交付什么 |
| --- | --- | --- |
| Requirement | 问题、价值、范围、验收 | 可进入设计的需求结论 |
| Architect | 边界、协议、数据流、风险 | 可指导实现的技术方案 |
| Backend | 领域行为、接口、数据、错误 | 可供验证和消费的后端能力 |
| Frontend | 用户流程、界面状态、联调 | 可观察的完整交互 |
| QA | 风险、验收、回归证据 | 可信完成结论或明确缺口 |

同一个 Agent 在不同阶段使用不同镜头，有助于避免“实现者已经知道自己想怎么写，所以需求看起来总是非常合理”的心理捷径。

## capability 是单任务的稳定语义

只有跨角色契约或跨会话状态存在时，才需要稳定 `capability_id`。它表示一个可独立理解和完成的用户能力，例如：

```text
order-export
sandbox-runtime
billing-invoice-download
```

ID 使用小写字母、数字、点、下划线或短横线，便于命令行、JSON 和自动化工具共同处理。普通快速任务不创建 capability，只为统一命名而制造状态没有实际价值。

## 契约索引与契约正文分离

跨角色协作需要回答：谁提供、谁消费、正文在哪里、当前能否联调。V-Team 的状态只保存这些索引字段：

- 契约 ID 和 capability；
- provider 与 consumers；
- 类型与 `source_ref`；
- `draft / ready / verified / blocked / deprecated` 状态；
- 版本、破坏性标记、验证证据；
- 可选 mock、说明和替代契约。

请求字段、响应结构和业务规则留在权威契约中。状态文件像图书馆目录，负责告诉你正文在哪里；它不把整份内容手抄进卡片盒。

## 单一状态文件的边界

需要持久化时，V-Team 使用：

```text
<project-root>/.vteam/state.json
```

文件包含四组当前事实：

- `capabilities`：模块完成记录；
- `contracts`：契约索引；
- `active`：每个 capability 一条恢复记录；
- `milestones`：显式记录的重大事实引用。

写入采用临时文件后原子替换，减少半写入状态。它不生成按日期增长的历史副本，也不承担审计系统职责。

## 读写边界与安全设计

V-Team 对状态输入执行明确约束：

- 项目根目录必须真实存在；
- 本地 `source_ref` 必须是项目内相对路径；
- 路径不能逃逸项目目录；
- 外部引用必须是结构合法的 URI；
- ID 和角色必须符合固定格式；
- 状态 schema 版本和字段类型必须正确；
- `ready` 契约必须包含提供者直接证据；
- 消费者只能验证登记给自己的契约。

这些规则不替代业务安全审查，但能阻止索引层最常见的猜测、错连和路径混乱。

## 为什么不把 Git、CI 和部署放进来

V-Team 不默认创建分支、提交、推送、PR 或发布。原因不是这些事情不重要，而是它们属于项目治理和交付平台，授权与规则差异很大。

功能技能只在用户请求或项目规则要求时执行这些动作。职责边界清楚后，V-Team 可以进入不同仓库而不擅自改写团队工作方式。

## 这套架构的优势

- **低上下文成本**：只读当前阶段规则；
- **高事实一致性**：契约正文始终留在项目权威来源；
- **适合个人开发**：同一 Agent 连续切换职责；
- **可恢复但不留垃圾**：状态按需创建，完成后清理 active；
- **易于验证**：CLI 行为稳定，流程判断保持可解释；
- **边界清晰**：不把功能交付扩张为全能工程平台。

V-Team 的系统设计不是追求更多层，而是让每一层都有停止工作的勇气。好的结构不仅知道自己负责什么，也知道哪些事情应该留给别人。
