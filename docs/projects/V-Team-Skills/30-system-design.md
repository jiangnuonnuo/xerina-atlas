V-Team 的系统设计有一个非常鲜明的取舍：它不试图把产品代码、完整聊天记录、项目管理历史和 Agent 编排平台全部塞进一个框架，而是只保留那些会直接影响功能交付正确性的最小事实。`SKILL.md` 负责告诉 Agent 如何判断路线，`references/` 负责提供阶段规则，`scripts/vteam.py` 负责保存和验证少量跨角色或跨会话事实，真正的业务代码、API 正文和测试仍然属于产品项目本身。

这让 V-Team 更像一个轻量控制面，而不是另一个产品运行时。它在项目开始前不抢占业务目录，在普通功能完成时不强行写状态，在不需要跨角色协作时不制造契约。理想状态下，控制面只在关键边界出现：需要选择路线时给出判断，需要对接时给出唯一来源，需要暂停时保存下一步，需要收口时验证事实。

## 四层结构：规则、角色、事实与产品代码

可以把当前 develop 的结构理解为四层：

```text
用户意图
   ↓
SKILL.md：模式 × 风险 × 当前角色
   ↓
references/：需求 / 架构 / 后端 / 前端 / QA / 契约 / 调试 / 里程碑规则
   ↓
scripts/vteam.py：context、contract、resume、module、milestone
   ↓
产品项目：业务代码、API/Schema、测试与发布系统
```

第一层是路由层。`SKILL.md` 先区分回答、评估/设计、实现、修复和恢复，再区分快速、标准和重大，最后决定当前需要哪一个角色参考。第二层是专业规则层，每个 reference 只解决一类问题，不把所有角色的注意事项混成一张无限增长的清单。第三层是事实索引层，脚本把契约、active、能力完成状态和里程碑落在项目内唯一的 `.vteam/state.json`。第四层是产品事实层，接口正文仍然放在 OpenAPI、GraphQL Schema、protobuf、JSON Schema、共享类型或契约测试里，V-Team 只保存定位索引。

这种分层的便利在于“谁负责什么”非常清楚：技能负责行为约束，参考文件负责专业判断，状态工具负责当前事实，产品仓库负责真实实现。理想情况下，即使换一个 Agent 宿主、换一个会话、换一位开发者，也不会因为控制面和产品面混在一起而丢失边界。

## `SKILL.md`：最小路由器，而不是百科全书

当前 `SKILL.md` 的核心设计是渐进式加载。它不预读所有角色，也不要求每个普通任务都创建记录，而是先给出判断框架，再把详细规则指向具体 reference。`agents/openai.yaml` 又明确设置 `allow_implicit_invocation: false`，意味着 V-Team 不会因为项目里存在这份技能就隐式接管每个请求；只有用户明确调用 `$v-team`，才进入这套路由。

这是一个非常适合 Agent 的边界。技能正文越短，冷启动越轻；角色 reference 越专门，阶段内的判断越精准；调用越明确，用户对流程成本越有预期。理想情况下，V-Team 甚至可以被看成一个“上下文预算管理器”：它不追求把所有知识一次性装进窗口，而是只在决定需要时载入下一片知识。

## `.vteam/state.json`：一个文件承载四类当前事实

脚本将状态集中在版本化的 `.vteam/state.json` 中，初始结构包含四类集合：

| 状态区 | 作用 | 为什么要保持轻量 |
| --- | --- | --- |
| `capabilities` | 记录某个 capability 的当前完成事实、摘要、验证证据和稳定契约 | 只表达现在是什么，不保存每一次历史修改 |
| `contracts` | 保存 provider、consumer、来源、状态、版本、breaking 和验证记录 | 索引真实来源，不复制接口正文 |
| `active` | 每个 capability 最多一条当前恢复记录 | 只保存当前摘要、下一步、阻塞、角色和必要引用 |
| `milestones` | 保存重大能力或架构事实及其外部引用 | 只在重大里程碑发生时记录，不把普通完成变成档案系统 |

状态版本固定为 `2`，读取时会校验根节点和各字段类型；写入时先写临时文件，再原子替换目标文件。这两个细节很容易被忽略，却决定了它在理想场景下能否被可靠地读取：版本化防止新旧结构静默混用，类型校验防止损坏 JSON 被当成正常状态，原子覆盖则避免在中断写入时留下半份状态。

更重要的是它明确规定“不保存什么”：不保存完整聊天记录，不保存接口正文，不保存完整测试日志，也不保存版本历史。这样做让状态文件成为“当前真相索引”，而不是一个越来越大的第二仓库。需要详细接口时跟随 `source_ref` 去权威来源，需要测试细节时读取实际测试结果，需要理解历史时查看 Git 或已有架构文档，各类事实各自归位。

## Capability 是交付边界，Contract 是协作边界

V-Team 用 capability 表示“正在完成的一项能力”，用 contract 表示“提供者与消费者之间需要稳定对接的接口”。两者相互关联，但不混为一谈：一个 capability 可以有一个或多个契约，一个契约属于一个 capability；能力完成前，相关契约必须达到 `ready` 或 `verified`，否则不能被包装成稳定闭环。

契约索引只保存定位信息：`id`、`capability`、`provider`、`consumers`、`source`、`source_ref`、`status`、`version`、`breaking`，还可以附带 `mock`、`verification` 和阻塞说明。`source_ref` 要么是项目内存在的相对路径，可以带 fragment，要么是清晰的外部 URI；绝对路径、逃逸项目目录的路径和不存在的本地文件都会被拒绝。这使契约既可以落在当前项目的 Schema 上，也可以连接外部 Catalog，而不会接受模糊的“某个接口文档”。

契约状态形成一条可解释的生命周期：`draft` 允许设计和 mock，`ready` 代表提供者已经实现并给出直接验证证据，`verified` 代表消费者或契约测试完成了真实验证，`blocked` 必须说明原因，`deprecated` 则停止新消费。理想状态下，这条状态链让跨角色协作拥有一个清晰的红绿灯，而不是依赖某个人说“后端应该已经好了”。

## Context 是冷启动的最小窗口

`context` 命令不会把整个项目状态倾倒给 Agent，而是按角色 ID 和可选 capability 过滤，返回当前角色职能、对应角色 reference 路径、能力当前状态、相关契约、active 恢复记录、里程碑数量以及状态文件是否存在。当 capability 未知时，前端等消费者可以先读取与自己相关的契约 inbox，再进一步按 capability 精确发现；当没有状态文件时，`context` 仍然是只读的，不会为了查询而创建 `.vteam` 目录。

这种设计可以被夸张地描述为“让新会话拥有上一会话的方向感，却不继承上一会话的噪音”。它不会加载无关 capability，不会复制接口字段，不会打开完整历史，也不会把状态查询变成写操作。理想情况下，一次冷启动就足以回答三个问题：我是谁、我正在处理哪项能力、下一步应该沿着哪个真实来源继续。

## 按需状态与按需里程碑

普通功能不需要创建任何 V-Team 状态。只有跨角色契约索引、明确的跨会话恢复，或用户要求/系统确实发生重大变化时，才使用 `.vteam/state.json`。`resume set` 覆盖某个 capability 的唯一 active 记录，`resume clear` 在任务完成或放弃后清除；`module complete` 会写入完成事实并顺手清理对应 active。重大里程碑则必须显式记录 `id`、capability、摘要和持久引用，查询列表时只返回紧凑索引，查看详情时才读取引用信息。

这套设计把“持久化”从默认负担变成有理由的选择。理想状态下，短命的上下文不会留下垃圾，真正需要接力的任务又不会因为会话结束而失去方向；一个完成的能力不会继续占用 active，一个已经停用的契约也不会重新出现在消费者的发现结果里。

## 系统设计的结论

V-Team 的架构并不靠复杂组件制造可靠性，而是靠边界清晰制造可靠性：规则与实现分离，索引与正文分离，当前事实与历史记录分离，必要状态与默认无状态分离。它把 Agent 项目最容易失控的部分——上下文、协作接口、恢复记忆和完成定义——压缩成一套很小的控制面。理想状态下，项目越大，越能感受到这种轻量设计的价值：新增能力不会自动新增一堆流程，只有真实的跨角色连接和重大状态变化才会留下可追踪痕迹。
