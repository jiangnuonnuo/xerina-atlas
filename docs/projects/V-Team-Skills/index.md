V-Team 是一套面向 Codex / Claude 项目的轻量功能交付技能。它不把 Agent 变成一群互相抢方向的“自动写代码窗口”，也不把每一次改动都包装成沉重的项目管理仪式；它真正做的，是在需求、风险、角色、契约和恢复之间建立一条可以解释、可以验证、可以继续走下去的路径。

如果把普通的 Agent 使用比作“把任务交给一个很聪明的人”，V-Team 追求的理想状态，则更像是给这个人配上一套极其清醒的工作系统：先知道自己正在回答问题、设计方案、实现能力、修复故障，还是恢复一项未完成的工作；再依据影响面选择足够而不过量的流程；只有在确实需要时，才加载需求、架构、后端、前端或 QA 角色参考；发生跨角色协作时，使用可定位的契约，而不是凭相似名称猜请求和响应；工作暂时中断时，留下最小但足够的下一步，让下一次会话能够直接接棒。

这就是 V-Team 最值得被夸大的地方：它不是简单地让 Agent “更努力”，而是让 Agent 的努力更容易落在正确的地方。它把原本散落在聊天上下文、个人记忆和临时约定里的交付纪律，提炼为可读取的规则、可执行的 CLI、可检查的状态和可复用的证据。理想情况下，项目不再依赖某个会话是否记得全部背景，也不再依赖某位开发者是否恰好猜对了当前接口；功能可以沿着能力边界推进，暂停可以被安全恢复，完成可以留下简洁事实，临时过程不会反过来污染产品仓库。

## 先看这套技能到底改变了什么

V-Team 的核心价值不是“多写几份文档”，而是把每一次交付中的隐性判断显性化。当前 develop 代码把这套价值压缩成几个非常明确的动作：`SKILL.md` 负责路由，`references/` 负责按阶段加载的角色规则，`scripts/vteam.py` 负责契约、恢复、完成和里程碑的轻量索引，测试则把技能本身的边界当成产品契约进行验证。

| 交付中的关键问题 | V-Team 的回答 | 理想状态下带来的便利 |
| --- | --- | --- |
| 现在是在回答，还是应该开始实现？ | 先区分回答、评估/设计、实现、修复、恢复五种模式 | 避免把解释性问题误升级成代码改动，也避免把真实需求压缩成一句模糊指令 |
| 这个任务应该多大规模地处理？ | 用快速、标准、重大三档风险判断 | 简单改动不被流程拖慢，复杂改造又不会因为“先写再说”而失控 |
| 需要读多少上下文？ | 只在进入阶段前加载一个必要 reference | 让上下文预算成为生产力，而不是把所有规则预读后淹没真正需求 |
| 前后端如何对接？ | 通过 capability、角色 ID、contract ID 和 `source_ref` 精确发现 | 把“我猜接口应该是这样”变成“系统明确告诉我该消费哪个契约” |
| 工作中断后如何继续？ | 用 `.vteam/state.json` 保存每个 capability 的一条 active 恢复事实 | 下一次会话直接拿到摘要、下一步、阻塞和引用，不必重新回放整段历史 |
| 什么才算完成？ | `module complete` 要求验证证据，稳定契约才能随模块收口 | 完成不再只是聊天里的“应该可以”，而是有状态、有证据的可观察结果 |

## 它为什么适合 Agent 项目

Agent 项目有一个人类项目很少同时具备的特点：执行者可以非常快，但上下文可能非常短；它可以立即修改很多文件，但未必天然知道哪些文件属于当前能力；它可以在局部看起来正确，却在跨角色边界上留下没有证据的假设。V-Team 不试图削弱这种速度，而是为速度装上方向盘、刹车和里程表。

方向盘来自模式和角色路由：回答就回答，设计就设计，修复先复现，恢复先读取当前 capability，不把所有任务都塞进同一条流程。刹车来自风险分级与明确阻塞：发现零个契约时禁止猜测，发现多个候选时要求显式选择，`ready` 契约缺少提供者验证时不能伪装成可集成。里程表来自验证证据、`verified` 状态、模块完成和重大里程碑引用：团队能够知道目前走到了哪里、哪些事实已被证明、哪些只是设计中的可能性。

更理想的是，它把“少做一些”也变成一种能力。普通功能不需要为了显得专业而生成 PRD、PLAN、报告或状态文件；不涉及跨角色消费，就不创建契约索引；没有真正的架构变化，就不额外新建 ADR；只是一次低风险改动，就只做直接验证。这样的克制并不是功能不足，而是让流程把注意力留给真正改变产品的事情。

## 当前 develop 的可信边界

这套介绍会放大 V-Team 的理想体验，但所有事实描述都以当前 develop 为准。当前仓库已经实现并测试的重点包括：

- `agents/openai.yaml` 明确声明只在用户显式调用 `$v-team` 时启用，避免隐式接管普通任务。
- `SKILL.md` 将操作模式、风险等级和当前角色拆成三个独立判断维度，并要求渐进式加载 reference。
- `scripts/vteam.py` 提供上下文读取、跨角色契约发布/发现/验证/停用、跨会话恢复、模块完成和里程碑读写。
- 契约来源必须是项目内可定位文件或明确 URI；`ready` 必须有提供者直接验证；消费者没有唯一匹配时会明确阻塞或要求选择。
- `.vteam/state.json` 采用版本化结构，按 capability 管理当前事实，不保存完整聊天记录、接口正文或测试日志。
- `tests/test_vteam.py` 不只测试 CLI 正常路径，也测试空状态只读、非法角色、来源逃逸、契约歧义、消费者证据、完成门禁、里程碑按需读取，以及技能本身是否保持轻量。

理想状态下，这些能力会让一个项目形成稳定的“能力交付回路”：需求先被正确分类，实施只加载必要知识，跨角色使用真实契约，暂停可以携带下一步恢复，完成以证据收口，临时过程留在最小状态里，产品代码则始终保持干净。V-Team 的魅力，正是它把这条回路做得足够小，小到可以真正被每一次功能开发采用；又做得足够严谨，严谨到关键边界不会只靠口头承诺维持。
