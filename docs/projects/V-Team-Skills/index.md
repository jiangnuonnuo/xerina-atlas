> 先判断值不值得做，再决定怎样做；代码完成不是终点，能够证明它正确才是。

V-Team 是一套用于 Codex、Claude 等 coding agent 的个人开发技能。它围绕一次功能需求建立完整交付路径：搜索已有能力、分析需求价值、形成技术与架构方案、约束代码实现、完成轻量验收，并在失败时回到真正需要修正的阶段。

它没有把开发包装成一场流程嘉年华。小任务应该保持小，重要功能应该认真，重大改造则必须面对契约、数据、安全、迁移和回滚。V-Team 所做的，是让每种任务得到与风险匹配的工程处理。

V-Team 由个人开发者在日常项目中持续使用和维护。实际开发中出现的判断、失误、取舍和有效经验，会逐步沉淀为技能规则。它不是为了展示一套漂亮流程，而是为了帮助使用 coding agent 的开发者真正进入功能实现工作：少做无价值功能，少做重复工作，合理化拆分角色实现，隔离对话上下文。

## 为什么会有 V-Team

coding agent 的执行速度很快，但速度本身不会自动带来正确方向。用户只说“加一个导出按钮”，几分钟后可能已经出现一个新接口、一个新服务、三份测试和一个未来没人敢删的抽象层。按钮还没验收，架构先获得了自己的小型城市规划。

V-Team 关注三个更基础的问题：

1. 这个需求是否真的有价值，现有能力是否已经能够满足？
2. 如果要做，怎样形成符合当前项目的技术与架构方案？
3. 怎样用最小充分证据确认功能、架构和代码质量都达到要求？

这些问题看起来朴素，却决定了开发工作是在解决问题，还是在高质量地制造新问题。

## V-Team 能带来什么

| 能力 | V-Team 的做法 | 实际价值 |
| --- | --- | --- |
| 复用发现 | 先检查项目代码、已有接口和可用 Skills | 避免重复实现 |
| 需求审判 | 支持 Pass、Reuse、Narrow、Reject 和 Blocked | 开发不再是唯一答案 |
| 技术落地 | 把目标映射到模块、契约、数据流和验证 | 方案能够直接指导代码 |
| 架构约束 | 实现必须贴合通过评判的方案 | 防止开发途中偷偷换题 |
| 分层验收 | 功能、架构、质量分别验证 | 结果正确，结构也健康 |
| 风险控制 | 快速、标准、重大三档流程 | 不让小任务被重型流程拖住 |
| 精确回退 | 哪里出错就回哪里 | 避免验收失败后全部重来 |
| 轻量恢复 | 只保存当前摘要、下一步和必要引用 | 跨会话继续而不吞下全部历史 |

## 它适合哪些任务

V-Team 适合处理：

- 新增用户可感知的功能；
- 修改现有业务行为；
- 设计页面、接口、数据流程或模块边界；
- 修复 Bug、测试失败和异常行为；
- 评估需求是否值得开发；
- 恢复一项跨会话尚未完成的功能；
- 需要前后端或其他角色通过契约协作的任务。

它不接管普通问答，也不自动管理 Git 分支、PR、CI/CD 或生产发布。V-Team 是功能交付技能，不是一个把所有工程工具吞进肚子里的“超级平台”。超级平台听起来很威风，维护起来通常也很有存在感。

## 一条完整任务怎样运行

V-Team 将单任务分为六个连续动作：

1. **发现**：搜索项目已有能力、相关 Skills 和必要的官方资料。
2. **审判**：判断需求的价值、必要性、可行性、范围和验收条件。
3. **方案**：形成能够落到真实模块、接口和数据流的技术设计。
4. **实现**：严格依据通过评判的方案编写代码。
5. **验收**：检查功能结果、架构符合性和代码质量。
6. **交付**：报告实际完成内容、验证证据和未覆盖风险。

需求价值不足时可以停止；已有能力满足时可以复用；方案错误时回到方案；实现错误时只修代码。流程允许前进，也允许在正确位置掉头。

## 风险决定流程深度

### 快速任务

局部、明确、易回滚，不改变公共 API、Schema、数据、权限、安全和架构。V-Team 完成本地检查后直接实现，只验证直接结果，不等待方案确认，不写状态。

### 标准功能

新增用户能力、业务行为或 UI 流程，或者存在真实技术取舍。V-Team 给出紧凑的需求与方案摘要；只有出现实质选择时才确认一次，批准后连续实现和验收。

### 重大变更

涉及公共协议、数据迁移、安全边界、核心架构或难回滚操作。V-Team 会明确兼容、迁移、失败恢复和回滚，并按照真实影响扩大验证。

风险等级由影响面决定，不由文件数量决定。改十个局部文件可能仍然是快速任务；修改一份公共权限 Schema，即使只有两行，也不会突然变得天真无邪。

## 如何使用

在项目任务中显式调用：

```text
$v-team 为订单列表增加按当前筛选条件导出 CSV 的功能。
```

也可以限定当前只做某个阶段：

```text
$v-team 先评估这个需求是否有必要，不要修改代码。
```

```text
$v-team 只设计技术方案和模块边界，确认后再决定是否实现。
```

```text
$v-team 恢复 order-export capability，继续上次记录的下一步。
```

V-Team 只在明确调用时启用。这让开发者知道什么时候增加了需求判断、架构约束和状态语义，也让普通任务保持原来的低成本。

## V-Team 的一句话原则

值得做的需求，使用合适的方案，以符合架构的代码完成，再用恰到好处的证据证明它。
