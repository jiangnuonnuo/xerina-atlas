V-Team 把需求分析放在代码实现之前，因为错误目标不会被高质量代码自动修正。一个功能可以编译通过、测试全绿、命名优雅，最后仍然没有解决真实问题。那种感觉像精心造了一把钥匙，做工无可挑剔，只是附近没有对应的门。

## 需求不是命令，而是需要验证的假设

用户提出的通常是“希望系统发生什么”，有时也会同时给出一个具体解法：

> “增加一个 Elasticsearch 服务，让搜索更快。”

其中真正需要确认的可能是：当前搜索在目标数据规模下太慢。Elasticsearch 是一种候选方案，不一定是需求本身。如果数据库已有合适索引，或者现有搜索服务只缺正确配置，直接引入新服务会让一个性能问题获得一整套新的部署、监控和维护问题作为朋友。

V-Team 因此会区分：

- **真实问题**：用户或系统正在遭遇什么；
- **目标结果**：完成后应该观察到什么；
- **用户解法**：用户建议怎样实现；
- **技术约束**：项目必须遵守什么；
- **非目标**：本次明确不处理什么。

## 先发现已有能力

需求评判从项目事实开始，而不是从互联网开始。

默认顺序是：

1. 搜索项目中是否已有相同或相近功能；
2. 检查现有模块、接口、组件、测试和工程约定；
3. 查看当前可用 Skills 是否能够直接帮助处理任务；
4. 只有信息易变、技术陌生或风险较高时，才查询官方资料；
5. 证据已经足够支持决策时停止搜索。

这种顺序有两个好处。第一，项目自己的约定比“互联网上最流行的做法”更接近当前答案；第二，研究具有退出条件，不会从“查一下 API”发展成“顺便比较过去五年的整个生态”。

## Skills 搜索怎样保持克制

V-Team 不会把所有已安装 Skills 全文加载一遍。它先读取名称和描述，只在确认相关后加载对应正文。

例如：

- 设计 Web 页面时，UI/UX Skill 可能直接提供设计规范；
- 创建架构图时，Archify 可以生成可验证的视觉资产；
- 操作 PDF、表格或演示文稿时，专用 Skill 比临时脚本更可靠；
- 普通后端条件判断则不必为了显得工具丰富，先召集半个技能市场。

若需要安装外部 Skill 或插件，必须先说明来源、用途和影响，并取得开发者许可。

## 什么时候需要网页研究

以下情况适合查询网页：

- 依赖、框架、API 或规范可能已更新；
- 存在不熟悉或新兴技术；
- 需要比较真实架构方案；
- 涉及安全、权限、兼容、数据或迁移；
- 用户明确要求搜索或验证；
- 本地证据不足以支持技术决策。

网页研究优先使用官方文档、正式规范和原始资料。它的任务是回答当前决策，而不是证明浏览器确实可以打开很多标签页。

## 需求审判的六个维度

| 维度 | 需要回答的问题 | 通过标志 |
| --- | --- | --- |
| 问题 | 谁在什么场景遇到了什么困难 | 问题可以被复述和观察 |
| 价值 | 不解决会有什么影响 | 收益与投入匹配 |
| 必要性 | 是否已有配置、复用或更小方案 | 新开发确有必要 |
| 可行性 | 技术、环境、权限和依赖是否允许 | 没有致命阻塞 |
| 范围 | 做什么，以及明确不做什么 | 任务可以独立交付 |
| 验收 | 怎样知道功能已经完成 | 结果可以验证 |

只有这些条件足够清楚，需求才进入技术设计。

## 审判不只有 Pass

V-Team 支持六种需求结论。

### Pass

问题、价值、范围、可行性和验收条件都已明确，可以进入技术与架构方案。

### Reuse

已有能力已经满足，或只需配置和轻量连接。没有新增代码并不意味着没有完成工作；有时最专业的实现，就是让现有代码继续安静地发挥作用。

### Narrow

需求方向正确，但范围超过单任务边界。V-Team 会将它缩小为可以独立验证、独立交付和独立回滚的能力。

例如，“重做整个后台权限系统”可以先收敛为“为订单导出复用现有角色权限，并补齐接口与页面的无权限状态”。

### Reject

需求价值不足、风险明显高于收益，或者与项目方向冲突。Reject 必须提供事实依据和更合理建议，不是一句略显高冷的“这个不行”。

### Decision Required

存在会实质改变结果的产品选择，例如数据保留期限、兼容范围或交互行为。V-Team 只提出这个关键决策，不把一整页问题清单原样退回。

### Blocked

缺少必要权限、环境、数据或外部依赖。Blocked 会说明已经检查的内容、当前缺口和条件恢复后的继续位置。

## 验收条件应该描述结果

“实现一个更好用的搜索”不能直接验收。更清楚的表达是：

- 用户输入关键词后只看到有权限访问的结果；
- 空结果显示明确提示，而不是一片具有哲学意味的空白；
- 网络失败时保留关键词并允许重试；
- 重复提交不会制造多个并发请求；
- 现有分页和筛选保持兼容；
- 在目标数据规模下达到约定响应时间。

验收条件描述结果，技术方案决定实现。两者分开后，架构可以比较真实选择，而不是被一句提前指定的技术名词锁死。

## 从价值和风险判断投入

V-Team 不会因为需求风险低就默认实现，也不会因为风险高就默认拒绝。

| 价值 | 风险 | 推荐处理 |
| --- | --- | --- |
| 高 | 低 | 快速完成并直接验证 |
| 高 | 高 | 深入设计后推进 |
| 低 | 低 | 优先复用、缩小或停止 |
| 低 | 高 | 通常拒绝，除非存在新的关键事实 |

例如，修正一条会误导用户付款的文案，风险低但价值高，应快速处理。为了“技术栈更新鲜”而重写稳定模块，风险高且价值不明，理应先接受需求审判，而不是先给新框架准备欢迎横幅。

## 需求阶段输出什么

标准和重大任务会形成一份紧凑结论：

1. 使用者、场景与真实问题；
2. 价值和必要性；
3. 本地复用、Skills 与外部研究结论；
4. 目标与非目标；
5. 可观察验收条件；
6. 风险、假设和阻塞；
7. 最终审判结果。

普通任务不会自动生成 PRD 文件。只有开发者明确要求留档，或项目已有正式产品文档需要维护时，才把结论写入项目。

## 需求能力的真正价值

需求分析并不是延迟写代码，而是在最便宜的阶段发现错误方向。设计阶段修改一句目标，通常只需要几分钟；实现完成后发现目标错了，往往还会附赠迁移、兼容和回滚。

V-Team 让 coding agent 不仅能够回答“怎样实现”，也能够负责地回答：

- 为什么应该实现；
- 为什么不应该实现；
- 为什么应该缩小；
- 为什么已有能力已经足够；
- 什么条件满足后才能继续。

这使开发从“收到指令就生产代码”变成“使用证据完成一次工程判断”。
