很多 Agent 工作流的问题，不是能力不够，而是启动方式错误：一个只需要解释的提问被误认为开发任务；一个局部、低风险的修复被拖进完整项目流程；一个涉及公共接口的改动却被当成普通文件编辑；一个已经有明确方向的恢复任务，又被迫从需求分析重新走一遍。V-Team 的第一项价值，就是在真正动手之前先回答“我们现在究竟处于哪一种工作状态”。

这不是为了增加一道形式上的分流，而是为了保护交付目标。操作模式决定是否允许修改代码、是否需要读取 reference、是否需要持久化状态；风险等级决定是否需要一次方案确认、是否应该扩大验证范围；当前角色决定本阶段应该吸收哪一种专业规则。三者被拆开后，流程就不会因为任务表面上“看起来复杂”而自动膨胀，也不会因为任务表面上“只是改一行”而忽略公共契约、数据、安全或兼容性风险。

## 从用户意图到可观察结果

V-Team 期待的需求不是一句“把这个做好”，而是一组可以被解释和验证的事实：谁在什么场景下遇到什么问题，现有能力能否复用，目标是什么，不做什么，成功后用户或系统能观察到什么。`references/role-requirement.md` 把这件事压缩成五步：区分真实问题和用户提出的解法，明确使用者与影响，检查复用可能，收敛目标边界，把成功写成可测试的验收条件。

这让需求阶段拥有一种被夸大的确定性。理想情况下，Agent 不会因为用户说“帮我加一个页面”就直接开始写页面，而会先识别真正的目标可能是“让用户完成一次可追踪的配置”；也不会在已有能力已经满足需求时，为了制造存在感而生成新模块。它可以选择不开发，可以选择小改，可以选择新建，但只有在存在真实价值和真实差异时，才把任务升级为功能交付。

换句话说，V-Team 把“停止”也纳入需求能力：如果现有系统已经满足验收条件，最专业的结论可能不是再写一段代码，而是明确指出无需扩展。这种判断在理想状态下会直接减少返工、减少无效上下文、减少为了追求“有改动”而引入的复杂度。

## 五种模式：同一个 Agent，也可以拥有不同的工作姿态

当前 `SKILL.md` 将工作分成五种模式，并明确每一种模式的边界。

### 回答

回答模式用于解释、理解和状态查询。它不改代码，不读角色 reference，不建立 ID，也不写状态。它的意义在于把知识性交付和产品变更切开：用户只是想知道某个命令做什么，就不应该触发一轮实现流程；用户只是想比较两个方案，就不应该在确认前改变项目状态。

### 评估 / 设计

评估或设计模式只读取必要的角色参考，在对话中交付需求、UI、架构或技术方案，然后停止。它不会把尚未确认的设计伪装成实现，也不会为每一次分析自动生成 PRD、设计稿或 PLAN 文件。理想情况下，用户可以在低成本地比较方向、识别风险，然后再决定是否进入实现阶段。

### 实现

实现模式面向真实的用户能力、行为或 UI 流程。若任务属于标准或重大风险，Agent 先给出紧凑决策摘要：问题与价值、目标与非目标、验收条件、推荐方案、关键风险、相关契约或迁移，以及最小角色链路。用户确认一次后，Agent 连续完成，不按角色或小步骤反复请示。这个“一次确认，连续执行”的设计，让方案确认真正成为方向校准，而不是把用户变成每一步的人工审批器。

### 修复

修复模式先走最短路径稳定复现，再检查日志、堆栈、输入输出和最近变化，沿数据流定位根因；一次只验证一个假设，优先做最小根因修复。连续三次假设失败，或者问题开始影响公共契约、数据、安全、兼容和架构时，才升级到更高等级的实现流程。理想情况下，调试不会被包装成一份冗长报告，但也不会变成无证据的试错堆叠。

### 恢复

恢复模式是 V-Team 最有“接力感”的一部分。已有 capability 状态时，下一次会话只读取当前角色、当前 capability、相关契约和 active 的下一步；方案没有实质变化，就不重新分析、不重复确认、不重走已经完成的角色。它把“我记得上次做到哪里了”从个人记忆升级成机器可读取的当前事实。

## 三档风险：让流程和影响面匹配

V-Team 不是把所有任务都按重大项目处理，而是用风险等级控制流程深度。

| 风险等级 | 适用条件 | 理想交付动作 |
| --- | --- | --- |
| 快速 | 结果明确、局部、易回滚，不改变公共 API、Schema、数据、权限、安全或架构 | 直接完成，只做直接结果验证，不读取多余 reference，不等待方案确认 |
| 标准 | 新增用户能力、行为或 UI 流程，或存在真实产品/技术取舍 | 先给一次决策摘要，确认后连续实现，验证关键主流程或直接受影响测试 |
| 重大 | 跨核心模块、破坏性协议、数据迁移、安全边界、核心架构或难回滚变化 | 走标准确认流程，按实际影响扩大架构、契约、迁移、回滚和测试说明，必要时维护恢复或里程碑状态 |

真正先进的地方在于：它不是根据文件数量判断风险，而是根据影响面判断风险。改十个局部文件可能仍然快速，改一个公共 Schema 也可能必须升级为重大。这样的判断让“流程轻重”与“用户真正承担的风险”对齐，避免用机械规则替代工程判断。

## 角色参考不是全量手册，而是按需加载的专业镜头

当前仓库提供需求、架构、后端、前端和 QA 五类角色参考，另有契约、调试和里程碑策略。`SKILL.md` 明确要求“不要预读所有角色”，只有进入阶段前才读取一个必要参考：需求不清才读需求角色，有边界或公共协议决策才读架构角色，开始后端实现才读后端角色，进入 UI 与真实联调才读前端角色，高风险或跨角色闭环需要独立验收才读 QA 角色。

这套设计带来的便利远不止节省几个 token。它让每一种角色都保持清晰的注意力边界：后端角色关注业务规则、权限、幂等、事务和契约；前端角色关注用户路径、加载/空/错误/无权限/网络异常/重复提交，以及真实契约集成；QA 角色关注验收条件、环境、数据、权限、契约版本和高风险场景。理想情况下，Agent 不会用一份巨大的通用清单掩盖关键问题，而会在当前阶段戴上最合适的专业镜头。

## 需求验收：从“想做”变成“看得见”

一项需求进入实现前，推荐至少能回答以下问题：

- 使用者是谁，触发场景是什么，发生频率和影响是什么？
- 目标是解决真实问题，还是只是实现用户提出的某个具体解法？
- 当前项目、现有组件、已有契约或已有状态能否直接复用？
- 本次要实现的行为是什么，明确不做的范围是什么？
- 成功结果由谁观察，应该通过什么测试、状态或证据确认？
- 如果跨角色，capability、provider、consumer、contract ID 和权威 `source_ref` 分别是什么？
- 如果中途暂停，下一步是否能被另一个会话直接执行？

理想状态下，这些问题会把需求从“我要一个功能”引导到“我们要让某个能力在某个边界内稳定完成，并且可以证明它完成了”。一旦目标具有这种形状，后面的系统设计和实现就不再是在黑暗中堆代码，而是在一条已经标记过风险、角色和验收点的路径上推进。

## 需求章节的结论

V-Team 的需求能力可以浓缩成一句话：先把问题说清楚，再决定需要多少流程；先把成功定义出来，再决定需要多少代码。它把 Agent 的聪明从“能生成很多东西”提升为“知道什么时候不该生成，知道什么时候必须停下来确认，知道什么时候可以一路执行到底”。在理想状态下，项目团队得到的不只是更快的实现，而是更少的误启动、更少的重复确认、更少的隐性取舍和更高密度的有效上下文。
