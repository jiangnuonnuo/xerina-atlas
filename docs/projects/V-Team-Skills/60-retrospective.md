V-Team 的价值不在于步骤比别人多，而在于每一步都有触发条件、退出条件和事实边界。它希望 coding agent 像一位可靠的开发搭档：动手快，但不会快到忘记为什么动手；重视质量，但不会为三行修改举办九轮评审。

## 原则一：显式启用

V-Team 只在开发者明确调用 `$v-team` 时启用。

这是一个重要的授权边界。需求审判、架构评判、状态写入和跨角色契约都可能改变任务的处理方式，不应该在普通问答中悄悄发生。

显式启用带来三个结果：

- 使用者知道本次工作采用完整的功能交付语义；
- 解释与状态查询仍然保持只读；
- 普通小任务不会无故背上额外流程成本。

好的自动化应该让人清楚它何时出现，而不是像办公室里突然新增的审批表，所有人都不知道是谁创建的，但每个人都得填。

## 原则二：先判断，再加速

coding agent 最显著的优势是执行速度，最容易被忽略的风险也是执行速度。方向错误时，产出越快，返工到达得越准时。

V-Team 在实现前检查：

- 真实问题和使用场景；
- 价值与必要性；
- 现有能力是否可以复用；
- 范围是否适合作为一次独立交付；
- 验收是否可观察；
- 方案是否能落到当前项目。

需求可以 Pass，也可以 Reuse、Narrow、Reject 或 Blocked。允许不开发，是开发技能成熟的重要标志。

## 原则三：流程重量由风险决定

V-Team 不使用“任务看起来很大”作为唯一判断。真正决定流程深度的是变化影响：

- 是否改变公共契约；
- 是否修改数据和权限；
- 是否触及安全边界；
- 是否引入迁移或兼容问题；
- 是否难以回滚；
- 是否需要多个消费者协调。

因此，跨十个局部文件的机械修改可能仍是快速任务，而一行权限判断的语义变化可能属于重大风险。文件数量只能说明手指可能会有点忙，不能独立说明工程风险。

## 原则四：渐进加载

V-Team 把入口路由与角色规则分离。需求、架构、后端、前端、QA、契约、调试和里程碑策略都存在，但只在相关阶段读取。

渐进加载避免两类浪费：

- 上下文浪费：任务尚未需要的规则提前占用注意力；
- 过程浪费：因为已经加载了某套规则，就下意识把它全部执行一遍。

完整能力不等于全量启动。消防车需要配齐设备，但不必每次出门都把所有水管铺在街上。

## 原则五：角色表示责任，不强制多 Agent

Requirement、Architect、Backend、Frontend 和 QA 是不同责任视角。V-Team 允许同一个 Agent 连续切换这些角色，更适合个人开发者和单任务交付。

这样既保留专业分工，又避免为简单功能制造协调成本。只有真正的跨角色事实需要稳定交接时，才使用契约索引；只有任务跨会话时，才保存恢复状态。

V-Team 因此不是多 Agent 编排器，也不依赖虚拟团队规模来证明专业程度。一个人能把事情想完整，就不必为了流程图热闹，先安排五个人互相写交接邮件。

## 原则六：项目事实只有一个权威来源

V-Team 不把 OpenAPI、Schema、共享类型或测试正文复制进 `.vteam/state.json`。状态只记录来源、角色、生命周期和证据。

这解决了常见的“双重真相”问题：

- 接口字段在 OpenAPI 中更新，状态里的副本却没更新；
- 前端按旧副本实现，后端按新契约发布；
- 两边都能指出一份文件证明自己没错；
- 联调现场充满了事实，唯独缺少同一个事实。

索引指向权威来源，既减少维护，也让冲突能够被准确定位。

## 原则七：完成必须有证据

V-Team 区分“已经实现”和“已经证明”。

提供者把契约标记为 `ready` 时，需要直接验证证据；消费者完成真实联调后，可以标记为 `verified`；模块完成时，也必须提供至少一条非空证据。

证据可以是：

- 直接受影响的自动化测试；
- 构建、类型检查或静态分析结果；
- API 调用与响应；
- 页面主流程验收；
- Bug 的同路径复验；
- 数据迁移演练或回滚验证。

证据必须是实际执行结果。“理论上没问题”是一种情绪稳定的预测，不是一条完成记录。

## 原则八：最小充分验证

V-Team 不默认运行全量测试，不要求每个角色重复验收，也不自动生成测试报告。验证范围来自验收条件和影响分析。

这种克制并不降低质量，反而迫使验证与结论建立直接关系：

- 快速任务验证直接结果；
- 标准功能验证关键主流程；
- 重大变更扩大到实际兼容、数据、安全和回滚边界；
- 修复使用相同复现路径验证前后变化。

全量测试在有必要时当然可以运行，但“有必要”需要依据。厨房换了一个灯泡，不必因此检查整栋楼的消防喷淋；如果换的是燃气阀门，事情就完全不同。

## 原则九：失败回到真正出错的位置

V-Team 的闭环不是“失败后全部重来”。

- 价值错了，回需求；
- 方案错了，回设计；
- 实现偏了，修代码；
- 证据不足，补验证；
- 新事实改变了架构，再重新评判方案。

精确回退能保留已经成立的判断，减少重复分析，也让修复动作更接近根因。

## 原则十：状态服务于恢复，不服务于收藏

普通功能不创建 V-Team 文件。需要恢复时，每个 capability 只保留一条当前 active；完成后清除 active，并以完成事实覆盖当前状态。

重大里程碑也只保存摘要和项目引用，不复制正文、不自动累计所有历史对话。

状态越多不代表项目越可控。有时它只代表项目擅长记录自己尚未完成。V-Team 更关心能否准确继续，以及完成后能否干净退出。

## 从个人开发实践中持续生长

V-Team 由个人开发者在日常项目中持续使用和维护。它吸收的不是想象中的完美流程，而是真实开发里反复出现的问题：

- 需求已经有现成功能，却又实现了一遍；
- 技术方案听起来先进，却无法落到当前模块；
- 前后端在不同会话里猜测接口；
- 为保证质量启动过多测试，周期和 token 消耗失控；
- 任务恢复时重新阅读大量历史，仍然找不到接续点；
- 代码完成后只报告“应该可以”，没有直接证据。

这些经验被沉淀为路由条件、角色规则、CLI 约束和自动化测试。个人维护并不意味着随意；恰恰因为作者自己长期使用，每一条新增规则都必须回答：它解决了什么真实问题，会增加多少成本，什么时候不应该触发。

## 完善程度评估

从单任务功能交付的定位看，V-Team 已经形成完整闭环，不是只有提示词框架而缺少落地机制。

| 能力面 | 完善程度 | 判断依据 |
| --- | --- | --- |
| 模式与风险路由 | 完整 | 五种操作模式、三档风险和升级条件均有明确语义 |
| 需求评判 | 完整 | 覆盖发现、价值、必要性、范围、验收与六类结论 |
| 技术与架构设计 | 完整 | 覆盖模块、契约、数据、安全、迁移、回滚和门禁 |
| 代码实施约束 | 完整 | 按角色渐进加载，实现必须贴合已通过方案 |
| 功能与质量验收 | 完整 | 功能、架构、代码质量三层检查，支持精确回退 |
| 跨角色契约 | 工程化 | 具备发布、发现、验证、停用和直接证据约束 |
| 跨会话恢复 | 工程化 | 单条 active、完成清理和里程碑渐进读取均已实现 |
| 自动化验证 | 充分 | 33 个测试场景覆盖主要行为、边界和策略一致性 |
| Git、CI 与部署 | 明确边界 | 由用户授权和项目规则决定，不属于默认职责 |

综合来看，V-Team 适合稳定承担个人开发者的功能评估、方案设计、代码实现、轻量验收和恢复工作。它没有尝试成为通用项目管理平台，也没有自动接管仓库治理；这些边界不是功能缺口，而是控制授权、周期和 token 成本的重要设计。

完善程度并不只看“能做多少”，还要看“会不会在不该做时停下来”。V-Team 的路由条件、状态触发条件和验证退出条件，与角色规则和 CLI 能力同样重要。

## 开源与分支

- 项目地址：[github.com/jiangnuonnuo/V-Team-SKILL](https://github.com/jiangnuonnuo/V-Team-SKILL/tree/develop)
- `develop`：持续开发与日常验证分支；
- `main`：稳定版本分支。

开源让流程设计可以被阅读、质疑和改进。适合参与的改动包括：

- 有真实案例支持的需求或架构判断；
- 能减少重复劳动的角色规则；
- 契约与恢复机制的边界修正；
- 能复现问题并锁住行为的测试；
- 更准确、更易读的使用文档。

新增流程最好同时说明不适用条件。只描述“什么时候运行”的规则很容易越长越胖；写清“什么时候停止”，它才可能长期保持健康。

## V-Team 不追求什么

它不追求：

- 把每个功能都扩写成完整 PRD；
- 用角色数量衡量任务专业度；
- 为普通改动创建 capability 和状态；
- 取代项目已有的契约、架构或测试体系；
- 默认接管 Git、CI、PR 与部署；
- 通过大量重复测试换取心理安全感；
- 为未来可能发生的问题预建所有抽象。

这些“不做”构成了 V-Team 的边界，也保护了它最核心的价值：让 coding agent 更可靠地进入真实功能开发，而不是把开发过程本身变成主要产品。

## 如何判断 V-Team 是否发挥了作用

一次使用结束后，可以从几个可观察结果判断：

- 需求是否被证明值得做，或被合理复用、缩小和拒绝；
- 方案是否明确指向项目中的模块、契约和数据流；
- 实现是否贴合通过的方案；
- 验收是否使用了直接、充分且不过量的证据；
- 跨角色时是否没有猜测接口；
- 跨会话时是否能够从最小状态继续；
- 完成后是否没有遗留无价值的流程文件。

如果这些结果成立，V-Team 就完成了它的工作：把一个想法变成经过判断、能够落地、可以验证的功能，同时让开发周期仍然像一个周期，而不是一个季节。
