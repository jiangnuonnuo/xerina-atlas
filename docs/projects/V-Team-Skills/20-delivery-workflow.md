V-Team 的工作流围绕一个问题展开：怎样让一次功能从“听起来不错”，走到“确实可用”，同时不把个人开发变成流程管理职业体验卡。

它采用有条件的完整闭环。快速修改走短路，标准功能确认一次，重大变更补足契约、迁移与回滚。门禁存在的意义是挡住错误，不是收集印章。

## 第一步不是写代码，而是识别操作模式

同一句“帮我看看登录功能”，可能是在问原理、做方案、实现功能，也可能是在排查线上异常。V-Team 先识别任务要产生什么结果，再决定读取哪些规则和是否修改项目。

| 模式 | 适用请求 | 允许的动作 | 结束条件 |
| --- | --- | --- | --- |
| 回答 | 解释、理解、查询状态 | 只读检查与说明 | 问题被准确回答 |
| 评估/设计 | 需求判断、UI 或技术方案 | 调研与设计，不改代码 | 交付可决策的结论 |
| 实现 | 新增或修改功能 | 分析、设计、编码、验证 | 功能闭环且证据充分 |
| 修复 | Bug、异常、测试失败 | 复现、定位、最小修复、回归 | 原路径恢复正确 |
| 恢复 | 继续跨会话工作 | 读取最小状态，接续记录位置 | 重新进入有效执行链路 |

模式之间有明确边界。评估请求不会顺手提交代码，修复请求若发现公共协议或数据模型必须改变，则升级为实现模式。这样既防止“只想问问，结果仓库长出了三个文件”，也防止把架构变化错误归类为小修小补。

## 风险分级决定流程重量

### 快速：局部、明确、容易回滚

快速任务不改变公共 API、Schema、持久化数据、权限、安全边界或核心架构。它可以直接实现，只验证受影响结果，不创建状态，也不要求方案确认。

典型例子包括：

- 修正局部文案或样式；
- 补充明确的空值处理；
- 调整现有配置的默认值；
- 修复影响范围清楚的条件判断；
- 在已有模式中增加一个简单映射。

### 标准：产生新的用户能力或真实取舍

标准功能需要一份紧凑摘要，包含价值、范围、验收、方案和风险。只有存在实质选择时才请求一次确认，批准后连续完成实现与验收。

例如“订单列表支持按当前筛选导出 CSV”通常属于标准功能：它增加用户能力，涉及筛选参数复用、下载行为、权限和错误反馈，但不一定需要引入新的系统边界。

### 重大：改变公共事实或难以回滚

以下变化通常属于重大任务：

- 破坏性 API 或 Schema 变更；
- 数据迁移、批量修复或不可逆写入；
- 权限模型、安全边界或敏感信息处理变化；
- 核心模块拆分、关键依赖替换；
- 多个消费者需要协调升级；
- 失败后恢复成本较高。

重大并不等于“把所有测试都跑一遍”。它意味着对真实影响进行更完整的设计、兼容、验证和回滚，而不是用仪式感替代判断。

## 发现：先检查家里有没有，再考虑下单

进入需求评判前，V-Team 先执行最小发现：

1. 搜索现有代码、组件、接口、配置和测试；
2. 识别项目正在使用的架构模式与工程约定；
3. 检查可用 Skills 是否有专门能力；
4. 在信息易变、技术陌生或风险较高时查询官方资料；
5. 找到足够证据后停止搜索。

发现阶段的产物不是“我看了很多”，而是“哪些可以复用、哪些约束必须遵守、哪些未知会改变决策”。浏览二十篇文章却没检查项目里已有的 `exportOrders()`，属于一种知识丰富的重复劳动。

## 需求门禁：允许不开发

需求门禁检查问题、价值、必要性、可行性、范围与验收。它可以得到 Pass、Reuse、Narrow、Reject、Decision Required 或 Blocked，而不是把所有输入都翻译成待办代码。

通过门禁至少意味着：

- 真实问题已经明确；
- 新开发相对于复用确有价值；
- 本次边界可以独立交付；
- 主要技术条件可满足；
- 验收结果能够被观察。

如果这些条件不成立，继续设计只会让模糊需求拥有更加精致的结构图。

## 技术落地：方案必须能指向真实代码

技术方案不是技术名词展览。V-Team 要求方案回答：

- 修改哪些现有模块，为什么由它们负责；
- 是否新增边界，新增边界解决什么问题；
- 请求、数据和状态怎样流动；
- 公共契约在哪里定义；
- 错误、权限、并发和幂等怎样处理；
- 如何兼容、迁移和回滚；
- 每条验收条件由什么证据证明。

方案应复用项目现有模式。若项目使用 service + repository，就不应为了一个导出功能临时引入一套微型六边形宇宙；若现有边界已经失效，也不能因为“保持一致”继续复制错误。V-Team 追求的是有根据的一致，而不是整齐地犯同一种错。

## 架构门禁：检查方案，而不是欣赏方案

技术方案进入实现前，需要通过四类检查：

| 检查 | 核心问题 |
| --- | --- |
| 完整性 | 是否覆盖目标、非目标、异常和验收 |
| 一致性 | 是否符合项目边界、依赖方向和事实来源 |
| 可交付性 | 是否能够分解为连续实现步骤 |
| 风险性 | 是否明确兼容、数据、安全、迁移和回滚 |

不通过时只修正方案，不提前写实现来“验证灵感”。原型确有必要时，应把它明确为探索性代码，并约定是否保留。

## 实现：代码服从已通过的方案

进入实现后，V-Team 按真实依赖顺序工作。例如一项前后端功能可能是：

1. 定义或确认共享契约；
2. 实现后端业务与接口；
3. 取得提供者直接验证证据；
4. 前端发现并消费可集成契约；
5. 完成交互、错误状态和联调；
6. 验证用户主流程。

实现阶段允许处理局部工程细节，但如果出现新的产品选择、实质方案变化或无法消除的阻塞，必须回到对应门禁。不能一边说“方案没变”，一边把 REST 改成事件驱动，再把它归为命名风格比较活泼。

## 验收：分成三个镜头看结果

### 功能验收

按照可观察验收条件验证主流程、关键错误路径和必要边界。重点是用户或调用者实际得到的结果。

### 架构评估

检查实现是否落在约定模块、依赖方向是否正确、公共契约是否可定位，以及是否出现未经批准的新耦合。

### 代码质量评估

检查可读性、错误处理、类型与数据边界、重复、测试价值和安全风险。质量评估不追求抽象数量；能用一个清楚函数解决的问题，不必先成立一个框架委员会。

## 失败如何精确回退

V-Team 不把所有失败都送回需求分析。

| 失败表现 | 回退位置 | 处理方式 |
| --- | --- | --- |
| 需求价值或范围不成立 | 需求评判 | 重写目标、缩小或停止 |
| 方案无法满足验收 | 技术设计 | 修正模块、契约或数据流 |
| 代码偏离已通过方案 | 实现 | 恢复架构一致性 |
| 功能结果错误 | 实现/修复 | 沿失败路径定位根因 |
| 架构约束本身错误 | 技术设计 | 修正方案后再改代码 |
| 证据不足 | 验收 | 补充最小直接验证 |

回退的原则是修正最早出现错误的事实。否则一个按钮颜色测试失败，也可能被隆重地送回需求访谈，大家都很忙，按钮依然是错的。

## 跨会话恢复：只带必要行李

只有任务确实需要跨会话继续时，V-Team 才保存一条 active 记录：当前 capability、角色、摘要、下一动作、阻塞和必要引用。恢复时读取当前事实，不重放整个对话，也不重新分析已经通过的部分。

模块闭环后 active 被清除，完成事实覆盖当前 capability 状态。恢复机制服务于继续工作，不负责收藏历史。

## 一次高质量交付应留下什么

最终结果应当清楚说明：

- 实际完成了什么；
- 需求与方案中的关键判断；
- 修改了哪些主要模块；
- 执行了哪些验证，结果如何；
- 仍有哪些未覆盖风险；
- 若涉及契约，契约来源与状态在哪里；
- 若存在阻塞，恢复条件和接续位置是什么。

这套工作流的价值，不在于每次走完同样数量的步骤，而在于每次都用足够的判断和证据，把功能交到真正完成的位置。
