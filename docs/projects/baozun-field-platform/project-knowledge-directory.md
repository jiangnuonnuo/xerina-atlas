## 字段目录平台项目技术总纲

字段目录平台把业务后台中的菜单、页面、页签、区块、表单字段、表格列和指标定义，沉淀为具有统一身份、层级关系、来源证据和版本记录的目录资产。

平台从页面采集字段证据，通过确定性规则和受限 Agent 生成候选字段树，在交互工作台中完成预览、修订和审核，再通过事务化变化集写入正式目录。目录可被分层查询、持续维护，并通过一致性快照和异步任务交付为字段字典。

整个项目关注的不是单点页面功能，而是下面这条全栈技术链路：

![字段目录平台全链路](./assets/platform-lifecycle.svg)

## 1. 全栈职责与系统边界

### 1.1 全栈职责

项目工作横跨页面交互、服务端业务、数据存储和智能化编排：

- **采集端**：人工框选、DOM-first 自动扫描、页面状态探索、证据预览与补采；
- **平台前端**：目录树懒加载、批量录入、拖拽移动、候选树审核、任务进度和文件下载；
- **应用后端**：采集任务、解析任务、目录命令、目录查询、变化发布和导出任务；
- **领域模型**：字段证据、候选树、目录不变量、变化集和任务状态机；
- **数据与文件**：MySQL 目录数据、闭包关系、SQLite 导出快照、XLSX 和本地/对象存储；
- **Agent 工程**：规则路由、Prompt 组装、白名单工具、结构校验、人工反馈和评估；
- **工程化**：认证、OpenAPI、SSE、测试、Nginx、部署、日志、安全和容量保护。

### 1.2 系统边界

平台负责字段从“页面痕迹”到“目录资产”和“字典产物”的完整生命周期，但不修改被采集系统的业务逻辑，也不定义下游数据仓库的指标计算公式。

## 2. 总体技术架构

### 2.1 业务处理架构

![字段平台业务处理架构](./assets/processing-architecture.svg)

### 2.2 工程分层

![模块化单体与端口适配分层](./assets/layered-architecture.svg)

采用模块化单体和端口适配结构，确保领域规则不依赖浏览器驱动、模型 SDK、MyBatis 或文件系统。外部技术可以替换，目录不变量、变化发布和任务状态不随之改变。

### 2.3 关键设计原则

1. 页面内容只作为不可信数据，先转换为结构化证据；
2. DOM 强规则优先，模型只处理规则无法确定的局部歧义；
3. Agent 只能调用白名单领域工具，不能直接写正式目录；
4. 模型输出先形成候选树，再经过结构校验和人工审核；
5. 正式修改以带基线版本的变化集为单位事务提交；
6. 目录树同时维护直接父子关系和可重建闭包索引；
7. 大数据量字典从一致性快照异步、流式生成；
8. 采集、解析、审核、发布和导出都保留可回放状态。

## 3. 关键方案演进

### 3.1 录入方式：逐节点操作 → 自适应缩进 → DOM-first

逐节点录入准确但效率低；缩进文本可以快速建立多层目录，但仍需要人工整理输入；DOM-first 直接读取页面的结构与语义痕迹，把人工工作收敛到异常补采和结果审核。

确定性缩进解析保留下来，作为输入归一和层级推断的基础能力，而不是被 Agent 替代。

### 3.2 层级解析：固定模板 → 全量模型 → 规则优先的受限 Agent

固定模板难以覆盖不同组件库和动态页面；全量模型解析容易受到 HTML 噪声、上下文长度和提示注入影响。最终采用规则优先、局部模型推断、领域校验和人工审核的组合方式。

Agent 的作用是编排证据加载、规则抽取、局部推断、结构校验和反馈重算，而不是自由浏览和自由写库。

### 3.3 目录写入：逐节点执行 → Candidate Tree → Change Set

逐节点写入会把解析过程中的中间状态暴露给正式目录。Candidate Tree 用于承载完整候选结构，Change Set 用于表达相对现有目录的新增、改名、移动和删除。

变化集携带基线 `tree_version`，发布前重新校验，避免审核期间的人工修改被覆盖。

### 3.4 数据交付：同步响应 → 异步任务 → 可恢复工作区

同步导出会占用 HTTP 线程、数据库连接和 JVM 内存。异步任务把源数据快照、清洗映射、XLSX 生成、文件提交和下载解耦；SQLite 快照与阶段检查点让本地处理可以恢复，并提前释放 MySQL 长事务连接。
