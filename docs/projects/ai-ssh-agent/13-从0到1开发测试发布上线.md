## 我要给新开发者一条可复现路径

这个项目不是只启动一个 Spring Boot 进程就算完成。开发者至少要同时理解 Maven 多模块、MySQL、Redis、模型 API、Agent YAML、SSH 测试目标和可选 Docker Sandbox。我的建议是先跑通“应用启动 → Agent 注册 → 连接配置 → 主机信任 → 短命令 → 长命令 → 文件和 Sandbox”的最小闭环，再扩展模型或动态工具。

![从开发到运行时的系统边界](./assets/architecture/architecture.gif)

图要回答的问题：代码、配置和外部依赖怎样汇聚成可运行的 Agent SSH 服务。关键节点是 Maven 模块、Spring Boot 配置、Agent 装配、MySQL/Redis、SSH 目标和可选 Docker；失败分支包括配置解析失败、模型不可用、数据库或 Redis 不健康、主机未信任和 Sandbox 能力不足。一致性边界在持久配置与运行时资源之间，隔离边界在本地开发工具、目标 SSH 主机和目标主机上的 Sandbox 之间。

## 第一步：准备依赖和配置

项目使用 Java 17，根工程由 Spring Boot 3.4.3 管理，构建工具是 Maven。运行开发 profile 至少需要：

- MySQL 8，数据库名 walissh，执行 docs/dev-ops/mysql/init/01-schema.sql 初始化空库。
- Redis 7，开发配置默认连接本机 6379；密码、数据库和超时时间由 application-dev.yml 提供或覆盖。
- 一个 OpenAI 兼容的模型 API。Agent 配置和意图识别配置分别提供 Base URL、API Key 和模型名，密钥不应提交到公开文档、镜像或日志。
- 若要验证隔离执行，还需要目标 SSH 主机已安装 Docker，并允许 SSH 用户执行 Docker 相关命令。

开发配置通过 spring.config.import 引入 Agent YAML。当前 dev 默认导入 code-agent.yml 和个人知识 Agent 配置；其他 Agent 配置可以切换导入，但多个配置必须保证 Agent 名称、工具策略和模型配置不冲突。

## 第二步：构建模块

常规构建从根目录执行：

    mvn -pl walicode-server-app -am package

本地开发时，默认保留 application-dev.yml。部署构建使用 docker profile 排除开发配置，避免本机密码和 API Key 进入部署 Jar：

    mvn -Pdocker -pl walicode-server-app -am clean package -DskipTests

应用模块默认把 app.tests.skip 设为 true，需要显式执行应用层测试时打开：

    mvn -pl walicode-server-app -am test -Dapp.tests.skip=false

领域、Case、基础设施模块的测试由各模块 Surefire/JUnit 配置负责。当前工作环境缺少可用 mvn 命令，因此我不能把本地未执行的构建写成通过；发布前仍需在具备 Maven 和依赖仓库访问能力的环境执行完整命令。

## 第三步：确认 Agent 装配

启动应用后，应用就绪阶段读取 Agent 配置，并装配 AI API、Chat Model、Agent、Workflow 和 Runner。开发者先调用 Agent 配置列表，确认目标 Agent 已注册，再检查日志中工具注册数量和模型初始化结果。

装配失败的处理顺序是：先检查 YAML 层级和导入路径，再检查模型 URL、Key 和模型名，最后检查内置工具与动态工具是否重名、白名单是否引用了未加载工具。工具说明里的安全约束只帮助模型做选择，真正的拒绝仍来自执行策略、连接检查和文件规则。

## 第四步：跑通 SSH 最小闭环

我会按以下顺序联调，所有目标都使用明确的 connectionId：

1. 创建连接配置，选择密码或私钥认证，确认查询响应不泄露原始凭据。
2. 调用连接建立；若返回未知主机指纹，人工核对目标，再调用主机密钥确认接口。
3. 用 ssh_connection_check 或连接列表确认 Session 健康。
4. 执行无副作用短命令，例如读取主机名、当前用户或工作目录。
5. 执行超过同步等待窗口的安全长任务，使用 execution_get 按 nextCursor 读取到终态。
6. 单独验证取消，再以只读命令核验远端状态；不能把取消响应直接当成远端进程终止证明。
7. 打开页面终端，验证 PTY 输入、输出、resize 和关闭；再验证外部 Agent 终端是独立观察资源。
8. 读取文件、获取 SHA-256，再用预期版本保存或精确 Patch，主动制造一次版本冲突确认拒绝覆盖。
9. 检查 Sandbox 能力；只有在目标 Docker 就绪时创建模板 Sandbox，并用不挂载用户工作区的托管隔离模式验证强制隔离命令。

## 联调时我使用的入口分组

为了避免把 HTTP、MCP 和内置 Agent 混在一起，我按下面的入口分组验收：

| 入口 | 典型操作 | 响应形态 | 重点检查 |
| --- | --- | --- | --- |
| `/api/v1` | Agent 配置、会话、聊天、绑定和权限确认 | 统一响应或 SSE | userId、sessionId、事件关闭和错误映射 |
| `/api/v1/ssh` | 连接创建、连接、断开、列表 | 统一响应 | 指纹确认、Session 健康和凭据不回显 |
| `/api/v1/ssh/terminal` | 终端列表、打开、执行、写入、读取、resize、关闭 | 统一响应 | PTY、终端上限和所有者边界 |
| `/api/v1/ssh/file` | 目录、内容、分块、上传、下载和变更 | 统一响应或文件流 | UTF-8、二进制标志、版本冲突和远端权限 |
| `/mcp` | initialize、tools/list、工具调用 | MCP Streamable HTTP | Bearer、MCP 会话头、工具白名单和游标 |

`/api/v1/ssh/agent` 仍保留旧终端绑定接口做兼容过渡，新的绑定接口已经合并到 `/api/v1`。验收脚本应优先使用当前入口，兼容接口只验证不会破坏已有调用方。

## 第五步：发布镜像

Dockerfile 提供两个运行目标。runtime-local 复制宿主机已经打好的 Jar，适合个人快速迭代；runtime 先在 Maven builder 阶段完成 docker profile 构建，适合干净环境和 CI。运行镜像基于 Java 17 JRE，以非 root 的 walicode 用户启动，并只暴露 8091。

多架构本地构建脚本使用 Docker 的 amd64 和 arm64 目标；镜像推送脚本面向阿里云镜像仓库，需要本地私密配置文件提供登录信息。登录凭据、模型 Key、SSH 凭据和应用加密密钥都不应写入 Git 或文章。

## 第六步：上线前配置检查

生产 profile 从环境变量注入数据库、Redis、端口、模型占位配置和 MCP 开关。上线前至少检查：

| 检查项 | 期望 |
| --- | --- |
| SPRING_PROFILES_ACTIVE | prod |
| WALISSH_SECRET_KEY | 稳定且至少 32 个随机字符 |
| MySQL/Redis 地址和密码 | 指向生产依赖，应用容器能连通 |
| MCP_STATIC_BEARER_TOKEN | 直连 MCP 时使用长随机 Token；由网关认证时关闭应用静态 Token |
| APP_BIND_ADDRESS | 只在确有需要时对外监听，公网入口由 TLS 网关承接 |
| Agent YAML | 不含本地开发密钥，模型和工具均能成功装配 |
| SSH 目标 | 已完成 host key 验证，连接账户权限符合运维范围 |

## 上线后的验收顺序

Compose 启动后先看 docker compose ps，确认 MySQL、Redis 和 app 健康，再看 app 最近日志。MCP 直连时先完成 initialize 和 tools/list，随后按“探活 → 连接列表 → 连接检查 → 只读命令 → 长任务 → 取消”验收。不要用清库、格式化磁盘、删除根目录或未知脚本做上线测试。

上线不等于完成权限治理。若应用端口可被客户端直接访问，应确认网络策略没有绕过网关；若部署为多个 app 实例，应先确认终端、JSch Session、执行线程和本地锁的路由方案，否则多实例会改变当前单 JVM 的语义。
