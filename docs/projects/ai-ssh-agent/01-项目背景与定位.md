## 我要解决的真实问题

运维场景里，模型最有价值的动作往往不是生成一段建议，而是读取真实状态、执行检查、修改远端文件、验证结果，再根据结果决定下一步。SSH 是进入真实主机的主通道，但 SSH 也意味着凭据、主机信任、命令副作用、长任务输出、交互状态和网络失败同时出现。

我观察到，直接把 SSH 客户端暴露给 Agent 会把几个不同问题混在一起：模型是否理解了任务，调用者是否被允许操作这台主机，命令是否应该在真实环境执行，命令输出是否还在继续，以及连接断开后能否证明发生了什么。这个项目的建设动机，就是让这些判断在代码中各自有位置。

## 项目定位

我将它定位为“面向运维的 Agent 执行底座”。它提供统一的 Agent 装配和工具调用入口，但把 SSH 作为主业务链路，把 Sandbox、SFTP、交互终端和长任务恢复作为 SSH 周边的完整能力，而不是单独的演示功能。

| 方向 | 当前真实实现 | 适用边界 |
| --- | --- | --- |
| Agent 装配 | 从 YAML 装配 AI API、Chat Model、Agent、Workflow、Runner | 适合固定配置驱动的应用内 Agent，不是在线多租户编排平台 |
| SSH 运维 | 连接管理、密码或私钥认证、主机指纹确认、命令执行、取消、查询 | 适合受控服务器操作，不替代企业堡垒机审计体系 |
| 文件操作 | SFTP 读取、分页、上传、下载、创建、移动、删除和 SHA-256 版本保护 | 适合有限大小的文本编辑和普通文件操作 |
| 隔离执行 | Docker Sandbox 能力检查、创建、执行、重置、销毁 | 适合不可信或需要隔离的命令，不保证 Docker 一定存在 |
| Agent 对外接入 | 普通 HTTP API、内置工具和 `/mcp` Streamable HTTP | MCP 有静态 Bearer Token；普通 API 不自动获得同等认证 |
| 长任务 | 10 秒同步等待，之后用 executionId、Redis Stream 和游标观察 | 可恢复记录与输出，不承诺跨重启恢复远端进程 |

## 为什么 SSH 是主链路

HTTP、MCP 和内置 Agent 都只是请求来源。真正的运维副作用从 `ssh_execute`、交互终端写入或远程文件变更开始。因而我把连接、主机信任、执行准入、远端 Shell、输出记录和恢复能力放在同一条可追踪链上。Agent 可以决定“下一步需要检查什么”，但不能跳过连接身份、目标策略或执行安全规则。

这也解释了为什么工具说明中要求先拿到完整 `connectionId`，禁止猜测连接名称，禁止自动切换服务器；为什么长任务查询要求原样传回 `nextCursor`；为什么被要求进入 Sandbox 的命令不能换回 HOST 重试。它们不是提示词层面的礼貌约定，而是把副作用边界固定在调用协议和 Case 中。

## 我观察到的真实使用流程

用户第一次使用系统时，并不是直接让 Agent 执行一句命令，而是完成一条有前后关系的流程：

1. 在页面或调用方创建 SSH 连接配置，选择密码或私钥认证。
2. 单独发起连接；未知主机密钥时暂停，用户核对指纹后再确认。
3. 用连接列表或连接检查确认目标已经建立 Session。
4. 通过聊天、MCP 或操作工具执行只读检查；结果若超过同步窗口，就转为 executionId 查询。
5. 需要改文件时先读取或获取版本摘要，再进行 SFTP 写入或精确 Patch。
6. 命令被判定为不可信时，先检查目标服务器的 Docker 能力，再创建不绑定用户目录的 Sandbox。

这个顺序说明项目的业务对象不是“一个带 SSH 的聊天框”。连接建立、命令执行、文件编辑、终端交互和隔离容器分别有自己的状态和失败补偿，Agent 只负责在这些能力之间做下一步选择。

## 外部入口和能力边界

当前入口可以分成三类：普通 HTTP 的 `/api/v1` 接口、MCP Streamable HTTP 的 `/mcp` 端点，以及应用内 Agent 的 ADK Function Call。三者最终共享 SSH、执行、文件和 Sandbox 的 Case/Domain 能力，但认证、会话来源和响应形态不同。普通 HTTP 返回统一响应对象；聊天流和 ReAct 使用 SSE；MCP 按协议返回工具结果。

我特别保留“没有实现”的边界：源码没有发现消息队列、完整用户登录、租户目录、细粒度角色授权或跨实例 Session 迁移。它可以作为运维 Agent 的执行底座，但不能在文档中包装成已经具备这些平台能力的产品。

## 不适用的场景

我没有把这个项目描述成以下系统：

| 不应被误解成 | 原因 |
| --- | --- |
| 完整堡垒机 | 当前实现提供连接和执行控制，但没有完整的企业账号、角色、审批、租户和统一审计产品能力 |
| CMDB 或资产平台 | SSH 连接是执行前提，不承担资产发现、配置基线和主机生命周期治理 |
| 任意 TTY 终端 | Managed Shell 使用非 PTY 和控制帧；页面终端独立处理交互资源，不等价于 Agent 任意接管 TTY |
| 可靠分布式工作流引擎 | 执行上下文、Session、终端和部分恢复能力主要在单进程内存中协调 |
| 自动提权系统 | `sudo -n` 只在明确授权和受控语义下使用，系统不会索取或传递用户密码 |

## 我的设计判断

第一，我把“模型能力”和“执行权”分开。模型可以生成工具调用，但工具调用仍需通过权限、目标、安全和并发门禁。第二，我把真实远端状态和可恢复记录分开。Redis 记录可以帮助客户端继续读输出，却不能制造已经死亡的远程进程。第三，我把页面终端和 Agent 执行分开。页面终端可以交互，外部 Agent 终端只能观察或关闭，避免把人工会话和自动化会话混成一个写入通道。
