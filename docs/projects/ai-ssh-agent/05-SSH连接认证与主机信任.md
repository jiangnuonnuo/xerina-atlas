## 我要解决的问题

运维链路的第一步不是执行命令，而是确认“目标是谁、凭据是什么、我是否信任这台主机”。如果只保存 host、port、user，然后在第一次命令执行时默默接受主机密钥，系统无法解释连接是否遭遇了错误主机或中间人风险。

## HTTP 入口和状态变化

连接管理统一挂在 `/api/v1/ssh` 下，实际接口包括创建、更新、删除、查询、列表、连接、主机密钥确认和断开。页面通常先创建或更新连接配置，再单独发起连接；连接配置存在，不代表进程内已经有健康的 JSch Session。

连接状态可以按下面的业务语义理解：

| 阶段 | 系统保存或检查的事实 | 失败含义 |
| --- | --- | --- |
| 配置 | 地址、端口、用户、认证类型和加密后的凭据 | 参数不完整或保存失败 |
| 待信任 | 收到远端 host key 或指纹 | 未确认时不应继续认证 |
| 已连接 | JSch Session 建立并通过健康检查 | 认证失败、网络失败或 host key 不匹配 |
| 已断开 | Session 被关闭或健康检查失败 | 连接配置仍可能保留 |
| 已删除 | 配置事实清除，运行时资源也应清理 | 后续 connectionId 不应继续可用 |

## 两种认证材料

实现支持密码认证和私钥认证。密码、私钥等敏感材料通过应用密钥加密保存，查询响应不返回原始凭据。部署资料要求配置至少 32 个随机字符的应用密钥；更换密钥会使使用旧密钥加密的凭据无法解密，这是一个必须在发布前安排迁移或回滚窗口的运维事实。

连接建立时，认证材料由基础设施网关解密并交给 JSch；领域层只关心认证策略、连接配置和结果，不应该知道 JSch 的 Session API 细节。

## 主机密钥确认

项目采用严格主机密钥检查。第一次遇到未知 host key 时，系统保留待确认信息并要求用户显式调用主机密钥确认接口；确认后才允许把该主机纳入可信连接。指纹确认不是前端装饰，而是连接状态的一部分。

我选择严格检查，是因为运维系统更怕“连错但执行成功”而不是单纯的连接失败。代价是首次连接多一步交互，也要求部署和测试资料把指纹确认作为验收步骤。

## Session 缓存和健康检查

成功连接后的 JSch Session 以连接为键保存在进程内运行时缓存中。重复使用同一连接时，系统复用 Session；SFTP 操作不复用 Channel，而是每次操作建立独立 Channel。连接健康检查使用 SSH `sendIgnore()`，而不是通过执行一个可能产生副作用的 Shell 命令探活。

Session 是运行时资源，不是数据库事实。应用重启后，数据库中的连接配置仍然可能存在，但 JSch Session 必须重新建立。这个边界会影响 [交互终端与远程文件操作](./08-交互终端与远程文件操作.md) 和 [部署拓扑、配置、监控与运维](./14-部署拓扑配置监控与运维.md)。

## 失败分支

- 指纹不匹配：拒绝连接，不自动接受新的 key。
- 凭据解密失败：连接不能进入已连接状态，重点检查应用密钥是否变更。
- 认证失败：返回连接失败，不把旧 Session 当成健康连接。
- 网络中断：健康检查失败，运行时 Session 需要清理；正在执行的远程命令是否可观察要交给执行生命周期处理。
- connectionId 不存在或不属于当前调用上下文：在执行前拒绝，不自动按名称搜索或切换其他连接。

## 验证方式

领域测试覆盖密码、私钥和不完整认证配置；主机信任规则测试覆盖未知、确认和不匹配 key；基础设施测试覆盖凭据加密、host key 仓库、连接创建和错误映射。真实服务器集成测试需要显式配置目标和 `app.tests.skip=false`，不能把本地单元测试当成真实 SSH 握手证明。
