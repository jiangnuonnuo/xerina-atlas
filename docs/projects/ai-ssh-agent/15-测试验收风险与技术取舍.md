## 我用什么证据判断实现可信

这个项目的风险集中在副作用：模型可能选错工具，工具可能选错连接，命令可能运行很久，输出可能超过 HTTP 响应，SSH Channel 可能在终态前消失。因此测试不能只验证 Controller 返回 200，而要验证请求是否走过正确的 Case、策略是否拒绝越界命令、状态是否可解释、失败后是否能恢复查询。

## 测试分层

当前源码中共有 85 个 Java 测试文件，分布在 app 31、case 15、domain 29、infrastructure 10。测试重点如下：

| 层 | 已覆盖的真实主题 | 还需要外部环境证明的内容 |
| --- | --- | --- |
| Domain | SSH 认证策略、主机信任、命令规则、终端上限、文件版本、Sandbox 生命周期、Agent 工具策略和 ReAct 辅助组件 | 真实 SSH 握手、真实远端账户权限和实际 Docker 行为 |
| Case | Agent ReAct 节点、执行准入、上下文占用、长任务生命周期、取消和恢复 | 应用重启、多实例、真实网络抖动下的恢复语义 |
| Infrastructure | Redis 执行仓储、SFTP/SSH 网关、Docker 命令构造、凭据加密、Stream 游标和 host key 仓储 | 真实 MySQL/Redis 版本、远端 SSH 服务、容器 daemon 和镜像仓库 |
| App/Trigger | MCP 会话头解析、Agent 入口、工具路由、SFTP 工具和个人知识 Agent 入口 | 完整 Spring Boot 启动、真实模型 API、跨域/网关/TLS 组合 |

应用模块的 Surefire 配置默认跳过测试，显式传入 -Dapp.tests.skip=false 才执行；这是一项构建约定，不是测试不存在。当前工作环境没有可用的 mvn 命令，所以我只能以源码和测试清单证明覆盖范围，不能把本轮构建结果写成绿色。

## 我把测试结果分成三种证据

| 证据级别 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| Domain/Case 单元测试 | 规则、状态、策略、上下文和失败分支按预期变化 | 真实 SSH、Docker、Redis、模型网络可用 |
| Infrastructure 集成或适配器测试 | JSch/SFTP/Docker 命令构造、Redis 游标和 MyBatis 映射符合约定 | 目标服务器的权限、网络和镜像实际状态 |
| 部署环境验收 | Compose 健康、真实握手、模型调用、长任务和故障行为 | 高可用、多实例和企业身份治理，除非另有专门环境 |

我不会用“Controller 返回成功”替代第三类证据，也不会把编译通过等同于远端执行安全。每一条上线结论都需要注明它来自单元测试、适配器测试还是实际环境。

## 最小验收标准

我会把验收拆成五组，每组都要求观察成功和失败：

1. **启动与装配**：Maven 构建成功，prod profile 能启动，MySQL/Redis health 通过，Agent 和配置白名单工具完成注册；模型配置错误、工具重名和 Token 缺失时要明确失败。
2. **连接与信任**：密码和私钥均可连接，未知 host key 先待确认，错误指纹拒绝，认证失败不留下健康 Session，断开后连接配置仍可查询。
3. **命令生命周期**：短命令同步返回，超过 10 秒返回 executionId，同一上下文重复提交被占用或按幂等键复用，非零退出、超时、取消、线程失败和上下文丢失分别可识别。
4. **终端、文件与 Sandbox**：终端最多 5 个，页面 PTY 可读写，外部 Agent 终端不可被页面注入；文件 SHA-256 冲突不覆盖；Sandbox 无 Docker、权限拒绝和 daemon 不可用时不回退 HOST。
5. **恢复与安全**：Redis 游标可以连续读取，游标过期返回新起点，Redis 不可用时返回持久化降级状态；应用重启后不把旧 JSch Channel 或 RUNNING 记录伪装成可取消成功。

## 关键风险

| 风险 | 现状判断 | 验收或补强建议 |
| --- | --- | --- |
| 身份和租户 | /api/v1 主要依赖 userId，未发现完整登录/RBAC；MCP Token 是应用级 | 由网关建立可信主体，后端对每个资源入口做归属检查 |
| 多实例一致性 | Session、终端、绑定、上下文锁和执行线程在 JVM 内 | 单实例或粘性路由；扩展前外置状态并引入分布式协调 |
| 远端副作用 | 命令不应因 HTTP 超时自动重试；取消不保证脱离进程已停止 | 强制使用 executionId 查询和只读核验，保留审计 |
| AI 安全判断 | 工具描述帮助模型选择，服务端确定性规则才是实际防线；风险分类异常不能被当成绝对安全 | 绝对拒绝默认拒绝，危险操作增加人工确认和策略审计 |
| 输出保留 | Redis 有 TTL 和消费清理，超过边界可能 CURSOR_EXPIRED | 客户端及时消费，重要结果另行保存，不依赖临时 Stream 做永久审计 |
| 凭据轮换 | 应用密钥变更会影响旧 SSH 凭据解密 | 设计密钥迁移或双密钥解密窗口，轮换前备份和演练 |
| 依赖和模型 | 启动依赖 MySQL、Redis、模型配置；外部 API 不是本地可重复证据 | 联调环境固定版本，区分模型失败、工具失败和远端失败 |
| 运维观测 | 目前主要是日志、healthcheck 和执行状态，没有完整指标链路 | 增加命令耗时、拒绝、队列、Redis、SSH、Sandbox 和安全事件指标 |

## 为什么采用当前方案

我选择 DDD 分层单体，是因为 SSH 规则、执行状态和 Agent 工具需要共享同一套领域边界，而当前规模还不值得把每条链路拆成远程服务。Case 层承担场景编排，Domain 层保留认证、策略、状态和文件版本规则，Infrastructure 通过 Port 接 JSch、Redis、MySQL 和 Docker；这样模型供应商或传输协议变化时，远端副作用规则不用重写。

我选择 Managed Shell 而不是把每条命令简单拼到 exec，是为了获得控制帧、输出边界、退出码和长任务生命周期。代价是要维护 Shell 协议、输出预算和超时后的 Channel 清理，且不适合真实交互 TTY 程序。

我选择 Redis Hash + Stream，而不是把长任务输出全部塞进 MySQL，是因为输出是高频增量数据，查询需要游标和有限保留；代价是没有跨 Redis 与远端 Shell 的事务，应用重启不能恢复进程句柄。

我选择 HOST、INTERACTIVE_TERMINAL、SANDBOX 三个明确目标，而不是一个“万能执行器”，是为了让隔离要求可以拒绝和解释；代价是用户必须理解何时开终端、何时建 Sandbox，Docker 不可用时也不能自动完成不可信脚本。

我选择文件 SHA-256 乐观校验和本地锁条带，是为了避免 Agent 覆盖用户刚刚修改的文件；代价是本地锁只对单 JVM 有效，跨实例仍需要外部协调。

## 实际遇到的困难

最难的不是接通 SSH，而是把“执行已提交”“输出已交付”“远端是否仍可控制”分成不同事实。第二个困难是终端页面和 Agent 都需要 Shell，但页面需要 PTY，Agent 需要可解析的控制帧，外部 Agent 还只能观察自己的独立终端。第三个困难是 Agent 工具既有内置能力又有动态 MCP/Skills 能力，必须在装配时处理白名单、重名、调用上限和会话上下文。

我通过领域测试、Redis 仓储测试、Shell 帧协议测试、终端并发测试、Sandbox 错误状态测试和工具注册测试验证这些边界；对于真实网络、真实模型、真实 Docker 和多实例场景，仍然需要部署环境验收，不能用单元测试代替。

## 最终结论

当前实现已经形成一条真实可追踪的 SSH 运维主链路：配置连接、确认主机、执行命令、读取长任务、操作文件、打开终端、按风险进入 Sandbox，并由 Agent 通过 ReAct 调用。它适合单实例或受控部署中的 Agent 运维实验和实际辅助操作；在补齐身份、授权、多实例状态、指标和灾备前，我不会把它描述成完整企业堡垒机或高可用多租户平台。
