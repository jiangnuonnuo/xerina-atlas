## 我要先定义哪些数据是事实

这个项目同时管理数据库记录、Redis 临时记录和进程内运行时资源。如果不先区分事实来源，就会把“数据库显示已连接”误读成“JSch Session 一定健康”，也会把 Redis 中的 RUNNING 记录误读成“远端进程仍然可控”。

![长执行一致性与恢复链路](./assets/execution-recovery/execution-recovery.gif)

图要回答的问题：命令提交后，实时 Shell、有限内存缓冲、Redis Hash、Redis Stream、查询游标和终态判断怎样共同工作。关键节点是准入、运行时注册、输出转存、终态保存和 ACK；失败分支是线程池拒绝、Redis 写入失败、Shell 上下文丢失、游标过期和取消未确认。一致性边界是“Redis 记录可读”与“远端进程仍可控制”之间，隔离边界是执行上下文和目标类型之间。

## 三类状态源

| 状态源 | 记录 | 生命周期 | 可信范围 |
| --- | --- | --- | --- |
| MySQL | Agent 会话、消息、里程碑、SSH 连接配置和核心记忆等持久事实 | 跨进程保留 | 适合查询业务事实，不代表运行时连接健康 |
| Redis | SSH 执行元数据、增量输出、最近执行索引、运行中索引和幂等映射 | 按 TTL 保留 | 适合跨请求读取和恢复查询入口，不是远端 Shell |
| JVM 内存 | JSch Session、Shell Channel、执行线程、输出缓冲、终端绑定和本地锁 | 进程生命周期 | 负责实时控制，重启或多实例时不能单独作为持久事实 |

SSH 执行没有新增 MySQL 任务表，执行实体只进入 Redis 临时仓储。Redis 也不是跨 Hash、Stream、索引和运行时注册表的全局事务协调器，所以我把状态设计成可以解释的阶段，而不是宣称所有写入原子完成。

## 提交和终态的顺序

一次 HOST 或 Sandbox 执行大致经历以下阶段：

1. Case 先完成请求规范化、参数校验、目标选择、策略评估、幂等查找和上下文占用检查。
2. 通过准入后创建执行记录，登记 executionId、上下文、目标、命令摘要和初始状态。
3. 运行时注册表保存执行跟踪器，工作线程调用对应策略，把输出字节交给有界缓冲。
4. 缓冲按时间或字节阈值转存 Redis Stream，同时更新 Hash 中的预览、字节数和游标。
5. 远端 Shell 给出退出码或发生异常后，终态决策树区分成功、非零退出、取消、超时、线程失败和 UNKNOWN。
6. 终态和最后输出再次写入 Redis，移除运行中索引；客户端用 Stream ID 查询并 ACK，达到消费窗口后才清理旧数据。

这里没有 MySQL 和 Redis 的跨库事务。业务上最重要的取舍是：宁可把一次执行标记为 MEMORY_ONLY、PERSISTENCE_FAILED 或 UNKNOWN，也不把没确认的远端结果伪装成成功。

## Redis 输出的一致性策略

执行元数据放在 Hash，原始输出分块放在 Stream；Sorted Set 用于最近执行和运行中索引，Value 用于幂等键到执行 ID 的映射。Stream ID 是外部游标，响应同时带有 nextStreamCursor、是否还有更多、输出是否截断和首个可用游标。

输出策略有四个约束：

- 单次命令最大输出约 20 MiB，预览只保留尾部，诊断尾部约 64 KiB。
- 单次内联响应约 256 KiB，超出后必须继续用 executionId 查询。
- 每次查询最多返回有限数量的 Stream 块，后续请求原样传回 nextCursor。
- 客户端确认消费到某个游标后，累计达到约 2 MiB 的清理窗口才删除更早的 Stream 数据。

游标早于 trimmedBeforeCursor 时，系统返回 CURSOR_EXPIRED 和新的可用起点；这不是数据损坏，而是有限保留策略的公开结果。终态已交付记录的 TTL 约 10 分钟，普通和运行中记录约 1 小时。

这里的 Redis 是执行状态和输出投影，不是所有业务数据的缓存层。MySQL 的聊天、里程碑、核心记忆和 SSH 连接配置不会因为 Redis 失效而自动从缓存重建；执行记录则没有 MySQL 任务表作为第二事实源。因此 Redis 不可用时，系统只能把正在运行的结果保留在 JVM 内存并标记降级，不能把执行状态切换到一个并不存在的数据库事务。

## 幂等、重试和补偿

幂等键以执行上下文为作用域映射到 executionId。重复提交同一个业务键可以找回原执行，而不是重新创建一个远端命令；这对删除、发布和修改类操作尤其重要。幂等映射本身也有 TTL，过期后不能再把它当成永久审计索引。

我把可重试动作和不可重试动作分开：

| 动作 | 可否自动重试 | 原因 |
| --- | --- | --- |
| Redis 输出转存 | 可以有限重试 | 追加的是已有 Shell 输出，需要避免重复 Stream 记录并公开持久化失败状态 |
| 查询 Redis 状态 | 可以重试 | 只读，不会再次产生远端副作用 |
| execution_cancel | 可以幂等重试 | 重复取消只影响同一 execution，但最终是否终止远端脱离进程仍需核验 |
| 原始 SSH 命令 | 不能因客户端超时自动重试 | 可能重复删除、发布、修改或启动服务 |
| 文件保存 | 不应盲目重试 | 需要结合 SHA-256 版本和精确替换次数，冲突时重新读取 |

补偿也遵守同样边界：查询、重新读取和人工确认是安全补偿；业务反向操作只有在已知语义下才可执行，不能用“再跑一遍原命令”填补不确定结果。

## 并发控制的层次

我在不同资源上使用不同粒度的控制：

- SSH 执行工作线程池默认核心 4、最大 8、队列 32，拒绝策略为 AbortPolicy。队列满时提交失败，不会排队到无法解释的时间。
- 执行上下文注册表限制同一上下文只能有一个运行中命令；不同连接、不同会话和不同目标可以并行。
- 终端写入使用单写锁，页面原始输入和 Agent 控制帧不能交错；Agent 命令超时后先发中断并等待结束帧，收不到边界就关闭当前 Shell Channel。
- 同一连接最多 5 个终端，打开动作使用连接级计数和并发测试覆盖上限。
- 文件修改使用 64 条本地锁条带，再配合远端文件 SHA-256 乐观版本校验。
- Sandbox 过期清理使用单线程定时维护，每轮最多处理配置的批量数量；SSH 未连接时跳过销毁，等待下一轮。

这些控制默认都是单 JVM 语义。文件锁、终端计数、上下文占用和 Session 复用都不是分布式锁，多实例部署必须增加路由或外部协调，否则同一个远端资源仍可能被两个实例同时操作。

## 异常如何收口

命令已完成但退出码非零，会收口为 COMMAND_EXIT_NON_ZERO，它与连接故障不同。超时会标记 TIMED_OUT，取消会标记 CANCELLED，但消息明确说明“已发送中断或关闭独占 Shell”不等于确认远端脱离进程已经停止。工作线程异常、上下文丢失、Shell 协议错误和被中断但无法确认的结果会进入 UNKNOWN。

Redis 写入失败时，运行时可能保留内存输出。终态提交失败会把输出放回缓冲，标记 MEMORY_ONLY 或 PERSISTENCE_FAILED，并在结果中说明当前查询可靠性下降。应用重启后这段内存结果消失，Redis 未落盘的输出不能恢复。

普通 HTTP Controller、MCP 工具和内置 Agent 工具会把不同异常映射为各自的响应形态，但底层语义保持一致：参数错误不进入远端，策略拒绝不创建执行，命令非零退出保留退出码，Redis 故障暴露存储状态，进程重启把孤儿运行记录标成 UNKNOWN。这样调用方可以根据 `code`、`status`、`storageState` 和 `nextAction` 决定下一步，而不是只看一个布尔成功值。

## 我如何验证一致性

单元测试覆盖 Redis Hash、Stream、TTL、游标过期、幂等映射、执行终态树、上下文忙、终端并发和文件版本冲突。真正的验收还必须注入 Redis 短时不可用、应用重启、SSH Channel 中断、命令超时、取消无结束帧、重复提交和跨实例文件修改，观察系统是否返回“不确定”而不是错误成功。
