## 我如何划分业务对象

我没有把“SSH 连接”“终端”“命令”“文件”和“Agent 会话”看成一个大对象。它们的生命周期、失败方式和并发规则不同，强行合并会让一个功能的状态变化污染另一个功能。

| 对象 | 负责的事实 | 关键规则 |
| --- | --- | --- |
| SSH Connection | 主机地址、端口、用户名、认证材料和主机信任状态 | 密码或私钥加密保存；严格主机密钥检查；连接状态与运行时 Session 分离 |
| SSH Session | 进程内 JSch Session | 连接复用；健康检查使用 `sendIgnore()`；进程重启后需要重新建立 |
| Execution | executionId、目标、命令、上下文、状态、退出码和输出位置 | 同一执行上下文同一时刻只允许一个运行中命令；取消幂等；长任务不重复提交 |
| Terminal | 页面或 Agent 观察资源、输入输出和窗口尺寸 | 每个连接最多 5 个终端；外部 Agent 终端只能观察或关闭 |
| Remote File | 路径、内容、大小和版本摘要 | 可编辑文件最多 2 MiB；写入支持 SHA-256 乐观版本；删除根目录被拒绝 |
| Sandbox | Docker 能力、运行时规格、资源、网络和工作区模式 | 隔离场景不能把用户工作区自动挂入；能力不足时不能静默回退 HOST |
| Agent Chat Session | 对话上下文、工具调用、结果和 SSE 进度 | 工具调用回到统一工具平面；连续相同调用超过 2 次时由循环保护阻断 |
| MCP Session | 外部 transport 的会话标识 | MCP 工具按会话解析执行上下文；丢失会话时拒绝执行，不猜测目标 |

## 领域边界

SSH Connection 解决“我连的是谁以及是否信任这台主机”；Execution 解决“这次命令是否允许、怎样运行以及如何报告”；Terminal 解决“一个可观察或可交互的通道怎样存在”；Remote File 解决“文件怎样有界读写和防止并发覆盖”；Sandbox 解决“命令是否需要隔离”；Agent Session 解决“模型如何循环和保留上下文”。这些边界在 Case 层组合，但不互相偷取生命周期。

## 状态变化

连接大致经历“已配置、等待主机信任、已连接、已断开或已删除”。主机指纹确认不是普通连接字段更新，而是连接到真实主机前的信任门槛。连接建立成功后，JSch Session 进入进程内缓存；断开或健康检查失败时，运行时资源被清理，但数据库配置可以继续存在。

执行大致经历“创建、准入、运行、成功、非零退出、失败、取消、超时、记录可查询”。其中命令退出码非零不等于 SSH 工具失败，系统把 `COMMAND_EXIT_NON_ZERO` 与通道断开、提交失败区分开，调用者需要结合 `exitCode` 和输出判断。

终端和文件不共享同一个状态机。页面终端的写入、读取和 resize 由终端资源处理；文件写入经过 SFTP 或受控的 sudo 文件策略，先检查版本，再执行精确替换。Agent 使用 HOST Managed Shell 时不会把页面交互终端当成自己的命令帧通道。

## 规则为何落在这里

我把“最多 5 个终端”“根目录不可删除”“文件大小限制”“同一上下文不可并发运行”放在领域或 Case 约束中，而不是交给前端。前端限制只能改善用户体验，不能阻止 Agent 或 MCP 客户端直接构造请求。

相反，JSch Session 如何缓存、SFTP Channel 如何创建、Redis Stream 如何写入属于 Infrastructure；Controller 如何将错误映射成 HTTP 响应属于 Trigger 或响应组装。这样每条规则都能在不启动远端主机的情况下进行单元测试。

## 领域边界中的空白

当前没有完整的租户聚合、企业用户聚合或授权策略存储；普通 HTTP 请求主要依赖 `userId`。因此，领域对象虽然有连接、会话和执行上下文的隔离，但不能被描述成已经完成的多租户数据平面。真实边界见 [认证、权限、会话与隔离边界](./11-认证权限会话与隔离边界.md)。
