# 字段目录平台

把散落在业务页面里的“字段定义”沉淀为可维护目录，并以稳定的字典产物交付给分析、配置和对接场景。这里采集的是菜单、模块、页签、分组、字段名、筛选项、表头、指标及其层级关系，**不采集业务数据值**。

这套文档既能帮助我回忆项目是怎样从输入、治理到交付跑通的，也让 HR 和技术面试官能在各自关心的粒度上读懂项目价值。它不是源码导览：不公开内部接口、表结构、类名或提示词原文。

## 先看这一页：项目到底解决什么

页面上的字段看似只是几行文字，实际会随着菜单改版、页签切换、权限差异和业务调整不断变化。只靠人工表格，更新慢、路径易错、历史难追；只靠模型“看页面”，又会漏掉折叠区、滚动区和未展开页签。

平台将问题拆成一条可验证的资产链：先拿到字段证据，再理解其层级和语义，随后把结果治理成稳定的树，最后按快照异步导出，并把后续变化纳入审核。DOM 可以乱，目录树不能跟着长成麻花。

## 完整业务链

1. 业务人员指定页面和字段范围。
2. 人工点选或受限浏览器工具形成页面字段证据。
3. Agent 应用把证据、规则和人工反馈编排为候选字段树。
4. 规则校验和人工预览共同决定哪些结果可进入目录。
5. 目录治理维护节点、路径、生命周期和结构一致性。
6. 字段字典任务从一致性快照出发，分段生成可交付产物。
7. 再次采集时，对比快照并审核新增、删除、改名和移动。

## 事实状态说明

为了让面试材料可信，本文档用三个标签描述不同成熟度：

| 标签 | 含义 |
| --- | --- |
| 已落地 | 当前项目已有可验证实现与工程机制 |
| 技术验证 | 已做过工具试验，结论会影响方案选择 |
| 方案设计 | 面向后续演进的完整目标实现，不描述为已上线功能 |

当前项目的目录树治理、结构生命周期和可恢复交付属于“已落地”；纯 Agent 自动采集出现漏采的结论属于“技术验证”；DOM-first 的自动采集与内部 Agent 应用编排属于“方案设计”。这不是减分项，反而体现了先验证风险、再确定职责边界的工程判断。
