# 03 · 读写分离与异步导出

> 对应简历点：**"读写分离 + 异步导出（百万字段不爆内存）：导出仅在 MySQL 建 REPEATABLE READ 一致性只读快照（不持目录写锁），落本地 SQLite 用递归 CTE 算树传递闭包 + tree_path 排序得 DFS 前序流，JVM 仅用 O(depth) Deque 维护祖先路径、叶节点即时落盘，Apache POI SXSSF 流式写（内存窗口恒定 100 行）、.part 原子提交；50 万字段字典导出 35s，百万级体量下服务内存平稳、业务不中断，导出与实时采集并行"**。
> 本篇问题：Q7（为什么 XLSX 任务化交付）→ Q8（MVCC 较真：快照防什么）→ Q9（为什么 SQLite 中转）→ Q10（O(depth) 机制）→ Q11（异常与恢复）。这条是"后端硬核"链，Java 后端面试官会在这里连环较真。

## Q7：字典为什么必须"导成几十万行的 XLSX"交付？为什么不能前端拼？

**考察意图**：产品思维（两种使用模式）+ 量级认知。面试官要看你能否区分"治理场景"和"交付场景"，以及是否理解"为什么这个量级天生是后端+异步的活"。

**问题原话**：平台里不是有目录树查询界面吗？为什么还要导文件？下游拿这份几十万行的 Excel 干什么？为什么不是前端拉树、前端拼 Excel 的轻量做法？

### 标准回答（完整版）

> 平台里确实有查询界面——那棵目录树工作台，支持懒加载、搜索、审核。但那个界面是给**"治理字典的人"**用的：找一个字段、看它挂在哪个组下面、改层级、走审核。它的使用模式是"在活树上点来点去"，要的是实时和交互。
>
> 导出解决的是另一件事：**交付**。字典的消费方是数仓、报表这些"取数侧"——他们的映射/校验程序是吃表格输入的，报表同学也要照着字段清单写 SQL。他们需要的不是一棵可以点的树，而是一份**完整、扁平、钉在某个时间点上的静态产物**：全量、格式固定、可拿去做映射、可放进自己的流程。所以"查询工作台"和"导出文件"是两个不同需求，前者管治理，后者管交付。
>
> 为什么不能前端拼？两个硬理由。**第一，量级扛不住。** 这是几十万行、还带树层级的数据——要把全量先拉进浏览器再拼 Excel，传输和内存都扛不住，浏览器直接卡死。而且数据本来就在 MySQL 里，前端拼等于让每个用户都去全量查一遍库。**第二，可靠性为零。** 五十万行要跑半分钟左右，用户中途关个页面、断个网，前端方案就什么都没了。只有把导出做成**服务端任务**，才谈得上状态机、失败重试、断点恢复、进度可查。
>
> 而且我们还踩过一个真实的坑：如果让用户并发从前端拉全量树，等于把海量查询无控制地打回服务端——我们线上吃过 **MySQL 连接池被拖垮**的教训。所以导出必须走独立任务 + 有界线程池 + 信号量限流，全局同时只放一两个任务进来，绝不能让导出和在线业务抢连接池。

### 注意方向

- ✅ 先立"**治理场景 vs 交付场景**"两个模式——这是产品思维的直接体现。
- ✅ "连接池被拖垮的教训 → 限流"是异常意识的硬证据，主动讲。
- ⚠️ "他们的比对映射程序是表格化输入实现的"这句太绕，就说"他们的映射/校验程序吃的是表格输入"。
- ✅ 收尾把"固定时间点的一致性视图"埋下——自然衔接 Q8 的快照话题。

## Q8：MVCC 较真——普通 SELECT 本来就不阻塞写入，你的"一致性只读快照、不持写锁"到底在防什么？

**考察意图**：MySQL 原理的**真懂还是背词**。这是全场最危险的一问：如果你只会背"一致性快照"四个字，会被一句话问穿。答好的钥匙是：**语句级快照 ≠ 跨语句一致性**。

**问题原话**：InnoDB 里普通 SELECT 靠 MVCC 本来就不阻塞写入、也不被写入阻塞——那你这句"不持写锁"到底在防什么？如果不这么设计、直接开一条大查询去导这棵几十万行的树，真实会发生哪几类事故？

### 标准回答（完整版）

> 先承认前提：普通一致性读在 InnoDB 里靠 MVCC，确实不阻塞写入、也不被写入阻塞——所以我要防的**不是"单条读被写阻塞"**。
>
> 第一，我明确**不用 `FOR UPDATE`**。如果哪个想当然的方案为了"锁住一棵稳定的树"去做大范围锁读，人工修改、采集同步、移动删除就全得排队等导出结束——文件阶段越慢、锁持越久，写侧直接被读卡死。导出是低频重活，绝不能牺牲高频写入。
>
> 第二，真正要防的是**"跨语句的一致性"**。注意：**语句级快照是自洽的，但一次导出不可能一条 SQL 拿完**——平台列表、每个平台的节点、详情要分开读。如果每条语句各自开快照，而采集写入在导出过程中一直在提交，你就会导出一份"多时刻拼凑"的假快照：父节点是 10:00 的版本、子节点是 10:02 的版本；改名的字段前半段是旧名、后半段是新名；中途被删掉的字段还留在文件里。这份文件给下游做映射，是致命的。所以导出把全部读取放进**同一个 RR 事务**——第一次一致性读建立事务级快照，之后所有语句看到的都是同一版本。这就是"一致性只读快照"真正的含义。
>
> 第三，就算排除了锁和一致性问题，**直接一条大查询同步导出还有两类必然事故**：
> 一是**连接池和请求线程被打满、服务雪崩**。如果导出同步跑在请求线程上，一次导出占一个 HTTP 线程、同时占一个 MySQL 连接几十秒；两三个用户同时点导出，连接池就空了——采集在写、业务人员在改目录、普通查询，全拿不到连接，接口开始超时，慢查询越积越多，线程池排队把服务拖成雪崩。我们线上就吃过这个亏。
> 二是**JVM 内存被数据量撑爆**。百万级节点如果一次性读进堆、在内存里建成树对象、再用非流式 POI 拼 XLSX——非流式 POI 会在内存里建整本工作簿——内存随数据线性涨，几十万行就能吃掉几个 G，直接 OOM，或者长时间 Full GC、服务假死。
>
> 所以"不持目录写锁、只建一致性只读快照"防的是三件事：不锁写、不撕裂、不把自己打死。口径上我也注意，准确说法是"导出不持目录节点写锁"，不能说"数据库完全没有锁"——长 RR 事务仍占一个连接，undo/history、CPU、IO 都有成本，只是控制在"读快照"那一小段。

### 注意方向

- 💡 核心弹药：**"语句级快照 ≠ 跨语句一致性"**——导出要防的是撕裂视图，导出读取必须放进同一个 RR 事务。这句话一出口，面试官就知道你真懂 MVCC。
- ✅ 三类事故（连接池雪崩 / JVM OOM / 撕裂快照）逐个讲，按"锁、一致性、资源"三个维度组织。
- ⚠️ 口径一致性：简历标题"读写分离"被追问"是不是配了主从/从库"时，回答"是**任务/连接池层面的分离**：导出不占业务写连接、与采集写入并行"，不要顺着说有从库（你没提过从库）。文档站 01/40 章已统一此口径。
- ⚠️ 别说"完全无锁/零成本"这种绝对话——主动补"长事务仍占连接、有 undo 成本"，反而显得严谨。

## Q9：你们已经有 MySQL 一致快照了，为什么还要倒进本地 SQLite 再展开？为什么不在 MySQL 一条 SQL 搞定、或直接在 JVM 里建树？

**考察意图**：架构取舍的颗粒度。这题考你三个层面：资源边界意识（重活不能压源库）、内存模型意识（谁攒谁爆）、以及一个高级概念——**可重放、可核对的"死中间态"**。

**问题原话**：多引入"本地 SQLite 工作区"这个中间组件是有代价的（多一跳 IO、多一份磁盘、多一个要维护的部件）。你买到的到底是什么？没有 SQLite、用另外两条路，分别会死在哪？

### 标准回答（完整版）

> 两条被我否掉的路，恰恰能说明 SQLite 买到了什么。
>
> **第一条路：MySQL 一条 SQL 展开 + 排序出全量。** 技术上能——MySQL 8 有递归 CTE。但这条路把我们整套设计最想躲开的那件事又请回来了：递归展开、路径编码、对百万行带长路径串的数据做全局排序，这是典型的**重活**，放在源库上意味着三笔账：一是生产库要为一次交付物付出 filesort、临时表，CPU 和磁盘被导出偷走——我们正是靠快照才做到"导出期间采集和写入照常跑"，这条 SQL 一上去就破坏了它；二是要保持一致性，它得在一个长 RR 事务里全程持有连接和 read view，加工越久，undo 堆积、连接占用全回来了；三是**中途失败等于整单重来**，再伤一次源库。
>
> **第二条路：JVM 里把树建出来遍历。** 这条路撞的是内存墙——百万节点建成对象图，再配一张 parent 查找用的 Map，轻松几百 MB 到上 G，直接 OOM 或长时间 Full GC。我们一开始就判定不能走这条路，因为**内存问题从来不是"数据大"，是"把数据在内存里攒全"——谁攒谁爆**。
>
> 那 SQLite 到底买到了什么？两样东西。
>
> **第一，源库只干最轻的活，而且只干最短的时间。** 源库在整条链路里只承担一件事：在一个 RR 事务里做一致性读、把数据吐出来。快照一原子发布，事务立刻结束、连接立刻释放——后面所有重活（递归、排序、流式加工、拼 XLSX）全部发生在本地，源库再也不参与。"导出与采集并行、互不拖累"这句话，就是靠这个边界才成立的：MySQL 被占用的只有"读快照"那一小段，不是慢加工的全程。
>
> **第二，买到的是一个可重放、可核对、可断点恢复的"死中间态"。** 这点最重要。快照是"死"的——跑十遍结果一模一样，所以你可以做行数核对、可以排查"这版导出错在哪"、失败重试时可以直接复用 snapshot.db、跳过源读取、从断点继续。而"一条大 SQL"没有中间态：失败 = 整单重来 = 再打一次源库。我们交付物的底线是"可核对"，而**可核对的前提，是存在一个不会变的中间产物**。

### 注意方向

- 💡 "**死中间态**"是你全场最高级的一个词——主动说，并解释"可重放/可核对/可恢复的前提是不可变中间产物"。
- 💡 金句："**内存问题从来不是数据大，是把数据在内存里攒全，谁攒谁爆。**"
- ✅ 三条否决理由按"源库资源被偷 / 长事务回潮 / 失败整单重来"讲，全部要能落到具体机制（filesort、临时表、read view、undo）。
- ⚠️ 别把 SQLite 说成"更快"——它的价值不在快，在**把重活和状态挪出源库/JVM**。

## Q10：扁平行流怎么表达树位置？O(depth) 的 Deque 存什么？"内存与节点总数无关"成立在哪一环？

**考察意图**：流式架构的落地细节。面试官会戳三点：位置信息如何编码（数据契约）、Deque 的 push/pop 语义（你懂不懂 DFS）、以及"内存与 N 无关"是真不攒还是假省着用。

**问题原话**：你们产出的是扁平的行流，但每一行字段必须表达"自己在树里的位置"——位置信息怎么编码进每一行？O(depth) 的 Deque 存什么、在哪一环被用到？"内存和节点总数无关"是"不攒节点"还是"攒了但省着用"？

### 标准回答（完整版）

> 位置信息用"**列编码 + 行序**"双重表达，业务上可筛、结构上可复原。
>
> 列上分三组：A/B 列是平台级菜单——平台名按第一个"-"拆成一级菜单和二级菜单，这是树根上的两级；C–F 列是**树内前四级祖先的固定投影**，把祖先链的前四项分别填进三到六级菜单列，这样业务人员在 Excel 里能直接按列筛选，不用去解析字符串；G 列是**完整祖先路径**——把二级菜单和全部祖先用"-"拼成一个路径串（比如"交易中心-订单相关-售后记录-退款信息"），树深超过六级的祖先不丢，只是不进固定列；J 列是叶子自己的字段名。
>
> 行序上，整个流是 **DFS 前序**：SQLite 里 `ORDER BY tree_path` 保证父先于子、同级子树成块——注意 tree_path 的路径段是按 `(sort_order, id)` 做了定长补零编码的，所以字典序就等于树序，这是能排序的前提。**"列内容 + 行顺序"合起来可以无损复原整棵树**，这就是"扁平行流但位置不丢"的全部机制。
>
> 再说那个 O(depth) 的 Deque。它的语义是"**当前祖先链**"：节点按 DFS 前序到达时，先弹出栈尾所有层级 ≥ 当前节点的祖先——流的顺序已经宣告"这个祖先的子树走完了"，所以弹栈不是去查子节点；然后如果当前节点还有子节点就压入栈（记住"我现在在谁下面"），如果是叶子节点就**复制一遍祖先路径 + 自己的字段名产出一行**——复制栈是因为一行要把完整祖先链写进 C–F 和 G 列。整条链上 JVM 不做任何逐节点查询，未来的节点都还躺在 SQLite 的结果流里。
>
> 至于"内存与 N 无关"成立在哪一环——它成立在 **JVM 加工环节**，前提是前面把所有随 N 增长的存量全部安排在磁盘上：节点全集在 SQLite 快照里、排序中间态在 SQLite 临时文件里、输出行在 `rows/*.bin` 和 SXSSF 的临时 XML 里。堆里只留下两样东西：与树深度相关的 O(depth) 路径栈，和三个固定常数窗口（SXSSF 100 行窗口等）。所以形态是"**不攒**"——随 N 增长的存量被赶出堆外，JVM 只保留路径上下文。唯一带"攒"字的是那个栈和 100 行窗口，但它们是有界常数，恰恰证明这不是"省着用的 O(N)"——因为 **N 从头到尾没有进过堆**。整体复杂度是 O(N + L×depth)：N 是流节点数、L 是叶节点数，时间随数据走，但堆内存不随 N 走。

### 注意方向

- ✅ 主动补半句"**tree_path 按定长补零编码，字典序 = 树序**"——上次你没说，被面试官点破；这是纯字符串排序做不到的。
- ✅ "固定列投影（好筛）+ 完整路径列（无损）+ DFS 行序（可复原）"是双编码设计，主动讲出"业务要能按列筛选"这个用户视角。
- 💡 收尾句"唯一带'攒'的是有界常数，证明它不是省着用的 O(N)"——"主动排除另一种解释"是技术深度的外显。
- ⚠️ 别把复杂度说成"O(1) 内存"——严谨说法是"堆内存与 N 无关，为 O(depth)+常数；总耗时与临时文件仍随 N 增长"。

## Q11：导出跑到一半挂了怎么办？.part、下载门控、幂等、原子提交各守在哪一环？

**考察意图**：异常意识与工程完备度。这题没有标准答案，面试官在听你有没有把"进程被杀 / 磁盘满 / 重复触发 / 竞态窗口"这些脏事都想全。

**问题原话**：任务跑到 60% 容器 OOM 被杀、磁盘写满、用户取消后又有人重复触发——怎么保证不产半个文件、已跑阶段不白费、不会同时两份全量导出抢资源？

### 标准回答（完整版）

> 我们把这条链拆成"写入侧、读取侧、清理侧、触发侧、执行侧"五道防线：
>
> **写入侧：.part 隔离 + 原子提交。** 整条链上所有"写了一半"的东西都带 `.part` 后缀——`snapshot.db.part`、`manifest.json.part`、`field-dictionary.xlsx.part`。`.part` 永远不是合法产物：SQLite 要完整提交后才从 `.part` 原子改名成 `snapshot.db`；Excel 要 `workbook.close()`、算完大小和 SHA-256 后，才 `ATOMIC_MOVE` 到正式 key。这样任何时刻都不存在"可被当成成品的半截文件"。
>
> **读取侧：下载门控。** 这里有个容易漏的竞态窗口：进程可能死在"物理文件已经挪到 final key、但数据库还没提交 SUCCESS"之间。我们的下载接口在打开文件前必须同时满足三个条件——任务状态是 SUCCESS、详情完整（大小/哈希都写好了）、物理文件存在且大小一致。而且状态和文件详情是在**同一个数据库事务**里更新的：详情没提交，下载就永远被状态栏着，半成品不可能流出去。
>
> **清理侧：孤儿回收 + TTL。** 上面那个窗口里留下的孤儿 final 文件，由巡检/清理器按时间窗口回收，不会变成可下载的半成品；工作区按最后修改时间和 TTL（24 小时）由每小时清理器回收，成品按保留期（7 天）每日清理并记录 `file_deleted`。磁盘水位、临时文件量是我们文档里明确标了"生产必须监控"的项——我的态度是：**磁盘真的写满了，最该问的是为什么没有提前告警，而不是指望重试能把数据救回来。**
>
> **触发侧：幂等键。** 带 `Idempotency-Key` 的请求，用"创建人 + 分隔符 + key"做 SHA-256 生成**确定性任务号**：同一个人、同一个 key、同一种导出，直接返回原任务，不新建；key 一样但类型或平台不一致，返回幂等冲突。
>
> **执行侧：状态条件更新。** 就算没有幂等键、两个人各建了一个任务，执行侧还有一道保险：任务领取用状态条件更新——`UPDATE … SET status='RUNNING' WHERE status IN ('PENDING','RETRYING')`，数据库保证只有一条更新成功，所以一个任务只会被一个执行者跑，不可能重复执行。
>
> 最后说边界：以上是**单实例**下的完整结论——我们公司内部场景不是 C 端大并发，所以是单实体部署。如果被问到多实例，我清楚破绽在哪两处：确定性任务号和状态条件更新其实**天然抗多实例**（唯一性和 CAS 都在数据库层），真正依赖单实例的是**本地 SQLite 工作区的归属**和**清理器**——多实例要升级成可靠队列/租约、共享或对象存储工作区、全局配额。

### 注意方向
