# 02 · 采集范式演进

> 对应简历点：**"采集范式演进（核心 AI 应用能力）：针对早期 Agent + Playwright 全量抓取存在采集不全、整页 HTML Token 消耗高、结果不可控等问题，重构为『人工定界 + 浏览器插件采集 + Agent 解析』方案；基于 DOM 定制内部插件，完成 DOM 清洗、敏感值掩码及 sourceNodeId 节点回指，由 Agent 负责层级与字段语义解析并支持人工预览核验。单页 DOM 18.2KB → 3.3KB（-82%）"**。
> 本篇问题：Q3（第一版怎么翻车）→ Q4（三段式设计动机）→ Q5（中间产物与受限机制）→ Q6（效果量化口径）。这条链是"核心 AI 应用能力"，面试官会挖得最深。

---

## Q3：第一版"Agent + Playwright 全量抓取"在真实页面上是怎么翻车的？

**考察意图**：真实性检验 + 技术判断力。面试官听的不是"这方案不行"的结论，而是你**亲眼撞到的具体失败**，以及你有没有把失败归类到本质（完整性 / 成本 / 可控性），而不是停留在"调参没调好"。

**问题原话**：最早跑的是 Agent + Playwright 自动遍历抓取，后来才重构掉。讲一两个具体翻车场景——是抓不到、抓回来没法用，还是你怎么判断"这条路走不通、必须换范式"？

### 标准回答（完整版）

> 当时我们用基于 Codex 的 Agent 去驱动 Playwright，登录真实业务后台（比如抖音商家后台）让它按我们设计的技能全量抓字段。一开始在结构清晰的页面上效果还可以——表格、明面上的路由层级，它能返回不错的结果。但很快暴露了三类问题，而且都不是调技能描述能解决的。
>
> **第一类，也是最致命的：采集不完整，而且它不知道自己不完整。** 典型场景是折叠框和隐藏字段。比如一个"售后记录"页签，里面的字段是懒加载的，没展开就不渲染。Playwright 的 Agent 看不到没渲染的东西，它把当前页签扫完就认为完事了——**看到渲染完就走了，然后自信地报告"采集完成"**。还有的页面结构是"看起来同级、业务上其实是上下级"，Agent 没有业务上下文，判断不了。更糟的是京东那种防护比较强的页面，自动化驱动根本拿不到完整的 DOM 层级。我们试过去优化技能描述和脚本，但每解决一个 case，下一个 case 又冒出来——说明这不是某个页面没写好，而是**范式上它就没有"完整性判据"，无法自证采全了**。
>
> **第二类：贵，贵到不可持续。** 真实页面都是 React/Vue 加组件库层层包出来的——一个 `ant-form-item` 外面能套七八层 div，class 全是随机 hash。整页 HTML 动不动几十上百 KB，其中绝大部分是跟字段识别毫无关系的包装层、脚本和样式，喂给模型的 token 按页面复杂度线性涨。我们当时量过，一个典型区域原始 DOM 就有 18KB 以上，真正有用的可能不到五分之一。全公司 15+ 个平台、一百多万字段，这个成本根本扛不住——**当时抓一个页面，就把一周的 Plus 额度烧完了**。
>
> **第三类：结果不可控、没法追责。** Agent 自由发挥，同一个页面这次和上次抓出来的可能不一样；出了问题，你没法说是哪一步错的、责任在哪。而公司对字典准确率的要求很高，纯 Agent 这条路在"可信"上就过不了关。
>
> 所以我们的结论是：这不是把 Playwright 换成别的工具、或者把 Prompt 写得更细就能解决的——**让一个看不见完整页面、又没有判据的模型去决定"看什么、采什么"，这个范式本身错了**。这就是后面重构的起点。

### 注意方向

- 💡 **金句（务必背）**："看到当前页签渲染完就走了，然后自信地报告采集完成"——用这句话点破 Agent 的"无完整性判据 / 不知道自己不知道"。
- 💡 量化痛感："一个页面烧掉一周 Plus 额度"比"token 消耗高"有说服力十倍。
- ⚠️ 工具名别说含糊（别说自造词），就说"基于 Codex 的 Agent + Playwright"。
- ⚠️ 折叠框、隐藏字段、未渲染页签这些例子是"**完整性**"问题；组件库包装、hash class 是"**成本/噪声**"问题；自由发挥、无法定责是"**可控性**"问题——三类分开讲，别混成一锅。
- ✅ 收尾定性句"范式错了，不是调参问题"是转向 Q4 的最佳过渡。

## Q4：为什么新范式偏偏是"人工定界 + 插件采集 + Agent 解析"三段式？两刀分别治什么病？

**考察意图**：设计动机，检验方案是"想出来的"还是"撞出来的"。面试官会逼你把每个设计决定对应回 Q3 的每一类病。

**问题原话**：定界为什么必须交给人？采集为什么从 Agent 手里拿走、交给浏览器插件？这两刀分别治你刚才讲的哪类病？

### 标准回答（完整版）

> 这两个决定其实是同一件事的两面——**把"完整性"和"责任"收回到人身上，把"噪声"和"成本"挡在模型前面**。
>
> **第一刀，定界交给人，治的是完整性和定责。** 第一版失败的根本原因是 Agent 没有完整性判据、也不知道自己不知道什么。但业务人员恰恰知道——他清楚自己要采的是"退款信息"还是"物流信息"。所以新范式让人来划范围：**"采什么、采到哪算完"由人决定**，Agent 不再负责决定边界。还有一个更现实的原因：公司对字典准确率要求很高，纯 Agent 的产出**没法定责**——出了问题找不到人扛。业务人员参与进来（他定界、他最后确认），安全性和准确性就有了责任主体。
>
> **第二刀，采集从 Agent 手里拿走、交给浏览器插件，治的是噪声、成本和"拿不到"。** 三个层面：一是插件用确定性代码做结构清洗——删除脚本样式、压缩组件库包装层、掩码输入框真实值，把 18KB 的原始 DOM 压到 3.3KB 再进模型，上下文干净了，token 也省了；二是插件能拿到 Agent 拿不到的 DOM——真实渲染后的结构、Shadow DOM、跨域 iframe 内部的字段，都能读；三是这里有一个容易被低估的结构性优势：**插件跑在业务人员自己已登录、已打开的浏览器会话里**。登录是真实用户完成的，页面由真实会话打开，不存在自动化驱动被风控识别的对抗问题——像京东那种防护强的页面，第一版抓不到，这个方案天然绕开了。
>
> 而 Agent 保留了它最擅长的部分：基于这份干净的结构化快照，判断**业务语义和真正的层级**。一句话总结：**把不确定关进"人定界 + 插件定结构 + 受限 Agent 定语义"的笼子。**

### 注意方向

- 💡 "**纯 Agent 没法定责**"是你独有且罕见的理由——大厂面试官会很吃这一套，一定主动讲。
- ✅ "插件跑在业务人员已登录会话里 → 绕开登录态和风控防护"是**你必须主动补上的点**（你第一次答漏了，面试官帮你补的；已在项目文档 10 章固化）。
- ⚠️ 回答要"病 → 刀"一一对应：完整性无判据/无法定责 → 人定界；噪声贵/结构不可信/防护拿不到 → 插件定结构；语义判断 → Agent 定语义。别只讲"每段做什么"。
- 💡 收尾金句："把不确定关进笼子"——这句方法论贯穿全场，结尾还能复用。

## Q5：插件清洗完交给 Agent 的中间产物长什么样？你靠什么让它"只能"做语义解析、不能自由发挥？

**考察意图**：技术实现细节 + 受限 Agent 的设计功力。这题在检验你**数据契约**意识和**权限/感知隔离**意识。

**问题原话**：插件交给 Agent 的是一份什么样的中间产物？第一版失败在 Agent 自由发挥，这版是"受限解析"——你具体靠什么机制限制它？约束装在哪几道环节？

### 标准回答（完整版）

> 先说中间产物。插件交给 Agent 的不是原始页面，而是一份**去噪、去敏的结构快照（DomSnapshot）**：只保留能支撑后续判断的东西——层级标签、带业务名称的 span、label 与控件的关联、表头顺序这些结构证据；每个节点带一个采集期内稳定的 `sourceNodeId`，可以回指回页面原节点。**输入框的真实值、订单号、金额这类敏感数据会被掩码删除，根本不会进入 Agent 的判断，也不出浏览器**——这是合规底线。
>
> 至于怎么让它"只能"做语义解析，我们的设计是三层隔离：
>
> **第一层，感知隔离——它没有"眼睛"。** 第一版 Agent 是自己开浏览器、想看哪看哪，自由发挥最大的来源就是"自己决定看什么"。新版 Agent 眼前只有插件交给它的那一份快照，页面区域是业务人员通过插件选的，它想"看别的页面"也没有通道。
>
> **第二层，权限隔离——它没有"手"。** Agent 从头到尾没有任何写权限：碰不到数据库、碰不到正式目录，它只做一件事——**交一份建议**。真正把字段写进目录的，只有业务人员最后点确认的那一下。
>
> **第三层，出口校验——它交的东西还要过闸。** Agent 的产出先是 `HierarchyProposal`，由后端编译成前端同构的 `FieldTreeDraft`，再走确定性校验：JSON 结构合法性、是否存在多个父级/环/超深、每个结论能不能回指到证据、同级有没有重名冲突。校验不过就生成 `RepairFeedback`，交给受限的修复节点做局部重算，最多两次；还不行的，标记 `PARTIAL` 交人工。
>
> 这里还有一个推论值得说：正因为 Agent"没眼睛"，它**永远无法自证采全了**——所以"完整性"这个责任被我们设计性地前移给了"人定界 + 插件快照"。这跟"业务人员参与才能定责"是同一套逻辑的两面。

### 注意方向

- 💡 "**没有眼睛、没有手**"是这题的骨架话术，请原样背下来（感知隔离 + 权限隔离）。
- ✅ 主动讲中间产物细节（保留什么/删什么/sourceNodeId/掩码）——这是"数据契约意识"的直接证据。
- ✅ 收尾补"完整性责任前移"推论，逻辑闭环，面试官会觉得你想得深。
- ⚠️ 别说"通过 React 的执行方式"这种含混话——就说"多 Agent 按职责编排（Evidence → Hierarchy → Field Semantics → Reflection），独立验收节点复核"。文档站 20 章有完整编排，背下来。
- ⚠️ 角色名/产物名要说得顺：EvidencePack → HierarchyDraft → SemanticDraft → ReflectionReport → HierarchyProposal → FieldTreeDraft。

## Q6：18.2KB→3.3KB 是怎么测的？除了体积，有没有口径衡量"比第一版准了多少"？

**考察意图**：数据素养 + 诚实度。这题有两个陷阱：把代表样本吹成全量统计结论（会被抓）；"正确率高"这种空话（会被追着要口径）。你上次第一段答得很好，第二段有缺口——标准答案补齐。

**问题原话**：这个 18.2→3.3 是怎么测出来的？在什么页面上、采样了几页？准确率怎么算、人工复核的比例大概多少？

### 标准回答（完整版）

> 先说 18.2→3.3 是怎么测的。它的口径是：拿一个典型的业务页面区域（组件库风格的表单/详情块），**固定同一个选区、固定同一个页面状态**，先量清洗前的原始 DOM 字节数，再量清洗后快照的字节数，两个一除。要说明的是——这是**代表性样本上的量级测量**，不是"采了几十页取平均"的统计结论；我们在文档里也明确写了"不外推为所有页面的固定压缩率"。真实生产里不同页面的压缩比会有波动，所以我们同时会记录 Token 变化、字段证据保留率这些指标，避免为了压缩把业务语义也删没了。
>
> 质量维度我们后来补了一个口径，我觉得比单纯说"准确率高"更站得住：**统计"草稿节点里人工实际修订/删改的比例"**。Agent 解析完先出一版草稿树，业务人员审核时会改名字、挪层级、删错的节点——把"人工改动的节点数 ÷ 草稿总节点数"算出来，比如 100 个节点只改了 3 个，那就是 97% 的草稿节点不需要动，这才是可核对的"正确率"。另外我们从端到端时间上也验证过：业务人员用日常可支配的时间，平均一天能采集完一个平台；而第一版方案一个页面都跑不完、更别说一个平台——时间维度上是数量级的提升。

### 注意方向

- ✅ **保留"代表性样本、不外推"的自知之明**——这是加分项不是减分项，说明你真测过。
- ⚠️ 不要再答"准确率没具体算，业务上觉得安全可靠就行"——这是你上次的减分点。要么补出"复核改动率"口径（见上），要么诚实说"当时以业务上线验收为准，复核改动率没有单独统计"，并立刻补"如果要量化，正确口径是统计人工修订比例"。
- ⚠️ "1 天/平台 vs 一周/页"是**时长成本维度**的证据，和"质量维度"是两回事，分开讲，别混着说。
- 💡 简历里"结果可控、正确率高"是空话——真实面试前把它替换成有数字的表述，或者删掉"正确率高"。

## 本篇小结（注意方向汇总）

1. 采集链四问是一条完整叙事：**病（Q3）→ 药（Q4）→ 药的机制（Q5）→ 疗效怎么验（Q6）**，背熟后可以一口气讲下来。
2. 三条金句必背：*"自信地报告采集完成"* / *"没有眼睛、没有手"* / *"把不确定关进笼子"*。
3. 两个必补的严谨点：插件"跑在已登录会话绕开风控"、测量"代表样本不外推"。
4. 两个必补的量化口径：采集的"人工修订比例"（替换"正确率高"）。
