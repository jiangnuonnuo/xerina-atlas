# 04 · 目录治理（预案）

## 一、30 秒版（概览，张口就来）

> 目录是一棵长期维护的树，我们的治理目标是三个不变量：**不重复、不断链、不丢更新**。
> 做法上分四块：**防重**用双层——应用层先做名称冲突预检，数据库再用"存储生成列 + 唯一索引"做并发竞态的最后防线，逻辑删除时生成列置 NULL 自动释放同名；**并发子节点**用父节点行锁 + 同级排序尾行 `FOR UPDATE` + 版本号 CAS，保证后写不覆盖先写、不同节点可并行，不锁整张表；**移动子树**按节点 ID 升序锁 + 锁后闭包集合复查 + 有限重试，把死锁概率压到可控；**存储结构**用邻接表存直接父级事实（写入的真相）+ 闭包表支持祖先/子树 O(1) 查询，逻辑删除保留闭包以支持恢复，任何结构变更在事务末尾递增 `tree_version`，前端凭版本失效刷新。冲突都可压测复现成 409 可恢复错误：同节点并发修改是一个成功、一个 `NODE_VERSION_CONFLICT`；同级同名是一个成功、一个 `DUPLICATE_SIBLING_NAME`。深度上限 64、单批 ≤100 节点、写事务 10 秒超时。

## 二、2 分钟版（深讲，逐层展开）

### 2.1 先讲清楚"为什么目录治理难"

> 字典不是一张把名称存下来的表，它是一棵**长期维护的树**：字段挂在分组下，分组挂在平台下，业务人员每天都在上面做新增、改名、移动、删除。树结构最难的是并发下的三个不变量：同一父级下不能出现两个同名的（**不重复**）；移动/删除不能让子树断在中间、不能让某个节点同时有两个爸爸或形成环（**不断链**）；两个人同时改同一个节点，后写的不能把先写的悄悄覆盖掉（**不丢更新**）。这三个不变量一旦破了，下游拿字典做映射就会静默出错——比报错更可怕。

### 2.2 防重：双层防线

> 第一层在应用：写之前先做一次可读的名称冲突预检——但它只负责让用户早点看到友好的错误提示，**不承担并发正确性**。真正的最后防线在数据库：`catalog_nodes` 上用两个存储生成列——`unique_parent_id` 和 `unique_name`——建唯一索引 `UNIQUE(platform_id, unique_parent_id, unique_name)`。两个请求同时新增同名兄弟，数据库只让一个成功，另一个捕获唯一键冲突转成 `409 DUPLICATE_SIBLING_NAME`。逻辑删除的节点生成列置 NULL，所以删除后可以重新创建同名节点。为什么必须"存储生成列 + NULL 技巧"？因为 MySQL 唯一索引把 NULL 视为互不相等——这样已删除节点不参与唯一约束，不用做"部分唯一索引"这种 MySQL 不支持的事。

### 2.3 并发子节点：行锁 + 尾记录 + CAS

> 关键认知：**锁粒度是"事实行"，不是"整个平台"。** 具体到并发新增/改名：
> 新增子节点时锁**父节点行** + 同级**排序尾行**（`FOR UPDATE`）——锁父节点保证父级还在、锁尾行是为了给新节点算一个稳定的自动追加排序位；改名只锁目标节点行 + 版本 CAS。节点更新不是"先查后覆盖"，而是：工作台打开时读到 `version`，提交时带上 `expectedVersion`；写事务里 `findByIdForUpdate` 锁行，锁后重新读版本，然后执行 `UPDATE … SET version = version + 1 WHERE id = ? AND version = ? AND deleted = 0`，**影响行数必须为 1**，为 0 就返回 `409 NODE_VERSION_CONFLICT`。
> 这样两个人都从版本 7 打开同一节点时：先拿到锁的更新到 8 并提交；后拿锁的重新读到的已是 8，`expectedVersion=7` 校验失败——**后写绝不覆盖先写**，而不同节点之间完全并行，不把整张表锁死。

### 2.4 移动子树：升序锁 + 锁后复查 + 有限重试

> 移动是最容易出事儿的操作：可能移成环、可能把闭包弄脏、可能两个移动互相交叉死锁。我们的顺序是固定的：
> 1. 先用**非锁定**的闭包查询读出"移动子树"的候选 ID 集合（这只是候选，可能已过期）；
> 2. 候选集合去重、加上新父节点 ID，**按节点 ID 升序**执行 `id IN (…) ORDER BY id FOR UPDATE`——统一升序是为了避免 A 按顺序 A、B 按反序拿同一批锁造成的死锁；
> 3. 锁后**重新读取**子树 ID 再比对：如果集合和第一阶段不一致，说明等锁期间结构被改了，整笔事务回滚、有限重试——不能拿着过期集合继续写；
> 4. 校验通过后更新父级、按层差修正整棵子树的 `node_level`，闭包表只删"子树与外部祖先"的关系、插入"新父级祖先 × 子树"的笛卡尔组合，子树内部关系不动；
> 5. 事务末尾递增一次 `tree_version` 再提交。
> 我们不承诺"数据库永远不会死锁"——死锁发生时按错误码 1213 从**事务入口**重新执行有限次重试（30–150ms 随机退避），达到上限返回 `409 CATALOG_WRITE_BUSY`。

### 2.5 存储结构：邻接表 + 闭包表

> 两个表各管一件事：`catalog_nodes.parent_id` 是**写入的直接事实**——新增、改名、移动都围绕它执行，它不可替代；`catalog_node_closure` 存 `(ancestor_id, descendant_id, depth)`，包括自身关系（depth=0），用于**一次查询**拿到祖先链、子树、面包屑，查询与写入解耦。删除是逻辑删除、闭包保留，所以能恢复、能审计。任何结构变更在事务末尾递增平台 `tree_version`，工作台发现版本变了就失效刷新，不在本地用旧树做全量覆盖。最后补一句：闭包是**可重建的关系索引**，正式节点和直接父级关系才是业务事实——这句话能挡住"闭包坏了是不是全完了"的追问。

### 2.6 一个可压测的收尾

> 这些约束不是嘴上说说，都可以压测复现：同节点并发修改 → 一个成功、一个 `409 NODE_VERSION_CONFLICT`；同级同名并发新增 → 一个成功、一个 `409 DUPLICATE_SIBLING_NAME`；相交子树并发移动 → 一方提交、另一方锁后复查回滚或重试。我们的验收基线是：深度上限 64、单批 ≤100 节点、写事务 10 秒超时、死锁重试上限后转 409。

## 三、追问弹药库

| 可能的追问 | 一句话答案 |
|---|---|
| 为什么用"存储生成列"，不能直接建唯一索引？ | 唯一索引要把"已删除节点"排除在外，MySQL 无部分索引；生成列在删除时置 NULL，利用"NULL 互不相等"天然释放约束 |
| 为什么不用"整个平台一把锁"？ | 会把所有高频写串行化；锁到"本次命令实际需要互斥的事实行"即可，靠唯一索引 + 锁后复查兜并发正确性 |
| 为什么移动要先非锁定读候选、再升序锁？ | 锁前快照可能过期；先发现候选集合、再统一升序加锁并**锁后复查**，避免死锁与基于过期集合写入 |
| 闭包表坏了一半怎么办？ | 闭包是可重建索引：以邻接表事实为输入、拓扑序重建并校验计数/深度/无环；巡检发现问题只生成修复任务，不在在线请求里静默重建 |
| 深度的 64 是怎么来的？ | 目录治理的 `maxDepth` 不变量（配置基线 64）；导出侧不重复做拦截，靠写入准入 + 巡检保证 |
| 前端怎么感知别人改了树？ | 每笔写事务末尾递增平台 `tree_version`，工作台返回的版本与本地不一致就失效刷新，不覆盖未确认草稿 |
| 和导出快照是什么关系？ | 导出只读、不进写事务、不参与闭包修改；它用 RR 只读事务看到提交后的稳定版本（详见 03 篇 Q8/Q9） |
| 你文档里"读写分离"是指主从吗？ | 不是；是任务/连接池层面的分离——导出不占业务写连接、与采集写入并行（口径已统一） |
